# OpenDraft architecture

A 2D CAD app on egui/eframe. This file records the rules new code follows.

## Crates (dependencies point downward)

| Crate | Owns | Must not depend on |
|---|---|---|
| `opendraft-core` | Document, entities, geometry | anything else |
| `opendraft-commands` | `Registry`/`Command`, `Action`, undo `History`, `Session`, transactions, the `Editor` (user interaction) | egui |
| `opendraft-files` | File formats (`FileFormat` trait; native `.odraft` JSON, DXF import and export, DWG import by converting `opendraft-dwg`'s output), atomic save | egui, the app |
| `opendraft-dwg` | A standalone DWG reader (AC1024, AC1027, AC1032): container, header, tables, flat model-space shapes (ellipses, splines and text included), the text style table, named blocks with block references, and a typed report. Depends only on `opendraft-core` | egui, MCP SDKs, the app |

This table is a test: `opendraft-app/tests/crate_rules.rs` reads each crate's declared dependencies (`cargo metadata --no-deps`, offline) and fails if one depends upward, on a crate of ours it may not, or on what it must never depend on, and if a crate has no rule. Change a rule by editing this table and that test together. The `opendraft-agent` crate (see "Embedded assistant") may depend on `opendraft-api` and no other crate of ours, and never on `rmcp`, `interprocess`, `egui` or `eframe`, so the assistant can reach a drawing only through the operations outside programs use.


**Naming (shared with OpenCalc and OpenPath).** A crate is `opendraft-<role>`, always with the full product name, never a short prefix such as `od-` (a later app, OpenDraw say, would collide): `-core` is the model with no UI, `-ui` the theme and widget library, `-app` the program (binary `opendraft`), and a format crate is named after its format (`-dwg`). Environment variables are `OPENDRAFT_*`. Drawings are `.odraft` and templates `.odraftt` ("o" plus the product word, as OpenCalc's `.ocalc` and OpenPath's `.opath`). The bundled stroke font keeps its name, OD Roman.

## Rules

1. **Every user action is a command** in `opendraft-app/src/commands.rs`, built with
   `Command::new(..).key(..).when(..).checked(..)`. Ribbon, quick access, status
   bar, shortcuts and the command line refer to commands by id and read enabled
   and checked state from the registry. Never match on command ids in UI code
   to find state; give the command a `checked` predicate.
2. **Every document change is an `Action`** run by the `Session`, so it is
   undoable. A command that makes several edits groups them in a transaction
   so they are one undo step (see "Commands and the Editor"). Entity edits
   that keep ids and positions stable use `ModifyEntities`.
3. **Logic is pure and tested; UI only draws.** Anything with rules (property
   values, parsing, snapping, selection) lives in a function over plain data
   with unit tests. `state.rs` has no egui code.
4. **UI state that belongs to a widget** (open menu, typed text) lives in egui
   temp memory; **state that belongs to the user** (settings, layout) is
   persisted; **state that belongs to the drawing** lives in `Doc`.
5. **Files stay under about 400 lines of production code** (tests do not
   count). `opendraft-app/tests/file_sizes.rs` enforces it at 450, and keeps a
   list of files allowed to stay over, which may not grow (empty now: `view.rs`
   moved its painting to `view/paint.rs`, and `dxf/read.rs` is 401 lines). A file
   over the limit is split, or listed there with its size until it is. Split by
   responsibility, not by layer. `opendraft-app/src/app/` shows the pattern: `app.rs`
   owns the struct and the frame loop, and each submodule adds one area as an
   `impl` block.
6. **No `unwrap`, `todo!`, `dbg!` or prints in production code** (clippy warns).
   Unwrap is fine in tests. `unsafe` is forbidden.
7. **Wording helpers** (`text::plural`) are shared; do not repeat inline
   `if n == 1` pluralisation.
8. **An edit that touches many objects is one pass, never a loop of single
   edits.** `Document` keeps a lookup from id to position, so taking an object
   out or putting one in costs a pass over every object after it. Use
   `remove_many`, `insert_many`, `push_many`, `replace_many` and `replace_each`
   (`document/object_list.rs`, `document.rs`) for erase, the undo of an add,
   adding copies, changing geometry, and exploding blocks or dimensions for a
   file. They also update the spatial index once (see "Spatial index").
   `remove` and `insert` are for one object. A guard test for each such path
   (erase and undo, undo of adding copies, exploding references) fails if
   someone writes the loop; add one when you add a bulk path. Measure with
   `cargo run --release -p opendraft-app --example bench_features` before and after
   a change that may affect speed (earlier findings: `docs/history.md`, "Performance").

## Data model (design decision)

The drawing follows the AutoCAD/DXF shape, in typed Rust structs rather than a
generic property table:

- **Entities** are an ordered list (draw order). Each `Object` has a permanent
  `EntityId` that never changes and is never reused, a geometry enum (Line,
  Circle, ...) and common attributes: layer, colour, linetype, lineweight.
  Code that filters or groups objects by kind uses `Entity::kind()`, which
  returns the `EntityKind` enum (one variant per entity, so a new entity fails
  to build until every `match` has it), never a name. `EntityKind` also holds
  the three names, so a label can be reworded without changing behaviour:
  `display_name` (running text), `title` (headings, lists) and `wire_name`
  (the MCP and JSON token, part of the contract; `from_wire` parses it).
- **Symbol tables** hold layers, text styles, linetypes, blocks, and dimension
  and multileader styles. Entities refer to them by id, so renaming a layer edits one record.
  Each object has a layer plus colour, linetype and lineweight that are either
  `ByLayer` or set on the object (`Attr<T>`). A layer can be on, frozen or
  locked: hidden layers are not drawn, snapped to or picked; locked layers are
  drawn and snapped to but not picked. Layer 0 always exists and cannot be
  deleted, renamed, or removed while current or in use. Ask the `Document`
  (`color_of`, `is_visible`, `is_selectable`), never resolve this by hand.
- **Extension data**: each entity can carry a small key/value map namespaced by
  plugin id, so plugins attach data without new entity types. The core stores
  and saves it without interpreting it.

**Invariants.** A drawing has layer 0 first, unique layer ids and names
(ignoring case), unique object ids, every object on an existing layer, a
current layer that exists, and id counters ahead of every id in use.
`Document::validate()` checks all of that. The low-level mutators
(`push`, `insert`, `push_layer`, `replace_attrs`...) are what undo and redo
use to restore state, so they trust their caller; the net under them is that
`Session` validates after every `perform`, transaction, undo and redo in debug
builds and tests (an edit that breaks the drawing panics where it happened),
and `NativeFormat::write` refuses a drawing that fails it, so a corrupt
drawing is never written to disk. Not done yet: making the mutators return
`Result` so release builds also reject a bad edit at the call (listed in
`docs/parking_lot.md`, "Code"). `layer_of` still falls back to layer 0 for a missing
layer so that drawing never panics; `validate` is what reports it.

Rules that follow:

1. **Refer to entities by `EntityId`, never by list position.** Selection,
   actions, the undo history, files and plugins all use ids. `Document` hides
   its list behind `objects()`, `get(id)`, `add`, `remove`, `replace`; ids
   come from `allocate_id` and are never reused. The selection is a set of
   ids and survives edits, undo and redo (ids that no longer exist drop out).
2. **Geometry types stay closed** (the enum). Plugins build from built-in
   entities plus extension data; custom entity types are out of scope.
3. **Files are `opendraft-files`' job** (see "Files" below). The in-memory types are
   not serialised directly; each format converts to and from its own schema.
4. Properties shown in the panel come from the entity type plus the common
   attributes, so a new attribute adds its row in one place.

## Files

- **Native format:** `.odraft`, a JSON file with a header (`"format":
  "opendraft-drawing"`, `"version"`) and a `drawing` holding the layers, the
  objects in draw order, the current layer and the id counters (so ids of
  deleted objects are never reused, even after reopening). It is readable and
  diff-friendly on purpose, and the schema (`opendraft-files/src/native.rs`) is
  separate from the in-memory types so refactoring cannot change what is on
  disk by accident.
- **Versioning:** two phases, told apart by `CURRENT_VERSION`. *Development*
  (version 0, now): the schema changes in place with no bump and no
  conversion, and a file from an earlier build may not open; when a
  version-0 file fails to parse, the error says it is the development format
  and names the build that saved it (`saved_by`). *Stable* (version 1 and up):
  set to 1 once, as a deliberate release step. From then on adding an optional
  field needs no new version (readers ignore unknown fields), a new entity kind
  or anything else an older reader would misread bumps `CURRENT_VERSION`, and
  each older version gets a conversion in `read`. Only `CURRENT_VERSION` is
  read without a conversion; a newer file is refused ("saved by a newer
  version"). The header is read before the body, so a file of another version
  is refused by name (`WrongVersion`, with `saved_by`) rather than failing to
  parse. Declaring the format stable has a checklist in `CONTRIBUTING.md`.
- **Block expansion budget:** nesting is a graph, so depth alone does not bound
  the work (a block inserting the next one twice, forty levels, is 2^40
  objects from forty definitions). Expanding an insert visits at most
  `MAX_EXPANSION` (1,000,000) objects, nested ones included, and then stops;
  `BlockDef::expansion_size` counts it per definition (memoised), and the
  native loader refuses a file with a block over the budget.
- **Limits and ids:** a file over `MAX_BYTES` (512 MB) is refused before it is
  read. Id counters advance with `document::after`, which saturates, and a
  loaded drawing goes through `Document::validate` before it is handed over,
  so an id of `u64::MAX` is refused as damaged, not wrapped or panicked on.
- **Unknown entity kinds are refused, never skipped.** A reader that dropped
  an object it does not understand would delete it from the user's drawing the
  next time they saved. So once the format is stable, adding an entity kind
  bumps `CURRENT_VERSION`, and an older build reports the file as saved by a
  newer version; only optional fields can be added without a bump. In the
  development phase (version 0) the rule is the same in effect, since a
  reader always refuses what it does not understand, but nothing is bumped.
- **Version history:** none is kept while the format is in development. The
  numbers 1 to 8 that earlier builds used (see `docs/history.md`) were reset to 0 on
  28-10-2026, with no users and no compatibility kept. From version 1 on each
  older version gets a conversion in `read`.
- **Validation:** loading rejects what cannot exist (an object on a missing
  layer, repeated ids, a circle with no radius, no layer 0) with a message, and
  never loads half a drawing. Saving refuses what could not be read back.
- **Formats are pluggable:** `FileFormat` (name, extensions, read, write);
  `format_for(path)` picks by extension. `read` returns the drawing plus
  warnings (what did not come across) and whether it was an import; `write`
  returns the bytes plus notes (what the format could not keep). Two optional
  methods: `read_cancellable` (a slow reader gives up when the flag is set;
  the default ignores it) and `check_size` (refuse a file by its length
  before it is read into memory). The app opens through `load_cancellable`,
  which checks the size, reads, then dispatches, and passes the open job's
  Cancel flag; `FORMATS` is native, DXF, DWG, and the Open dialog's filters
  come from it. Before that, `AppState::open_path` asks about any file over
  20 MiB (`opendraft-app/src/large_file.rs`, "Open it anyway?"); it warns and
  never refuses. Automation opens skip the question.
  `.odraft` is also bounded by what it holds, not only by bytes: its long lists
  (objects, table rows, objects in a block, points of a shape) are cut off
  while they are read (`opendraft-files/src/native/limits.rs`), well above any real
  drawing, and building the drawing looks at the cancel flag as it goes.
- **DWG** (`opendraft-files/src/dwg/`, over the `opendraft-dwg` crate) is import only, on
  the same lifecycle as DXF: opening a `.dwg` installs an unsaved drawing with
  no file of its own and says "Imported", Save asks for an `.odraft` name, and
  `write` refuses (no Export DWG command exists). Files over the reader's
  1 GiB limit are refused before they are read. Its limits (`DwgLimits`) bound
  what a read allocates; one object may be as large as a section (512 MiB),
  since it is read in place and its size allocates nothing.
- **DXF** (`opendraft-files/src/dxf/`) is an exchange format, so it is treated as one:
  opening a `.dxf` is an *import* (a new unsaved drawing with no file of its
  own, so Save asks for an `.odraft` name) and `file.export_dxf` writes a copy
  without changing the drawing, its name or its unsaved state. We wrote our own
  reader and writer rather than use a crate because the available crate drops
  layer frozen/locked flags and cannot report what it skipped.
  - *Reading* takes any ASCII DXF version: lines, circles, arcs, splines (see
    "Splines"), ellipses (in any group order; a -Z extrusion runs the parameters the other way, a
    tilted one is skipped), lightweight and old-style polylines (with their bulges as arc segments), layers (colour, true colour, linetype, lineweight,
    on/frozen/locked), entity colour, linetype and lineweight. ARC entities
    stay arcs and polyline bulges stay bulges. Layouts and their viewports and sheet objects come in too (see "Layouts"), and named blocks with their references (see "Blocks"); hatches (see "Hatches"); everything else (text, dimensions)
    is skipped and counted in a warning shown in the command line. Files over 1 GiB are refused before
    they are read.
  - *Writing* is R12 (AC1009), which every CAD program opens and which needs no
    handles or object tables, except for a drawing with layouts, ellipses, splines or hatches, which is written as R2000 (AC1015; see "Layouts"): R12 has no ellipse, spline or hatch entity, and the R12 writer refuses one rather than approximate it. R12 cannot hold lineweights or colours beyond the
    255 AutoCAD indexes, so those are dropped or approximated and the notes say
    so; rectangles are written as closed polylines.
  - *Tests:* the writer's output is parsed by an independent library (`dxf`, a
    dev-dependency) and, in `tests/fixtures`, a DXF made by `ezdxf` checks the
    reader while `check_export.py` has `ezdxf` audit our output. Neither is
    AutoCAD itself, so a file that matters should still be opened in one.
- **Saving is atomic:** bytes go to a temporary file in the same folder, then
  rename over the target, so a crash or full disk never replaces a good file
  with a broken one. The temporary name (`.name.odraft.<pid>-<n>.tmp`) is unique
  to this process and save and is created exclusively, so it can never be
  another instance's file or one the user made, and the cleanup after a
  failure only ever deletes a file this save created. The file is synced
  before the rename and, on Unix, the folder after it.
- **File work runs off the UI thread** (`opendraft-app/src/io.rs`, `file_io.rs`).
  Open, save, export and autosave each have a `begin_*` half, which takes what
  the job needs (a path, or a *copy* of the drawing) and hands it to a worker,
  and a `finish_*` half that `AppState::poll_io` runs on the UI thread when the
  result arrives. The workers never see application state, so there is nothing
  to lock. They wake the window when they finish, since egui only draws when
  something happens. There are two kinds of job:
  - *Ordered* (recovery copies and their removal) share one worker and run in
    the order submitted, so a copy is never deleted before the write that made
    it has finished.
  - *Cancellable* (open, save, export: what the user waits for) each get a
    thread of their own, so one stuck on a slow disk or a dead network path
    blocks nothing else.
  - *Edits during a save:* the save writes the copy taken when it began and
    records the history position of that copy (`Session::mark_saved_at`), so
    anything done meanwhile still shows as unsaved.
  - *One at a time:* a drawing already being saved, or a file already being
    read, is not started twice. An autosave pass is skipped while the last
    one is still writing.
  - *Closing:* the "save changes?" question stays up showing "Saving..." until
    the file is written, and only then closes the tab or moves on. The window
    does not close while a file is being written (`AppState::can_quit`).
  - *Tests:* the app runs the worker on its own thread; most tests use an
    inline worker (`Io::inline`) that runs each job at once, and
    `file_io.rs` tests use the real thread.
  - *Cancelling:* after a second of file work the status bar shows a Cancel
    button, and Esc does the same (a quick save is not cancelled by a habitual
    Esc). A thread cannot be stopped from outside, so cancelling means
    forgetting it: its result is thrown away when it arrives, and a save that
    was cancelled checks its flag before the rename (`save_cancellable`), so a
    write that was stuck and finishes later never replaces the user's file. The
    drawing stays unsaved, a quit that was waiting on the write is called off,
    and the unsaved-changes question comes back so the user can try again.
    A cancelled job's thread may linger until the OS call returns.
  - *Not moved off yet:* recovering drawings after a crash reads its few
    files on the UI thread, and the file dialogs are the system's own.
- **Unsaved changes** are tracked by the undo history: `Session::is_modified`
  compares where the history is now with where it was at the last save, so
  undoing back to the saved state clears the star. Closing a tab or the window
  asks Save / Don't Save / Cancel for each modified drawing, one at a time
  (`opendraft-app/src/files.rs`; the dialog is `app/file_dialogs.rs`).
- **Folders the user may move** are `locations::Location` (Templates, Recovery, Library): the choice is an `Option<PathBuf>` field in `Settings` (none means the default, beside the saved settings), picked on Settings > Files, and read only through `Location::resolve`. New code never builds a path from `eframe::storage_dir`; a new movable folder is a variant in `Location`. Templates apply at once (`apply_settings` updates `AppState::templates_dir`); Recovery is read at start. Approved automation folders stay on the Automation page (a security grant, not a location).
- **Autosave and recovery** (`opendraft-app/src/recovery.rs`, `autosave.rs`): every
  few minutes (Settings > Files; default 2, can be off) each drawing with
  unsaved changes is written to this run's session folder under the app data
  directory, and the copy is deleted when the drawing is saved, closed or clean
  again. A normal exit deletes the whole folder, so only a crash leaves one. A
  running instance holds an exclusive lock on a file in its folder; a folder
  whose lock can be taken belongs to a dead instance, which is how the next
  start finds the leftovers without mistaking another running copy's files for
  a crash. Recovered drawings open as unsaved (and, if they had a file, keep
  its path, so Save writes back to it); closing the offer keeps the copies for
  next time.
- **The app** opens files from the Open command (Ctrl+O), the recent list in the
  application menu (the "A" button), drag and drop onto the window, and paths on
  the command line (so a file association works). A drawing already open is
  switched to, not opened twice; a blank untouched drawing makes way for the
  one being opened. File dialogs sit behind `FilePicker`, so tests script them.

## Commands and the Editor (built)

The command model follows the AutoCAD .NET SDK, using the same words so people
who know it find their way, minus its ceremony.

**What commands remember.** The values a command offers again (the last
rectangle rounding, text height, hatch pattern, polygon sides...) are not
globals. `opendraft-app/src/defaults.rs` holds one `CommandDefaults`, a `Slot` per
section, owned by `AppState` and saved with the user's settings. `AppState`
hands it to each command it starts as a `opendraft_commands::Context` (a typed bag
`opendraft-commands` only carries), and a command reads it with `ed.defaults()`
(`EditorDefaults`); system variables and dialogs reach it through
`AppState::defaults()`. Two `AppState`s therefore never share defaults, and
tests need no turn-taking locks. A new remembered value is a `Memory` struct
with `load(storage)` and `save(&memory, storage)` in its own `*_memory.rs`,
plus a field on `CommandDefaults`. The one remaining global is
`window_memory.rs`, the window size, which is the shell's, not a command's.

**Status.** Every interactive command is written this way: Move, Copy, Rotate,
Mirror (`opendraft-app/src/modify.rs`), Scale and Rotate with Copy and Reference
(`scale_rotate.rs`), Line (`draw.rs`; its first prompt also offers Single and Middle,
which run LINE SINGLE (SL: lines that do not chain, each given by its two ends) and LINE MIDDLE
(ML: each line given by its middle, then one end, the other mirrored), in `line_modes.rs`; at
LINE MIDDLE's end, dynamic input shows the half length, then on Tab the whole length (`Field::Length`,
`DynamicDimensions::Mirrored`), and a bare number is the half length; both are in the ribbon's Line list), Circle (`circle.rs`), Arc (`arc_cmd.rs`),
Rectangle (`rectangle.rs`, settings in `rect_memory.rs`; from the centre, by
three points and the oblongs in `rect_variants.rs`), Polyline
(`polyline_cmd.rs`, arc options in `polyline_arc.rs`), the window polygon, crossing polygon and fence
selections (`selection.rs`), Trim and Extend (`edges.rs`; the Edge option, `EDGEMODE`, lets each edge act as if it ran on past its ends: `Entity::with_implied_extension` in `opendraft_core::implied_edge` turns a line into the infinite line, an arc or an elliptical arc into its whole circle or ellipse, and an open polyline into itself plus a ray, or the circle of an arc segment, beyond each end; the options at the object prompt are Fence, Crossing (typed; a click in empty space starts the same window), mOde, Project (`PROJMODE`: kept for scripts, and it says that it changes nothing, because everything is flat and the coordinate system and the view only turn within the one plane), Edge, eRase (erase objects without leaving the command) and Undo, the small ones in `edges_options.rs`; the settings are remembered with `TRIMEXTENDMODE` in `trim_memory.rs`, user settings, not the drawing), Offset
(`offset.rs`: Through, Erase and Layer (Current or Source, asked when chosen, for the rest of the command) at the distance prompt; at the side prompt Multiple keeps offsetting the one object, each copy measured from the last by a distance and each point from the object for Through, Erase removing only the original; Exit and Undo at both prompts, each copy being one undo step; the last distance, or Through as a negative one, is the default, `OFFSETDIST`, in `offset_memory.rs`, user settings), Fillet and Chamfer (`corners.rs`, with Multiple, where Undo takes back the last corner, and Chamfer's mEthod between distances and length and angle; settings in
`corner_memory.rs`), Join (`join.rs`, geometry in `opendraft_core::join` and `join_gap.rs`: lines on one line and arcs of one circle, and elliptical arcs of one ellipse (`ellipse/join.rs`), join across gaps, the first object being the source and arcs running counter-clockwise from it; the Fuzz option at the selection prompt lets ends that miss by that distance join with a straight link; a lone arc, elliptical arc or open polyline offers Close, making a circle, an ellipse or a closed polyline), Explode (`explode.rs`; a pattern hatch becomes its strokes as lines and points, solid and gradient fills are left with a note), Object isolation (`isolate.rs`: ISOLATEOBJECTS, HIDEOBJECTS and UNISOLATEOBJECTS set `Document::hidden_objects`, which `Document::is_visible` honours so painting, picking, snapping and plotting skip them; not an edit, not undone, not saved, and the drawing is not marked changed), Arrays (`array_cmd.rs`, `array_path.rs`, `array_make.rs`; the geometry is `opendraft_core::array`, and an array is also an `ArrayRecord` in `Document::arrays` (sources, the items made, and the settings), saved in `.odraft` (`native/array.rs`) and set by the undoable `SetArrays`; ARRAYEDIT in `array_edit.rs` runs the same options from the record's settings and replaces the items; `ARRAYASSOCIATIVITY` 0 makes plain copies; the items are ordinary objects, so erasing one does not change the record), Draw Order (`draw_order.rs`, DRAWORDER or `DR`, and the four context-menu choices; the objects keep their ids and their order among themselves, in the one `ReorderObjects` action in `opendraft-commands`), Lengthen (`lengthen.rs`; lines, arcs, elliptical arcs, whose length is integrated and whose end is found by bisection in `opendraft_core::lengthen_ellipse`, open polylines, and open splines (`spline/lengthen.rs`: shortening cuts the curve exactly by knot insertion, lengthening continues it as a straight tail along the end tangent, built into the frame by keeping `p` copies of the last knot and adding `p` collinear control points, which leaves the old curve unchanged; closed objects, a whole ellipse included, are refused as in AutoCAD); the last delta is a drawing setting, see "Modify settings"), Edit Polyline (`pedit_cmd.rs`, with `pedit_join.rs`, `pedit_vertex.rs` and `pedit_curve.rs`; the edits are `opendraft_core::pedit`: Fit makes a biarc through the vertices (`pedit/curve.rs`), Spline the cubic B-spline of the vertices as short segments, and a spline picked, or the splines of a Multiple selection, are converted to a polyline at a precision, as arcs (`pedit/arcs.rs`, a greedy arc fit within the tolerance) when `PLINECONVERTMODE` is 1 and straight pieces when 0; vertex Tangent sets the direction Fit runs along at a vertex. What a polyline cannot hold itself, the tangents set on its vertices and the frame a Fit or Spline was made from (so Decurve brings the original vertices back and a second curve starts from them), lives in a `PolylineCurve` record beside the object (`opendraft_core::polyline_curve`, `Document::polyline_curve`, the undoable `SetPolylineCurve`, saved in `.odraft` as `polyline_curves`, not in DXF). A record describes the polyline exactly as it was left (`shape`) and applies only while it still is: any other edit makes it stop applying and it is then ignored and not saved; moving a vertex or changing a segment width in Edit vertex carries it on, and inserting, breaking or straightening drops the tangents), Match Properties (`match_props.rs`; the Settings option switches which properties are copied, in `Matching`, kept for the session; the destination prompt takes a click, a window (drawn left to right) or crossing window from a click in empty space, or a dragged path), Break and Break at Point (`break_cmd.rs`; BREAKATPOINT, alias BP, asks for the object, then the one point where it is divided in two, without AutoCAD's `@`), Stretch (`stretch.rs`) and the grip editor (`grips.rs`, whose polyline vertex edits are `Entity::with_vertex_added` and its relatives in `opendraft_core::vertex_edit`, offered as options of a single polyline grip, which
starts a "Stretch" command when a grip is pressed). The old model, where a canvas `Tool`
was armed and each command was spread over a prompt table, a typed-input
handler and the canvas, is gone. The canvas now only does three things for a
command: show its ghost and rubber band, snap and report placed points, and
select by clicking or dragging a box when no command is waiting for a point.
**A new interactive command is one function in one place.**

**Names.**

| Name | Meaning |
|---|---|
| `Document` (`opendraft-core`) | The drawing data: objects, layers. Pure, no UI. |
| `Session` | A `Document` (shared, see "Background pictures") plus its undo history. Headless and testable. |
| `Doc` (`opendraft-app`) | An open window: a `Session` plus view and selection. |
| `Editor` | What a running command is handed to talk to the user and to edit. |
| `Runner` | The UI side of a running command: its thread, its pending prompt. |
| `Command` | A named function that takes an `Editor`. |

**A command is straight-line code that asks and waits**, returning
`Result<(), Cancelled>` (Esc cancels any prompt). This is MOVE, nearly as built:

```rust
pub fn move_objects(ed: &mut Editor) -> Result<(), Cancelled> {
    let ids = ed.pickset_or_select("Select objects")?;
    let base = ed.get_point("Specify base point")?;
    let to = ed.get_point(PointOptions::new("Specify second point").base(base))?;
    let (dx, dy) = (to.x - base.x, to.y - base.y);
    ed.transaction("Move", move |tx| {
        for id in ids {
            tx.modify(id, |e| e.translated(dx, dy));
        }
        Ok(())
    })
}
```

It is registered in `commands.rs` with `s.start_command("Move", modify::move_objects)`.
The selection when the command starts is its `pickset`; `pickset_or_select`
uses it or, if nothing is selected, asks the user to select objects.

**The prompt service.** `get_point`, `get_distance`, `get_angle`, `get_number`,
`get_string`, `get_keyword`, `get_selection` return the value, or `Err(Cancelled)`.
When a prompt has keywords (`Options::keyword("Undo", "U")`) or a bare Enter
means something, use `ask_point`, `ask_distance`, `ask_angle`, `ask_number` or
`ask_string`, which return an `Answer`: `Value`, `Keyword(label)` or `Enter`.
The corner of a box (rectangle, text box) uses `ask_corner(base, options)` or `get_corner`: AutoCAD's `getcorner`, with no rubber band, X and Y readouts and an outline.
An option menu that ends on Enter uses `ask_keyword` (`Some(label)` or `None`):
typed letters match its keywords, which `ask_string` would take as text.
Leave the keyword list out of the message; the prompt line adds it.
Options (`PointOptions`, ...) hold the message, keywords, a default (Enter
takes it), a base point (rubber band, relative input, distances and angles
measure from it), a `ghost` callback that returns the entities to preview at
each pointer position and a `marker` callback for marks that keep one size on
the screen (it is given how many drawing units a screen point spans). An object prompt (`ask_object`) picks only objects
that can be edited unless `Options::pick_locked` lets it reach locked layers
too (LAYULK). Angles are radians; the user types degrees. The canvas
and the command line answer the same prompt, so the status-bar text, the
clickable options and the typed forms (`x,y`, `@dx,dy`, `d<a`, a bare distance
along the cursor direction) live in one place (`opendraft-app/src/interact.rs`).

**A running command owns the drawing.** While a command waits for the user,
`Registry::busy_when(AppState::command_running)` disables every command
except those marked `.transparent()` (cancel, zoom and the view toggles,
panels, settings, exit, and starting another interactive command, which
replaces the running one). Undo, redo, erase, save, open, new, close and the
layer commands wait. Edits made outside the registry (the Layers and
Properties panels) go through `AppState::perform`, `set_property`, `undo` and
`redo`, which end the running command first, so a command never works on a
drawing that changed under it. A new command is blocked by default; it only
runs mid-command if it says so.

**Threads.** A command runs on its own thread and blocks on a channel for each
answer. Anything touching the drawing (`ed.read`, `ed.transaction`) is sent to
the UI thread and run there between frames, so the drawing is never shared and
a transaction is atomic as far as the UI goes. `Runner::poll` does that work
each frame; Esc drops the reply channel, which makes the command's wait fail
with `Cancelled`. The app then pumps it a moment longer (`Runner::cancel_and_settle`, from `cancel_settle.rs`,
up to 100 ms per request) so it can do what it does when cancelled: PLINE's
polyline drawn so far is kept on Esc and when another command takes over; a
command still busy after that ends on its own. The work a command hands to the UI thread
(`ed.read`, `ed.transaction`) runs under `catch_unwind`, so a panic in it
ends that command as `Crashed` instead of the application. (A panic inside a
transaction can leave its edits half applied; the debug validation reports
that. Plugins stay out of process, so this only concerns built-in commands.) This is exactly how a Python plugin will call it, and tests
drive a command with `run_scripted` (a list of answers in, a `Transcript` out).

**Transactions.** `Session::transaction` and `ed.transaction` record edits as
they are made. Commit merges them into one undo step. An error or cancel
inside it reverts them, so a cancelled command leaves no trace. There are no
read/write open modes and nothing to dispose: `tx.add(entity)` appends,
`tx.modify(id, |e| ...)` changes, `tx.remove(ids)` deletes, `tx.document()`
reads. Code never keeps an object reference across transactions, only ids.

**Registration.** A command has a stable id, a typed name (`MOVE`), a label,
optional shortcut, `enabled` and `checked` predicates. The one flag built is
`transparent` (may run inside another command, for example zoom). Still to
build: finer flags (document-mutating, file operation) if `transparent` proves
too coarse, and a user-editable alias table in place of `cmdline::ALIASES`.
Shortcuts are matched by `opendraft_ui::shortcuts::consume_shortcut`, where
`Plus` also answers to `Equals` (Ctrl+= as Ctrl+Plus, as browsers do); no
command uses a Plus shortcut now. egui's own Ctrl+Plus/Minus/0 interface zoom
is turned off (`zoom_with_keyboard`); the interface scale is set in Options.

**Change reporting.** Every `Action` reports a `Changes` value: the ids it
added, removed and changed, and whether it touched layers. `Session::perform`
returns it, and undo and redo return it inverted in a `Step`. The app can use
it to refresh panels, and plugins can later subscribe to document events.

**Owner of objects.** Objects of model space and of each layout share the
document's list (`Object::layout`); objects of a block definition live in its
`BlockDef` (see "Blocks").

**Zoom** (`zoom_cmd.rs`). `ZOOM` (`Z`) asks "Specify first corner of window or
[Extents/Objects/Previous/Window]" and shows the window as large as the canvas
allows (`Camera::show_window`); the command leaves its answer in `Doc::zoom_to`,
which the UI thread empties into the view, and each zoom is a step for `ZP`. In a
layout the window frames the sheet, inside an unlocked viewport its view.
`ZO` (`view.zoom_objects`) and the Objects option zoom to the box round the
selected objects (asking "Select objects" with none); construction lines and rays
have no box and are left out, as `ZE` leaves them out. `ZO` was Zoom Out's alias.
There are no Zoom In and Zoom Out step commands (AutoCAD has none; they and `ZI`
were removed 26-11-2026): the mouse wheel and ZOOM's options zoom.

**Erase** (`erase.rs`). `ERASE` (`E`, `DEL`, the ribbon button) is an Editor
command like MOVE: it erases the selection at once, or asks "Select objects"
until Enter with none (one undo step). In a layout
a picked viewport is erased instead. The Delete key fires only with something
selected (`erase::may_fire`), as in AutoCAD, so it never opens a prompt.

**Not taken from the SDK:** a global application object (the context is passed
in), mutable entity objects that are built and then appended, `Dispose`/`using`,
and 3D types.

**Migration order:** (1) rename `Editor` to `Session` and add change reporting
(done); (2) transactions (done); (3) the `Editor`, prompt service and runner
(done); (4) port every command and remove the `Tool` enum and `prompt_for`
(done).

## Home tab (built)
The house at the left of the document tabs shows the Home page (`app/home_page.rs`: new, open, drawings open now, recent files with date and size) in place of the dock. `AppState::home` says it is showing. The page is built from named sections (`header_section`, `open_drawings_section`, `recent_section`, `recovery_section`, `start_section` (the From template dropdown is `opendraft_ui::menu::popup`, never a window), `whats_new_section`), each under a fixed `push_id`, with rows keyed by what they stand for, never by list position. The placeholder is filtered out of everything outside the UI (automation lists, ids and events). The recent list (`recent.rs`) is a list of records with stable `RecentId`s, ten at most with five pinned; only `add`, `add_replacing` (Locate), `remove` and `clear_unpinned` change what is remembered, so a failed open never forgets a drawing. `home_scan.rs` reads the files behind it on a worker thread; the page never does disk access itself. Items of a list that can reorder are keyed by record id with explicit widget ids (never egui auto ids, which shift with position), so keyboard focus follows the file. Previews: `opendraft-canvas::preview` renders a document to a 512 x 320 RGBA picture with no egui (it asks `opendraft_core::plot_model` for the paths, so it follows the plot rules); `opendraft-app/src/previews.rs` owns the worker thread, PNG sidecars (`previews/` beside the settings, keyed by real path, date, length and `RENDERER_VERSION`) and their trimming; `preview_textures.rs` the textures the page shows. Pictures are made only after a drawing has opened or saved, from the copy already in memory. Recovery is offered on Home, per crashed session (`AppState::pending_recovery`, `recover_session`, `discard_session`, `defer_recovery`): a recovered drawing has no `path`, only `recovery_origin` (where Save As starts), so Save can never overwrite the original. The page lays out by `home_page/layout.rs`: one column below 900 px of window width, two (main and side) from there; test any change at 320 to 3840 px and 1x to 2x (`dynamic_tests/home_layout.rs`). Colour contrast of text and the focus ring is enforced by `opendraft-ui/src/theme_contrast_tests.rs`. The What's new card is a compile-time table (`opendraft-app/src/whats_new.rs`, one `Note` per exact version; see "Releasing" in `CONTRIBUTING.md`); dismissal is stored by exact version and nothing is fetched. Templates are `.odraftt` files (`opendraft-files/src/template.rs`: the same contents as `.odraft`) in a `templates/` folder beside the settings, plus starters built into `opendraft-app/src/templates.rs`; `AppState::new_from_template` only reads one and makes a new unsaved drawing. No drawing open is allowed: `docs` then holds one hidden `Doc` with `placeholder` set (no tab, never saved, not counted by `has_drawings()`), so the many `docs[active]` sites cannot panic; `push_document` drops it. While `home` is set the registry (`Registry::needs_drawing_when`) enables only commands marked `.global()` (file, exit, settings, panel toggles). A new command is drawing-only unless it says `.global()`. The app starts on Home when it was given no files. Selecting tabs goes through `show_home` and `show_document`, never by writing `active`.

## Ribbon (built)
`opendraft-ui::ribbon` draws a ribbon declared as data and knows nothing about the document: a `Panel` holds `Column`s (`Large`, `LargeSplit`, `Stack`, `Rows`), a `Rows` column holds up to three rows of `Cell`s (labelled or icon-only buttons, split buttons, and `Slot`s), and every item names a command id. A `Split` runs the item last picked from its list (`RibbonState::split_picks`, by the command of its first item); `Split::labelled` keeps a fixed label, as AutoCAD's Paste. A `Slot` is room for a control the app draws: `Ribbon::show` returns a `RibbonOutput` with the click and each slot's rect, and `opendraft-app/src/ribbon_slots.rs` draws the layer list and the colour, lineweight and linetype lists there and returns a `SlotEdit` (they change the selection; with nothing selected the layer list sets the current layer and the others set the colour, linetype and lineweight of new objects, `Document::new_object_attributes`). In a layout with a viewport to work on (`AppState::target_viewport_ref`), the layer list has the Layers panel's VP Freeze switch between the sun and the padlock; that switch is the sun or snowflake framed by the four corners of a square, one pixel wide (`paint_vp_switch`), in both places, so it reads apart from the Freeze switch. The layouts are in `opendraft-app/src/ribbon_def.rs` (the Home tab in `ribbon_def/home.rs`, panel for panel as AutoCAD 2020's). An item whose command is not registered shows dimmed; Home's are listed in its `NOT_BUILT` test, which fails when a listed command gets registered or an id is misspelt, so take an id off the list when its command lands.

**Contextual tabs.** The usual tabs (Home, Insert, Annotate, View, Manage) are always there; while the drawing on screen is in the Block Editor or a layout, a contextual tab follows them. `RibbonContext::of(&AppState)` says which (none on the Home page, the Block Editor before a layout), `ribbon_for(context)` builds the ribbon, and `app/chrome.rs` rebuilds it when the context changes, reading the one shown back from its last tab (`RibbonContext::shown`). `tab_after_change` decides the tab shown afterwards: **the Block Editor's tab takes the focus**, because its Save and Close are how one leaves it; **the Layout tab never does** (AutoCAD's does by default, "Full with focus"; OpenDraft behaves as its "Full without focus"), because it holds set-up tools used now and then while the work in a layout is done on the usual tabs, and taking the user off the tab they chose needs a clear reason. Otherwise the tab showing stays, and when it goes away with its context the ribbon falls back to Home. A tab marked `Tab::contextual` is drawn with the accent (`opendraft-ui/src/ribbon/tabs.rs`): its label in `accent_text` and a 2-point line of it along its top, so it is seen when it appears. This is a deliberate exception to the rule that the chrome keeps to neutral tones and the accent is for selection and focus: a tab that has just appeared is a "look at me" moment. Do not take it as licence to colour other chrome. The Layout tab (`ribbon_def/layout.rs`) follows AutoCAD 2020's as far as the commands exist: Layout (New, Page Setup, and Plot, which AutoCAD keeps on an Output tab this ribbon does not have) and Layout Viewports (Rectangular, Lock, Viewport Scale, Viewport Layers), and OpenDraft's own Display panel with the Light Paper toggle (see "Layouts"); Lock shows pressed while the viewport it acts on is locked (`AppState::target_viewport_locked`).

## Icons (built)
An icon is a constant in `opendraft-ui/src/icons.rs` (declared with `icons!`, which also lists them all in `icons::ALL`), named after the command it is for (`DRAW_LINE`: the command id `draw.line`) or the part of the window (`LAYER_PANEL_FROZEN`, `RIBBON_SPLIT_ARROW`), so each has its own drawing, `assets/icons/<name>.svg` (`draw-line.svg`). A constant's value only identifies the icon (a private use character, not a font character); `icons::glyph` gives the Lucide font glyph that is drawn when there is no file, and two icons may share a glyph. A ribbon item or menu row for a command uses that command's icon, `command.id` upper-cased with `_`; if a menu wants a different picture for the same command it gets a `CONTEXT_` name. **Draw icons through `opendraft_ui::icon_set`**: `paint` for the painter, the `Icon` widget for buttons, toggles and labels, `image` for egui widgets that take an image; never `FontId::new(.., icon_family())` directly. They draw the SVG when there is one, else the glyph. Every drawing is also built into the program (`opendraft-ui/build.rs` lists `assets/icons/*.svg` into `EMBEDDED`; the glyph is only for an icon with no file at all), so an install needs no icon folder. A folder replaces drawings by name, and is read once at start-up (`opendraft-app/src/icon_library.rs`: `OPENDRAFT_ICONS`, else `icons/` beside the program, else, in a debug build only, the source tree's `assets/icons`), so an edited drawing shows on the next launch with no rebuild; a file that cannot be read is named in the command line and the built-in drawing is kept. A release build carries no source path. A drawing is rasterised with `resvg` the first time it is drawn at a pixel size. A *plain* drawing (one grey or white, as Lucide's; `currentColor` is white) is kept as a white mask and tinted with the colour asked for, so it follows the theme and dims when disabled; a *coloured* one (any clearly coloured part, or greys clearly lighter and darker than each other, such as white marks on a dark grey body, which a mask would fill in) is drawn in its own colours and only fades when disabled. Which it is is worked out from the file when it is read. `scripts/export_icons.py` writes the library (Lucide's original SVGs; files that exist are kept unless `--force`) and its index, `assets/icons/README.md`.

## Dynamic Input (built)

Dynamic Input is another input surface over the Editor prompt service. Commands
still run on the Runner and all accepted answers pass through `interact.rs`;
there is no second command engine. `coordinates.rs` supplies the shared finite
Cartesian/polar parser: command-line coordinates remain absolute by default,
while cursor input is relative at prompts with a base. `#` forces absolute and
`@` forces relative in both surfaces.

- Each `Doc` owns `DynamicInputState` (`dynamic_input.rs`): semantic field IDs,
  draft, scalar/coordinate locks, menu selection, placement, cursor and errors.
  A reply, cancellation, drawing switch, disabled DYN or another text editor
  clears transient state. Cursor motion preserves it.
- `Options::dimensions(DynamicDimensions::{Polar, Cartesian})` declares point
  dimension fields without adding UI dependencies to `opendraft-commands`. Line,
  Move, Copy, Mirror and grip point edits opt into polar dimensions; Rectangle
  opts into Cartesian. Scalar prompts already declare Distance/Angle/Number.
- `app/dynamic_input.rs` arbitrates keyboard ownership and submits answers.
  The raw-input hook captures navigation before egui applies spatial focus
  movement, so Tab follows semantic fields and Down opens options. The docked
  command line and other text fields keep their normal keyboard ownership.
  With no command running the same hook takes Up and Down for the command
  history (`app/history_keys.rs`), which egui would turn into focus movement.
- `app/dynamic_overlay.rs` draws compact rectangular foreground tooltips with
  stable TextEdit IDs. At a prompt with a base point the fields sit on ghost
  dimensions, as in AutoCAD (`dynamic_input/dimensions.rs`, pure screen-space
  geometry): a vector gets a linear dimension standing 30 px off the line and an
  angular arc from the zero direction (honouring ANGBASE/ANGDIR); a rectangle
  gets two orthogonal dimensions outside its edges; a lone distance gets the
  linear one. Too short to draw (under 24 px), absolute coordinates, or no base:
  the fields sit in a row with the prompt beside the cursor. The prompt stays
  near the cursor and flips and clamps with a 24-point dead band
  (`dynamic_input/placement.rs`). Boxes are nudged by `avoid` so none overlaps
  another, the prompt, or the 56-point square kept clear around the crosshair.
  Hovering an input freezes its anchor so it can be clicked. Numeric fields do
  not open secondary hover tooltips over the drawing.
- `View` receives a cursor constraint and overlay hit rectangles. Its snapped
  or trailing cursor drives values; constraints drive ghosts, rubber bands
  and placed points. Only accepted answers update the last-point origin.
- `DynamicInputSettings` is persisted with Settings. F12 taps toggle and holds
  temporarily suppress input (350 ms distinguishes a hold); the DYN status
  button is the same transparent registry command. Its context menu opens the
  Dynamic Input group in Settings > Drafting. Variables: `DYNMODE`,
  `DYNPROMPT`, `DYNPICOORDS`, `DYNPIFORMAT`, `DYNPIVIS`.

Still to build: entity-specific grip dimensions and `DYNDIVIS`/`DYNDIGRIP`,
recent-input recall and tracking aids. The fields show and read lengths and
angles in the drawing's units (see "Units"). Headless egui tests exercise focus, input/navigation in a single frame,
locking, menu keyboard/mouse actions, rejected clicks, F12 and viewport edges
at 100%, 125% and 150% scale.

## Ortho (built)

`opendraft_core::ortho` holds the maths (`axis_of`, `on_axis`, `constrain`). `opendraft-canvas` applies it where the pointer is resolved: `View::aim` builds an `Aim` (document, snap modes, grid step, aperture, `Ortho`, and the prompt's base when ortho is in force) and `Aim::resolve` returns the final point and the snap behind it, so the preview, the placed point and the readout cannot disagree. `Ortho { enabled, strict }` is a per-user setting passed in with `View::set_ortho`. **Decision (26-11-2026):** ortho, like the grid, snap and object snap modes and tracking, is a user setting and not drawing state, unlike AutoCAD, which saves `ORTHOMODE` and its like in the drawing's header. It describes how a person draws, not the drawing, and opening a file should not switch it on for whoever opens it; so DXF and DWG import and export neither read nor write `$ORTHOMODE`, and it is not on the parking lot. The snap is found first, as without ortho. Standard lets an object snap win (the grid snap and a bare cursor are held to the axis); strict projects the snapped point onto the axis chosen by the cursor (`hold` in `snap_axis.rs`), keeps the marker where the snap was found and draws a faint guide line from it to the held point. `ORTHOMODE` and the F8 command change `Settings::ortho.enabled`, and `ORTHOLOCK` (0 standard, 1 strict; our own name, AutoCAD has no equivalent) changes `Settings::ortho.strict`. Neither is saved in the drawing.

## Object snap (built: running snaps, Tab cycling, overrides and tracking)

Follows `private_material/autocad_snapping_behaviour.md`. One pass gathers every snap point under the pointer and ranks them; the view shows the first, or the one the user cycled to.

- **Pure core in `opendraft-canvas/src/snap/`.** `snap_all(objects, &Probe)` returns the ranked list; `snap` is its first element. `fixed.rs` holds what an entity offers by itself (endpoint, midpoint, centre, node, quadrant, insertion), `context.rs` what needs two objects (intersection) or the command's last point (perpendicular, tangent), `cycle.rs` the Tab choice. The maths for feet and tangent points is `opendraft-core/src/curve_snap.rs` (`Curve::perpendicular_feet`, `tangent_points`, `bounds`), over lines, circles, arcs and ellipses; intersections reuse `Curve::intersections`.
- **Ranking is our policy, not AutoCAD's (the spec says it publishes none).** Classes, best first: a point inside the aperture (every object snap, Perpendicular and Tangent included: the pointer has to be near the foot or tangent point itself, not merely over the curve); Nearest; the grid. Inside a class the closer to the pointer wins, then the more specific mode (`SnapKind::priority`), then source ids and position, so the order is deterministic. A point several modes find is listed once, as the most specific.
- **Identity and cycling.** `SnapPoint` carries its source objects; `SnapPoint::id()` (kind, sources, position to a micro-unit) lets the choice survive the pointer drifting. `View` keeps the chosen `SnapId`: Tab moves to the next (Shift+Tab back, our extension), wrapping; a choice no longer listed is dropped. The pointer used for the search is always the physical one; the magnet only moves the drawn crosshair (`SnapModes::magnet`), so a snap never feeds itself.
- **Tab versus Dynamic Input.** Tab is the canvas's when more than one snap point is under the pointer and no dynamic field is being typed in (`View::snap_cycles`, checked in `route_dynamic_input`); otherwise it moves between dynamic fields as before.
- **Settings.** `SnapModes` (a bool per mode, plus `marker`, `tooltip`, `magnet`, `aperture_box`) is saved with the user's settings; `OSMODE`, `AUTOSNAP` and `APBOX` change it. The status bar has an INT button and the SNAP button's right-click menu lists every mode; Settings > Drafting has only the AutoSnap display options (marker, tooltip, magnet, aperture box), not the modes or the Snap on switch. Each mode has a `view.snap_*` command.
- **Power Select** (`power_select.rs`, `app/power_select_dialog.rs`; AutoCAD's QSELECT under our own name). `POWERSELECT` (aliases `PSE`, `QSELECT`, `QSE`), the Selection panel's extra row and the context menu open a dialog laid out like QSELECT's: Apply to (Entire drawing, or Current selection, with a pick button that clears the selection, runs a selection prompt and comes back), Object type (Multiple or a kind present in scope), Properties (Color, Layer, Linetype, Linetype scale, Lineweight, then the kind's Properties-panel rows through `properties::rows` and `properties::value`), Operator, Value, Include or Exclude, and Append. Everything is pure and tested in `power_select.rs`: `kinds_in`, `props_for`, `values_present` (the Value list is what the drawing has), `value_is_usable` and `run`, which returns the ids. Numbers compare in the drawing's units with a 1e-6 relative tolerance (`Equals`, `Not Equal`, `Greater`, `Less`); text compares ignoring case, and layers and linetypes also take `*` and `?` (Wildcard Match). Exclude selects everything in scope that is not a hit. Only selectable objects of the space being edited are searched. Flags, fills, styles and arrowheads are picked from the values present rather than typed. Not built: Color as an ACI number or name, Lineweight as a number, properties of block attributes, and a `QSELECT` that takes its answers on the command line.
- **Clipboard** (`clipboard.rs`, `opendraft-core/src/document/transplant.rs`, `opendraft-commands/src/paste_action.rs`). `COPYCLIP` (Ctrl+C), `CUTCLIP` (Ctrl+X), `COPYBASE` (Ctrl+Shift+C), `PASTECLIP` (Ctrl+V), `PASTEBLOCK` (Ctrl+Shift+V) and `PASTEORIG`. egui turns Ctrl+C/X/V into `Event::Copy`/`Cut`/`Paste` rather than key presses, so `clipboard::shortcut` reads those events. What is copied is a small drawing: `Document::extract(ids)` clones the objects and every table (layers, text, dimension and multileader styles, linetypes, blocks). `Document::absorb(source, Placement, layout)` brings it into any drawing: layers, text, multileader and dimension styles and blocks are matched by name (ignoring case; the target's definition wins) and the missing ones are copied with their ids remapped, including the text style inside MText, dimensions and multileaders and the contents of nested blocks; linetypes the objects or new layers use are copied by name. `Placement::Loose` moves the objects; `Placement::Block` makes one `A$Cn` block (base point = the clipboard's) and one reference to it. `absorb` returns an `Absorbed` (tables before and after, the objects), so `PasteDrawing` (the action) undoes and redoes it exactly in one step. The clipboard lives in `AppState::clipboard`, a `ClipboardSlot` (an `Arc<Mutex<..>>`) so COPYBASE, which runs on a command thread, can fill it. Copying also writes the drawing to the system clipboard as text (`opendraft-clipboard <base x> <base y>` then the `.odraft` JSON, via `NativeFormat`; `arboard`). A paste first looks at the system clipboard: text that is not what this app last wrote and parses as ours (another window) is used; anything else leaves the last internal copy in place. Not built: pasting plain text as MText, pasting pictures, copying other drawings' layouts or viewports, and keeping a changed definition when a name already exists (the target's wins silently). Outside callers cannot use these commands (`automation/policy.rs`).
- **Selection styles.** With no point asked for (no command, or "Select objects"), what a click on nothing and a drag do is `Settings::selection_style` (`opendraft_canvas::SelectionStyle`, Settings > Display > Selection), handed to the view each frame by `View::set_selection_style`; `opendraft-canvas/src/view/select_gesture.rs` is the logic and `select_paint.rs` draws it. *Click clears* (the default; issue #165): a drag makes a box (Window to the right, Crossing to the left) and a click is reported as `CanvasOutput::click`; `AppState::click_select` clears the selection for a plain click on nothing only while no command runs, so a near miss at "Select objects" never loses what is being chosen. *Window and lasso*: a click on nothing starts an implied window that the next click closes (`Pending::Window`, a corner in drawing units), and a drag draws a lasso (`Pending::Lasso`): Window if it sets off to the right, Crossing to the left, and Space cycles Window, Crossing and Fence while it is drawn; it ends as an ordinary `RegionSelect`. Esc drops either: the app hands the view its keys first (`View::take_selection_keys`, from `app/ctrl_watch.rs`) so they reach neither the command line nor the shortcuts. A point prompt drops whatever is under way, and a click that takes a layout viewport's border neither clears nor starts a window.
- **Context menu.** A right click on the drawing with no command running opens `app/context_menu.rs` (`AppState::context_menu`, set from `CanvasOutput::context_menu`; a running command still takes the right click as Enter, at every prompt including "Select objects", and Shift/Ctrl+right-click at a point prompt is the snap menu). Rows are data (`Row`, `Kind`, `Action`): Repeat the last command, Recent Input (`CommandLine::recent`, newest first, set by `note_recent` with the commands that make something), Clipboard, Isolate, the Modify rows, Draw Order, Group, Select Similar (`AppState::select_similar`: same kind and layer), Deselect All, Power Select, QuickCalc, Find, Properties. The editing rows only show with a selection; without one the menu offers Undo, Redo, Select All and Zoom Extents. Rows with nothing behind them yet (Isolate, Draw Order, Group, QuickCalc, Find) are greyed (`Kind::Soon`); filling one in is a change of `Kind` to `Item`.
- **Geometry that is not in the drawing yet.** A point prompt can carry `Options::snap_to(entities)` (`Prompt::snap_geometry`, `PointPrompt::snap_geometry`); `View::aim` wraps them as stand-in objects (`Aim::extra`, ids counting down from `u64::MAX`) that `Aim::found` adds to the objects near the pointer, so endpoints, midpoints, intersections, perpendicular and the rest see them. PLINE passes the segments drawn so far (`Chain::drawn`), SPLINE the fit or CV curve through the points so far, LEADER and MLEADER the path through theirs (`draw::path_through`). LINE adds each segment as it goes and ELLIPSE's first axis is not passed. Every prompt of PLINE's options passes the segments too (Arc's, through `polyline_arc::arc_option` and ARC's `centre_after` and `to_end_from_centre`, which ARC calls with none; Width, Halfwidth and Length). What a pause keeps is looked up in the stand-ins as well as the drawing (`snap::Drawing` in `view/acquire.rs`, and `view/snap_choice.rs` hands them to `snap::targets`), so the points and segments of a polyline in progress are kept and tracked from as an object's are, as in AutoCAD.
- **One-shot overrides.** Typed at a point prompt (`END`, `MID`, `CEN`, `NOD`, `QUA`, `INT`, `INS`, `PER`, `TAN`, `NEA`: three letters or more of the name, several with commas, `NON` for none), or picked from the menu Shift+right-click (or Ctrl+right-click) opens at the pointer (`app/snap_menu.rs`). They replace the running snaps for the next point only, even with SNAP off (`SnapOverride::applied`), and are spent by any answer. A click that finds no snap places nothing and does not fall back to the grid (`Aim::place`; the spec's better-supported reading); it says "No Endpoint snap found" and lets go of the override so the prompt is never stuck behind it (`CanvasOutput::refused`). A word the prompt itself offers as an option is the option's. `snap_once.rs` is the pure state (`OneShot`); `once_input.rs` hooks it into `reply`, `answer_typed` and `answer_dynamic`. `FRO` (base point, then an offset typed relative to it or clicked) and `M2P` (middle of two points) are chains in the same state: each point is consumed until the chain gives one, and the rubber band starts at the base meanwhile. The status line shows `[Endpoint]` or the chain's question.
- **Deferred Perpendicular and Tangent** (spec 7.11, 7.12). With no last point (the first point of a Line, say) the foot or tangent point cannot be worked out, so the engine offers a *deferred* snap at the nearest point of the object under the pointer (`SnapPoint::deferred`, tooltip "Deferred Perpendicular"; Tangent only on curves). The click is held, not given to the command (`AppState::defer_one_shot`, only at a point prompt with no base): `OneShot` keeps the object and where it was picked (`Deferred`). From then on the rubber band starts at the point the object would give for the pointer as the next point (`Deferred::point`, the foot, or the tangent point nearest the pick), so the line stays square to, or tangent to, the object. The next point settles it: the command is given the settled point first and the clicked point after (`reply`, `send`). If there is no solution from that point (a foot past a segment's end, a tangent from inside a circle) it says so and waits for another; Enter drops it. A point prompt that knows the direction of the line it places but has no base (XLINE's Ang, Hor and Ver: `PointOptions::along`, carried by `Prompt::along`, `PointPrompt::along` and `Probe::along`) needs no deferral: Tangent and Perpendicular are found at once where a line along that direction touches the object or is square to it (`Curve::tangent_along`, `Curve::perpendicular_along`, and the same on `Spline`), on circles, arcs, ellipses and splines. AutoCAD does not do this: it defers and the snap does nothing.
- **Extension and Parallel follow what the pointer paused over** (`snap/track.rs`, pure; `view/acquire.rs`, the state). Resting on a line, arc, elliptical-arc or open-polyline end for 0.3 s keeps it (a "+" appears); resting on a straight segment, when no end is in reach and there is a last point and ortho is not holding the point, keeps its direction. Resting again on something kept lets it go. What is kept lasts until a point is placed or the prompt ends, and survives the pointer crossing a prompt box. Each kept item is resolved against the drawing every frame (`resolve`), so a changed or erased object drops out. Extension follows a straight end (a line, or a polyline's first or last segment) along the whole line through it, on past the end and back over the object, so a point or a typed distance can be taken back from the end, as in AutoCAD; an arc or elliptical arc follows its own circle or ellipse (never the tangent), on past the end over the part the curve does not cover, as in AutoCAD, and back over the curve itself too (AutoCAD does not go back; we do, as on a line), the dotted path taking the short way; and never within the aperture of the end (the end's own snap is there). Parallel is the line through the last point in the kept direction, both ways; its "+" sits where the pointer paused and its path is drawn as the whole line through the last point across the view. An Extension path is drawn dotted from the end to the snap point. Sources: lines, straight polyline segments and rectangle edges. `acquire.rs` is the one place that decides what a pause keeps, so object snap tracking can reuse it.
- **Object snap tracking and polar tracking** (spec Part II; `snap/otrack.rs` is the pure geometry, `view/acquire.rs` and `view/snap_choice.rs` the state). A snap point the pointer rests on for 0.3 s (endpoint, midpoint, centre, node, quadrant, intersection, insertion) is kept with a "+" (`Acquired::Origin`), and resting on it again lets it go; Shift stops a pause from keeping (or, with `POLARMODE` bit 8, is needed for it). Running snaps off suspends the kept points. Each kept point gives paths (infinite lines) along the horizontal and vertical, or along every polar angle with `POLARMODE` bit 2; polar tracking (F10) gives the paths from the command's last point. A path gives a snap point where the pointer is within `REACH` (0.75) of the aperture of it and outside the aperture of where it starts; two paths from different points give their crossing while the pointer is within reach of both and the crossing is on screen. A path also gives its crossing with an object under the pointer, as in AutoCAD, while the Intersection (or Apparent Intersection) snap is on (`snap/path_meets.rs`); it ranks with path crossings and its tooltip names it before the path (`Intersection | Polar: 40.0000 < 90°`). Paths that are straight lines through a point are exact on the axes (`directions`). Ranking, best first: direct snap points; path crossings; path points (Tracking, Extension, Parallel); Nearest; polar points; the grid (spec section 22: an explicit override, a direct snap, tracking, Nearest, then the constrained free point). The tooltip names where the path starts and the distance and angle from it (`Endpoint: 100.0000 < 0°`), and flips to the other side of the marker at the canvas edge. Extension and Parallel points carry their straight path too, so their tooltips read `Extension: 60.0000 < 0°`. **A typed distance follows a path:** with the pointer on exactly one straight path (a tracking, polar, Extension or Parallel point), a distance typed in the command line (`track_distance`) or in the dynamic input's distance field (`commit_dynamic_input`) goes that far from where the path starts, in the pointer's direction along it, not from the last point. **`TT`** (typed, or in the Shift+right-click menu) takes the next point as a temporary tracking point instead of the answer: it shows a "+" and tracks like a kept point until the point it helps with is given (`OneShot::temps`; it cannot be taken back by pausing on it, only by Esc). **`TK`** collects tracking points, each held to an axis from the one before (ortho is forced strict while it runs), and Enter answers with the last. `TRACKPATH` chooses full-screen or to-the-cursor drawing for polar and for object snap paths (`Tracking::full_path`, `shows`). Settings: `Settings::tracking` (`Tracking`), `AUTOSNAP` bits 8, 16 and 32, `POLARANG`, `POLARADDANG`, `POLARMODE` (bit 1, measuring from the last segment, is refused), `TRACKPATH`; F10 and F11 and the POLAR and OTRACK status buttons. Ortho and polar tracking exclude each other (`Settings::set_ortho`, `set_polar`). Intentional difference from AutoCAD's initial `AUTOSNAP` of 63: polar tracking starts off (ours is 55), since ortho already exists and polar snapping changes how the pointer feels.
- **Pieces, not only entities (`snap/context.rs`).** Intersection, Perpendicular and Tangent work over *pieces*: the segments, arcs, circles and ellipses of an entity and its spline, and, for a block reference or a dimension, the pieces of what it draws (`Scene`). Splines are cut into short straight pieces and each crossing is refined on the spline itself (`opendraft-core/src/spline/snap.rs`: chord zoom against a curve, Newton against another spline), so the point is on the curve; feet and tangent points are found by sign changes of the derivative test along the parameter. A polyline's or rectangle's own corners are Endpoints, but where two of its segments that are not neighbours cross is an Intersection (`Chain::adjacent`). At most 48 pieces in the aperture are crossed with each other.
- **Geometric Center, Apparent and Extended Intersection.** Geometric Center (`OSMODE` 1024, `GCEN`) is the centre of the area a closed polyline (arcs included) or closed spline encloses (`opendraft-core/src/outline.rs`); none for an outline that crosses itself or has no area; circles, ellipses and rectangles show theirs as Center. Apparent Intersection (2048, `APPINT`) is the same points as Intersection in 2D, labelled and marked as AutoCAD's. Extended Intersection (`EXTINT`; the Extended Apparent form is the same in 2D) is an override only (never an `OSMODE` bit): with it, resting on a line, arc or elliptical-arc end keeps it (as for Extension) and the points where its extension meets another object are offered, ranked with path crossings.
- **Not built:** taking back a `TT` point by pausing on it, `POLARMODE` bit 1 (angles measured from the last segment), Z tracking (2D only), tracking from the base point of a command that gives none, Extension past the ends of splines, intersections of a spline with itself, hatch and dimension-extension-line exclusions as options (`OSOPTIONS`; hatches are always excluded and dimensions have no extension-line endpoints to ignore), `OSNAPZ`. Node finds point objects and dimension definition points.

## System variables (first slice built)

Settings that a user reads and sets by name, as in AutoCAD: type `GRIDMODE`
at the command line to see it and be asked for a new value (Enter keeps it),
or run `SETVAR` and give the name; `SETVAR` then `?` (or `?GRID*`) lists
variables with their values. Names are upper case and matched ignoring case.

- **The table is generic.** `opendraft-commands::SysVarTable<C>` holds `SysVar<C>`
  entries (name, description, `Kind` with its range, read-only flag, getter,
  setter), like the command `Registry<C>`. It parses and range-checks typed
  text, then calls the setter, which may still refuse a value. It has no
  egui and no knowledge of the app.
- **The list is the app's.** `opendraft-app/src/sysvars.rs` binds the variables to
  `Settings` and the open drawing, so a variable that mirrors a setting is
  saved with the user's settings for free. Built: `GRIDMODE`, `GRIDUNIT`,
  `OSMODE`, `SNAPMODE`, `SAVETIME`, `CURSORSIZE`, `PICKBOX` (defaults to a 4 px pick-box radius; Settings > Drafting > Sizes), `APERTURE`,
  `GRIPSIZE` (pixel radii of the pick, snap and grip targets; see `PointerSizes` in `opendraft-canvas`), `FILLETRAD`, `CHAMFERA`, `CHAMFERB`,
  `OFFSETDIST`, `CHAMFERC`, `CHAMFERD`, `CHAMMODE`, `TRIMMODE` (the last eight are the
  drawing's `ModifySettings`: see "Modify settings" below), and read-only `CMDACTIVE`, `DWGNAME`.
- **Use AutoCAD's names and values** where the feature matches, so people and
  scripts carry over. `OSMODE` is a bit code (1 endpoint, 2 midpoint,
  4 centre, 8 node, 16 quadrant, 32 intersection, 64 insertion, 128 perpendicular, 256 tangent,
  512 nearest, 16384 off); a bit we have no snap for is refused rather than
  stored. `AUTOSNAP` (1 marker, 2 tooltip, 4 magnet) and `APBOX` are in `snap_vars.rs`. When a variable's meaning differs from AutoCAD's, give it its own
  name instead.
- **A new variable is one entry** in `sysvars.rs::build`. Settings that have
  a UI toggle keep their command; the variable and the command change the
  same field. Do not store state in a variable that is not also somewhere
  the app reads it.
- **Not undoable,** except the drawing-saved ones. Variables kept in the user's
  settings are not drawing edits, so they do not go through `Action`.
- **Scopes.** AutoCAD saves some variables in the drawing (`LTSCALE`,
  `LUPREC`), some with the user (`OSMODE`), some not at all. The user and
  read-only kinds are built, and so is the drawing kind, for the unit
  variables: the getter reads the active `Document` and the setter makes an
  `Action` (`AppState::set_units`), so setting one is undoable and marks the
  drawing modified. A new drawing-saved variable needs a field on `Document`,
  an optional field in the native format (no version bump if optional), a DXF
  header mapping and an `Action`; `units_vars.rs` is the example.
- **Not built:** transparent use inside a running command (`'GRIDMODE`),
  reading and setting from plugins (the table is the API, as the registry
  is), and a Settings window that lists them.

## Units (built)

The UNITS command (alias `UN`, `DDUNITS`; ribbon Manage > Drawing, and the
application menu) sets how a drawing writes and reads lengths and angles.
**The numbers in the drawing never change**: a length is a drawing unit and
an angle is radians counter-clockwise from east. Units only decide the text.

- **The settings are `opendraft_core::Units`**, held by the `Document` and changed
  only by the `SetUnits` action (one undo step, `Changes::units`). They are the
  AutoCAD variables: `LUNITS` (scientific, decimal, engineering, architectural,
  fractional), `LUPREC` (decimals, or the fraction step 1/2^n), `AUNITS`
  (decimal degrees, deg/min/sec, grads, radians, surveyor's), `AUPREC`,
  `ANGDIR`, `ANGBASE` and `INSUNITS` (21 insertion units, kept but not yet used
  to scale anything). All seven are system variables (`units_vars.rs`).
- **Writing and reading are pure** (`opendraft-core/src/units/`): `format_length`,
  `format_angle`, `format_point`, `parse_length`, `parse_angle`, with round-trip
  tests for every format. Architectural and engineering lengths take one drawing
  unit to be one inch. `parse_length` accepts feet and inches (`5'-3 1/2"`), mixed
  fractions and plain numbers in every format. `parse_angle` takes a bare number
  in the drawing's angle format, or letters that say what was meant (`45d30'15"`,
  `100g`, `1.5r`, and bearings `N 45d E`). A typed angle counts from `ANGBASE` in
  the `ANGDIR` direction (`Units::to_display_angle` / `from_display_angle`);
  surveyor's bearings are absolute.
- **Everything the user reads or types goes through them**: command-line and
  dynamic-input answers (`interact.rs`, `coordinates.rs`, `dynamic_input.rs`: a
  Distance prompt reads lengths, an Angle prompt reads angles, a Number prompt
  stays plain), prompt defaults (`Hint`, written by `units_state::hint_text`),
  the status bar readout, the Properties panel and the Rotate message. A command
  asks for a length with `get_distance`, never `get_number`. A new place that
  shows a length or angle uses `AppState::units()` and these functions, not
  `format!("{:.4}")`.
- **Saved in the drawing**: an optional `units` object in the `.odraft` file (no
  version bump; a file without it reads as decimal, an unknown code is refused)
  and the DXF header (`$LUNITS`, `$LUPREC`, `$AUNITS`, `$AUPREC`, `$ANGDIR`,
  `$ANGBASE`). `$INSUNITS` is read but not written, because the writer is R12;
  the export notes say so.
- **The dialog** (`app/units_dialog.rs`) edits a draft and OK commits it.
  Direction... opens Direction Control (East, North, West, South and an angle).
  Not built: the Pick button of Direction Control, the Lighting units (the app is
  2D), architectural display of areas (areas stay decimal), and a unit-aware
  grid spacing and Settings suffix (both still say `mm`).

## Custom coordinate system (built: the system, input, drawing aids and the CCS command)

AutoCAD's user coordinate system (UCS) under our own name: the **custom
coordinate system**, command `CCS` (alias `UCS`), View tab > Coordinates. It is
an origin and a turn about Z (`opendraft_core::ccs::Ccs`; 2D only, no tilt
about X or Y). **Objects are always stored in world coordinates**: a system
only changes how points and angles are typed and shown, and which way is
"horizontal".

- **Where it lives.** The Model tab has one (`Document::model_ccs`) and each
  layout viewport its own (`Viewport::ccs`), used while working through it;
  changing one never changes another. A layout's sheet has none (the world).
  `Document::ccs()` is the one in force: the document knows the viewport being
  worked through (`set_active_viewport`, set with the active layout by
  `Session::set_active_space` every frame). Systems saved by name
  (`named_ccs`) are shared by every space. Each change is one undo step:
  `SetCcs` (one space's system; it keeps the old one for Previous, ten per
  space, in `ccs_previous`, which undo also takes back) and `SetNamedCcs`;
  both report `Changes::ccs`. Saved in `.odraft` (`model_ccs`, `named_ccs`,
  each viewport's `ccs`; left out when world; no version bump).
- **DXF and DWG** keep a system as AutoCAD keeps a UCS: three points, an
  origin and the X and Y directions. `Ccs::from_axes` accepts only a flat,
  right-handed one; a 3D or mirrored UCS is read as World and the DXF reader
  says how many. DXF (`dxf/ccs.rs`, `dxf/read/ucs.rs`), R12 and R2000: the
  header's `$UCSNAME`, `$UCSORG`, `$UCSXDIR` and `$UCSYDIR` are the Model
  tab's system, the UCS table holds the saved ones, and each VIEWPORT's
  groups 110 to 112 its own (with 71, `UCSVP`, set when it is not World;
  R2000 only, as R12 has no layouts). Checked against a file ezdxf wrote
  (`tests/fixtures/make_ezdxf_ucs.py`), and ezdxf reads ours strictly with a
  clean audit. DWG (R2010 and later): the header's model-space `UCSORG`,
  `UCSXDIR` and `UCSYDIR` only.
- **Reading and showing values** go through `coordinates::Reading` (the units
  and the system in force; `AppState::reading()`). Typed coordinates are in the
  system, and `*` after any `@` or `#` means world (`*10,20`, `@*5<0`). `@` alone is
  the point the prompt measures from (the last point; at Break's second prompt,
  the first), so `@` there divides the object. A
  typed angle is a **direction** (counted from the system's X axis and
  `ANGBASE`) unless the prompt says it is an **amount to turn by**
  (`Options::turn`, `Prompt::turn`: ROTATE, grip rotate, included angles,
  chamfer and array angles, ellipse angles, LENGTHEN), which ignores the base
  angle and the system and measures a picked point from the system's X axis.
  Prompt defaults, the status bar readout and the dynamic input fields show
  values in the system; the dynamic input submits points as `#x,y` in the
  system so they read back the same. A new place that shows a point uses
  `Reading::show_point`, not `format_point`.
- **Drawing aids follow its axes**: ortho (`ortho::axis_of_turned`,
  `on_axis_turned`), grid snap (`Probe::grid_frame`), polar and object snap
  tracking paths and their tooltips, the grid, the axes (drawn from the
  system's origin), and the crosshair. A system other than the world shows an
  icon in the lower-left corner of the canvas or viewport. With the world
  system everything is exactly as before (the turned paths are only taken for
  a non-zero angle).
- **Commands that orient what they make** use the system: TEXT, -TEXT, MTEXT,
  INSERT and ATTDEF default to its X axis; RECTANG is square to it (a polyline
  when turned); XLINE Horizontal, Vertical and Angle; DIMLINEAR's automatic,
  Horizontal and Vertical directions; ARRAYRECT's rows and columns;
  DIMORDINATE, which measures from the system's origin along its axes. An
  ordinate dimension keeps the system it was made in (`DimKind::Ordinate`'s
  `frame`, World by default): its value and picture are worked out in it,
  moving or turning the dimension leaves it where it is, `.odraft` keeps it
  as an optional `frame`, and DXF as the definition point (group 10, the
  origin) and the horizontal direction (group 51, the negative of the
  system's turn; ezdxf writes the same sign). The automation API sends the
  points in world coordinates and not the frame. HATCH and HATCHEDIT keep
  the remembered pattern angle and origin in the system, as AutoCAD's
  `HPANG` and `HPORIGIN` (the angle is an amount from its X axis, the
  origin its coordinates), and a hatch gets them turned into world values
  (`hatch_memory::Memory::hatch`). MLEADER builds the multileader level with
  the system (`MLeader::build_turned`: left, right, the landing and the text
  along its X axis), keeping the points given exactly.
- **The command** (`ccs_cmd.rs`): two points (origin, then a point on X;
  Enter keeps the direction), Object (`ccs_align::aligned_to`: a line or
  segment from its nearer end along it, arcs and circles from the centre,
  text, inserts and construction lines from their insertion point and
  rotation, a point keeps the current turn; for polylines and rectangles the
  segment nearest the pick, where AutoCAD takes the first), View (origin at
  the bottom-left of the view, from `View::visible_area`), Rotate, Previous,
  World, Named (Restore, Save, Delete, ?). Enter alone is World. The World and
  Previous ribbon buttons act at once. Outside callers cannot run any of them
  (`automation/policy.rs`); the automation API stays in world coordinates.
- **Not built** (see `docs/parking_lot.md`, "Plan: custom coordinate system"):
  DWG's UCS table and viewports, turning the view (PLAN), `UCSICON`
  settings, a manager dialog.

## View rotation (built)

The Model tab's view, and the view of an unlocked layout viewport, can turn on
the screen (AutoCAD's view twist). It is the `twist` of the canvas `Camera`
(radians counter-clockwise, 0 = unturned); `world_to_screen`, `screen_to_world`
and `visible_world` all honour it, so painters that go through them need no
change. `visible_world` returns the box round the turned screen, so culling
stays safe (it keeps a little more than is seen). Objects are never touched:
only the camera turns.

- **Ways to turn it.** Ctrl+middle-drag about the canvas centre
  (`opendraft-canvas/src/view/twist.rs`; the angle is measured from where the
  button went down, Shift holds it to 15 degree steps, Esc puts the view back
  and goes no further, so it does not cancel a running command); `ROTATEVIEW`
  (alias `RV`: an angle, Points for a line to read level, Reset) and `PLAN`
  (Current, Named or World: turns the view so that system's X axis reads
  level, then shows the extents), both in `opendraft-app/src/view_twist_cmd.rs`.
  Like ZOOM they only ask: the answer goes to the drawing's `zoom_to` slot and
  the UI thread applies it (`View::request_twist`, `request_plan`). A layout's
  sheet never turns, and a locked viewport refuses with a message.
- **What follows the turn.** The layer cache key includes the twist (a turn
  repaints the picture); the grid, axes, crosshair, CCS icon and the dynamic
  input's arc are drawn turned; selection windows and grips stay square to the
  screen; a rectangle is drawn as its four corners when the view is turned;
  CCS View lines the system up with the turned view.
- **Saved.** A viewport's twist is `Viewport::twist` in `.odraft` and DXF
  group 51 (degrees), with the view centre in the viewport's own axes. The
  Model tab's twist is a view setting like its zoom: it is not saved.
- **The viewport controls.** The `[-][Top][2D Wireframe]` label in the drawing's
  top left corner; `VPCONTROL` (0 or 1) and Settings > Display > Navigation, under
  the gizmo's box, hide it (`Settings::show_viewport_controls`, on by default).
  Its `[-]` menu and view choices are not built.
- **The navigation gizmo.** In the top right of the drawing (the View ribbon's Gizmo

## Layouts (built, phases 1-3)

A layout is a sheet (millimetres) with viewports that show model space; the design follows AutoCAD's paper space but keeps this project's structures (no slotmap graph, handles or `nalgebra`).

- **Data** (`opendraft-core/src/layout.rs`, `plot_settings.rs`, `document/layouts.rs`): `Layout { id, name, width, height, plot, viewports }`, where `PlotSettings` is the authoritative page/device/media/plot-area/scale/orientation/style/shaded-output state, and `Viewport { id, center, width, height, view_center, scale, locked, on }`. `scale` is paper millimetres per model unit (the specification's `Hp / Hm`), so the mapping is `paper = center + scale * (model - view_center)`, a pure uniform scale and offset, tested for round trips. Layout and viewport ids are permanent like `EntityId`. `Document::validate` checks unique ids and names, sheet sizes, plot-setting invariants and counters. Layouts are replaced as one list by the `SetLayouts` action (`Changes::layouts`), so every edit is one undo step; builders (`new_layout`, `copied_layout`) are pure and number from the counters.
- **Spaces share one object list.** `Object::layout` is `None` for model space or the layout whose sheet holds it; ids are shared. The document has an active space (`active_layout`, set by the app when the view changes space; not undoable or saved), and `visible_objects`, `selectable_objects`, `bounds`, `has_objects_here` and the add actions follow it, so every command, snap, pick, grip and undo works on a sheet unchanged. `visible_in(space)`, `model_bounds` and `model_objects` ask for one space explicitly (viewports show model space; DXF writes model space). Actions that create objects remember their space the first time they run, so undo and redo put them back where they were. Deleting a layout removes its objects in the same transaction.
- **Spaces** (`opendraft-canvas/src/view/layout.rs`): `Space::{Model, Paper, Viewport}` per drawing, held by `View`. `View::camera` always maps the space being edited to the screen: the sheet in paper space, and in a viewport the sheet camera composed with the viewport's scale and offset, so picking, snapping, grips and ghosts are unchanged and only the clip window (`View::blocked`) is new. `show` reports `viewport_edit`, `enter_viewport` and `leave_viewport`; the app applies them (`layouts.rs`). On the bare sheet the commands edit paper space: new objects are tagged with the layout, so a drawing command never puts an object into the model at sheet coordinates.
- **App** (`opendraft-app/src/layouts.rs`, `layout_cmd.rs`, `layout_tabs.rs`): switching spaces, the tab strip, and `LAYOUT`, `MVIEW`, `VPSCALE`, `VPLOCK`, `MSPACE`, `PSPACE`. Every command is a registry entry like the rest. While a layout is on screen the ribbon carries the contextual Layout tab (see "Ribbon").
- **Light or dark paper** (`opendraft-app/src/canvas_style.rs`): a layout's sheet is white paper with black lines by default, as AutoCAD shows layouts (a preview of the printed sheet), or the dark look of model space (`Settings::layout_paper`, `LayoutPaper::{Light, Dark}`; per user, not saved in the drawing). It is switched by the Layout tab's Light Paper toggle, `LAYOUTPAPER` (`view.layout_paper`, shown pressed while light; OpenDraft's own command, as AutoCAD sets these colours in Options) or Settings > Display. Light paper is white unless the user chose one of the other presets, which glare less in the dark interface: Off-white (#F5F5F5), Light grey (#EEEEEE), Grey (#E0E0E0), Cream (#F0EAD6) or Sepia (#E8DCC0) (`Settings::layout_paper_colour`, `PaperColour` in `opendraft-app/src/paper_colour.rs`, saved by name so a preset's exact colour can be tuned; a row of swatches in Settings > Display > Layout paper). Presets rather than any colour, so every paper offered is tested and a picker never offers colours it would refuse: each is at least relative luminance 0.70 (`paper_colour::FLOOR`, about #D9D9D9), and a preset added must be too. Plots are on white whatever is chosen. Model space never changes. `canvas_style(colors, space, paper, colour)` builds the whole `CanvasStyle` each frame, after the layout tabs have run so a space switched by them is painted right at once. The light look covers the bare sheet and the model seen through its viewports, and every mark drawn over the drawing changes with it so it can be seen on any paper allowed (a test checks at least 3:1 for lines, selection, window and crossing boxes and the crosshair, and 4.5:1 for the snap label, on every preset; a darker preset may need darker marks): the selection is the accent itself, the snap marker dark amber, the crossing box a darker green, the grid dark, the crosshair dark grey. `CanvasStyle::surround`, the area around the sheet, stays dark on either paper, so off the sheet the canvas draws the crosshair in `Crosshair::OFF_WHITE` (`View::sheet_on_screen`); a crosshair colour the user chose is kept everywhere. The layer cache needs nothing new: its pictures are keyed by the line colour, so a toggle rebuilds the layout's pictures and leaves the model's alone, and text pictures are keyed by their resolved colour.
- **Per-viewport layer freeze:** `Viewport::frozen`, edited by `VPLAYER`. `Doc::keep_space_valid` runs every frame and copies the active viewport's list into `Document::active_frozen`, which `visible_objects` and `selectable_objects` honour; viewport painting passes the list to `paint_entities`. Stale ids (a layer deleted since) are harmless and are not validated.
- **Per-layout paper-space freeze** (AutoCAD's VP Freeze with no viewport active): `Layout::paper_frozen`. On a sheet with no viewport picked, `keep_space_valid` puts it in `Document::active_frozen`, the sheet's painting and the layout plot leave those layers' sheet objects out, and the VP Freeze switch acts on it (`view_freeze::FreezeTarget::Paper`, current layer left thawed). The layout's viewports and other layouts are not affected. DXF keeps it as the `331` handles of the layout's sheet-wide `VIEWPORT` (id 1), as AutoCAD does; `.odraft` has an optional `paper_frozen` list. Purge keeps such layers.
- **Freeze in the Model tab only** (an OpenDraft extension; AutoCAD has no such switch): `Layer::frozen_in_model`. In the Model tab, `keep_space_valid` puts those layers in `Document::active_frozen` (`Document::frozen_in_model`), so the Model tab hides them from painting, snapping, picking (`is_selectable` also honours `active_frozen`, and a newly frozen layer's objects leave the selection) and zoom extents; the Model-tab plot and its extents leave them out too. Layout viewports, and work inside one, ignore the flag. The Layers panel's VP Freeze column and the ribbon layer list's switch act on it in the Model tab (`view_freeze::FreezeTarget`); the current layer stays thawed, as Freeze leaves it. Files: an optional field in `.odraft`; in DXF, XDATA on the LAYER record (`1001 OPENDRAFT`, `1000 FrozenInModel`, `1070 1`, see `dxf::model_freeze`), with `OPENDRAFT` in the APPID table, so such a drawing is written as R2000. Home-page thumbnails still draw every visible layer.
- **Layers panel columns** (`layer_columns.rs`, `layer_column_resize.rs`): the name, linetype and lineweight columns are resized by dragging the line at their right edge in the header, or fitted to their widest entry by double-clicking it; the switches and the colour keep their width. The widths (`layer_columns::Widths`, never under 40 px) live in egui's persisted memory, so eframe keeps them between runs. Until the name is resized it fills the room left, as before; once resized it keeps its width, and a panel wider than the row leaves the rest empty. Every column always shows (they used to hide linetype and lineweight in a narrow panel): a row wider than the panel scrolls sideways (`Layout::fit`).
- **Plot / No Plot** (AutoCAD's Plot column): `Layer::plot`. A layer switched off it stays on screen but its objects leave every plot and preview (Model tab, viewports and the sheet's own objects; `Document::plots`, tested on each object and on each drawn piece: as in AutoCAD, a block on a No Plot layer leaves the plot whole, its objects on other layers too); Defpoints never plots, whatever its flag says (`Layer::plots`), as in AutoCAD. Plot extents still count them. The Layers panel has a Plot column after the padlock: a yellow printer, or a grey one struck through (`layer_columns::paint_plot_switch`); Defpoints' switch cannot be clicked. Files: DXF group 290 (written `0` only for a layer not plotted, and Defpoints; a No Plot layer makes the drawing R2000, since R12 has no flag), the DWG layer's plot bit (16), an optional `no_plot` in `.odraft`.
- **Plotting:** `opendraft_core::plot::plot_layout` turns a layout into `PlotSheet` paths in millimetres (pure, tested); `plot/settings.rs` then applies Layout, Limits, Extents or Window area, printable margins, exact custom/standard scale, fit-to-paper, centring, offset and optional lineweight scaling, with clipping to the physical paper. Display and named View are refused because OpenDraft does not persist an application display/view definition; they are never guessed. `opendraft_files::plot` writes the result as SVG or PDF (`plot_cancellable`, atomic like a save through the shared `write_atomically`); `AppState::plot_layout` (`plot_state.rs`) asks for the file and runs it as a background job. `plot_layout` first runs `plot_plan::validate_plot` (finite paper of 10 to 10000 mm, margins that leave room, a scale ratio in 1e-12..1e12, a window with area, name rules; errors are `PlotError::Invalid(PlotValidationError)`), and refuses a sheet over `MAX_PLOT_PATHS` / `MAX_PLOT_VERTICES` with `PlotError::ResourceLimit`; Extents of nothing is `NothingToPlot`, not a guess. `PlotSheet` keeps `paths` and `fills` with each fill's `after` (the paths painted before it); `paint_order()` is how every writer paints, so a fill sits between the strokes around it. `DRAW_VIEWPORTS_FIRST` decides whether viewport content or the sheet's own objects go first, `PLOT_VIEWPORT_BORDERS` plots viewport frames, `PRINT_LINEWEIGHTS` off plots every line as a hairline (width 0; SVG draws 0.05 mm), and wide polyline segments are plotted as filled ribbons (`width::triangles`), not single lines. Rotation (0/90/180/270) turns the upright placement onto the physical media. A layout's `width` and `height` are the paper as it feeds (AutoCAD keeps a landscape A4 as 210 × 297 with the plot turned a quarter), so the sheet's objects lie on the upright page, `Layout::page_size` (the sides swapped for a quarter turn). As in AutoCAD, a sheet's origin is the corner of its printable area (`Layout::printable_corner`, the margins turned with the plot): DXF coordinates are kept as they are, and the paper's own corner lies at minus that corner (`sheet_bounds`). The canvas draws the paper where the plot puts the drawing on it: `plot::paper_on_sheet` inverts `settings::placement` (area, scale, offset, centring), plotting the layout for Extents, and `view/paper.rs` keeps the answer per drawing revision. Margins can be edited in Plot and Page Setup for OpenDraft PDF and SVG (`page_setup_dialog/boxes/margins.rs`: one value with the padlock closed, four with it open, as the page is read; turning the page keeps each margin on its edge); a printer's are only shown. The user setting `plot_margins_mm` (Options, Files page; 5 mm) gives the margins of a new drawing's Model tab and of a new layout (`Layout::set_margins_keeping_paper`, the LAYOUT command through `CommandDefaults::plot_margins`), and replaces a printer's when that printer is not on this computer and the Plot dialog falls back to a PDF (`PlotDialog::settle`). A centred plot is written to DXF with the offset its centring comes to (`plot::centred_origin`), as AutoCAD writes it: AutoCAD shows and plots a drawing it opens with the stored offset until it centres again (when its printer changes). AutoCAD gives that offset along the paper as it feeds, so X and Y swap for a quarter turn (seen on an AutoCAD landscape A4: 5.81, 5.19 for a 277 × 190 frame). Checks still owed: a rotated plot that is not centred (which axis AutoCAD's offset is then read along), and our Extents of that drawing, 3.7 mm wider than AutoCAD's. Copies, style-table evaluation and device capabilities are not yet applied.
- **Plot dialog** (`PLOT`, `PRINT`, Ctrl+P; `PREVIEW` opens it with the picture drawn; `plot_job.rs`, `app/plot_dialog.rs`): starts from a complete copy of the layout's page setup (`PageDraft`) in `CommandDialogs::plot`, shares the Page Setup control groups (`app/page_setup_dialog/boxes.rs`, one function per group) laid out around the picture (one left column: Printer/plotter; Paper, its size and orientation on two lines; Plot, a caption-and-control form for area, scale and offset; Options in two columns; and a fixed-height preview on the right, with the printable margins dashed on the paper. Copies and Resolution appear only for a printer, the paper size is editable only for Custom, Display and View are not offered as plot areas, and the footer has Save changes at the left and the buttons at the right; it redraws itself on another thread (`plot_dialog_tick`) once the settings have stayed still for 250 ms, the first picture at once, and says "Updating the preview..." meanwhile; the plot options under it; the plot style table, "Plot with plot styles" and the shaded viewport options are left out of this dialog until a plot applies them, and Page Setup still shows them disabled), opening with the preview already drawn, and shows the exact `PlotSheet` the plot would write, drawn white through `opendraft_files::png` (`render_preview`, on another thread). Plot asks for the PDF/SVG file and writes from a copy of the drawing with the draft swapped in (`document_with_draft`), so the layout and the history are untouched; "Save changes to layout" and "Apply to Layout" go through `set_page_setup` (one undo step, none if nothing differs). `plot_controls.rs` is the pure enablement table (`control_state`): a layout area turns Fit and Centre off (and a layout plots from the printable corner whatever the centre flag says), Fit turns the scale numbers off but the draft keeps them (`kept_scale`), shaded options stay disabled in 2D, the plot style table and "Plot with plot styles" and "Hide paperspace objects" are disabled too (the plot applies none of them; the values are kept and round-trip, and the dialog says so beside each), and `-PLOT` does not ask about styles, and a setup that cannot plot disables Preview and Plot with the reason. The one Printer/plotter dropdown lists OpenDraft PDF and OpenDraft SVG (the file devices; each asks for its own kind of file) and then the machine's printers (found on a thread when the dialog opens; the dialog starts on the layout's stored device, else the last one used; Copies and Resolution apply to paper; the last printer and resolution are user settings, `plot_printer` and `plot_dpi`, taken again once the printers are found and only if that printer is still there; the body scrolls on a short screen so the buttons stay in view). `print_backend/` is the paper side: the `PrintBackend` trait (`printers`, `capabilities`, `submit`), `resolve_media` (the printer's own paper of the sheet's size within 0.5 mm, never a substitute), `validate_job` (copies 1..999, dpi 1..1200, names with no control characters or leading `-`), `raster_size` (100 million pixel cap), and a `Runner` that starts programs with an argument list, bounded output, a timeout and cancel. `cups.rs` asks `lpstat`/`lpoptions` and prints the PDF with `lp -d P -n N -o media=M -o scaling=100 -- file`; `windows.rs` runs a fixed PowerShell script (`print_windows.ps1`, passed as `-EncodedCommand`) over `System.Drawing.Printing`, with the mode in an environment variable and the job (printer, media, PNG path, size) in a JSON file, so a printer's name is never script text; a job the spooler accepted is not killed at the timeout. A `Done::Printed` result tells the user how it ended; the drawing and its history are untouched.
- **Plotting the Model tab** (`opendraft-core/src/plot/model_space.rs`, `plot_plan.rs`): the Model tab has its own page setup, `Document::model_plot` (`PlotSettings::for_model`: A4 landscape, Extents, Fit, centred), changed as one undo step by `SetModelPlot` (`Changes::layouts`) and stored in `.odraft` (`model_plot`) and as the DXF `Model` LAYOUT (an R12 file cannot hold it and says so in its export notes). `plot_sheet(document, PlotSpace::{Model, Layout(id)})` is the one entry point; for the model it takes the area (Extents of the visible model objects, or a Window in drawing units; Layout, Limits, Display and View are refused), works the scale out first (`settings::plan_scale`, which also converts a custom scale in inches) so curves are flattened as finely as the final size needs, generates the objects over the area with the same object code as a layout, and places the result with the same page setup code (margins, offset, centring, rotation, clipping, lineweights). `PageDraft` now holds a `PlotSpace`, so Page Setup, the Plot dialog, `-PLOT` (`Model` is a layout name) and the file writers all work on either; the model has no viewport options, its area dropdown offers Extents and Window, and the paper size is its own.
- **Plot window pick** (`plot_pick.rs`): with Area set to Window the dialog has a Pick button. It leaves the sheet's viewport if one is active (the window is in sheet millimetres), hides the dialog (`PlotDialog::picking`, and `modal_open` is false so the canvas takes the picks), and runs `PLOTWINDOW`, which asks for the first corner and then the opposite one with the usual rectangle following the pointer (`ask_window`, also used by `-PLOT`; a window with no width or no height is told and asked again). When the command has ended `take_window_pick` puts the corners in the draft; Escape, or another command replacing the pick, brings the dialog back unchanged.
- **-PLOT** (`plot_line.rs`, `plot_run.rs`; `opendraft-core/src/plot_input.rs` reads scales and offsets): asks Detailed plot configuration, a layout name (any layout, from either tab; `?` lists them), an output device (`PDF`, `SVG`, `OD PDF`, `OpenDraft SVG` or a printer by name or unique start; `?` lists), then with Detailed the paper size (name or `w,h` mm), paper units, orientation, upside down, plot area (Display and View refused, Window takes two points), scale (`1:50`, `2:1`, `Fit`), offset (`x,y` or Center), plot styles, lineweights, order and viewport borders; then the file name or number of copies, Save changes to layout, Proceed. It only asks: a finished request goes into `CommandDialogs::plot_requests` and the app carries it out once the command has ended (`take_plot_requests`), through the same file writer and print path as the dialog. A wrong answer is told and asked again; Escape plots nothing and changes nothing.
- **Page Setup** (`app/page_setup_dialog.rs`, `app/page_setup_dialog/preview.rs`, `AppState::set_page_setup`): an AutoCAD-shaped dialog edits the layout name and its complete `PlotSettings` working copy (`PageDraft`)—file plotter, paper/media, area/window, offset/centring, scale, orientation, plot flags, style sheet and shaded-output quality. Its third pane is a live, allocation-free placement preview of paper, printable margins and plotted area; it intentionally does not pretend to render drawing content before the plot transform consumes these settings. OK validates and replaces the layout list as one undo step; Cancel drops the draft. System printer discovery and paper output are clearly unavailable rather than represented by fake devices.
- **Files:** native `.odraft` stores layouts and their plot settings (`opendraft-files/src/native/layout.rs`) and an optional `layout` on objects. DXF keeps layouts too: a drawing with layouts is written as R2000 (`dxf/write2000*`: block records, `LAYOUT` objects with `AcDbPlotSettings`, viewports with scale, lock and frozen layers, sheet entities where AutoCAD puts them) and read back by `dxf/read/layouts.rs`. Without layouts the writer stays R12. Validated with ezdxf, not AutoCAD. A layer named Defpoints (any case) is written not plotted (group 290 = 0): AutoCAD never plots it and refuses the whole file when the flag says otherwise; the other layers leave 290 out, which means plotted.

## Dimensions (built)

`Entity::Dimension(Box<Dimension>)` (`opendraft-core/src/dimension/`) follows the AutoCAD model of a semantic entity plus a generated picture, in this project's structures (ids, `Point`, no handles or `nalgebra`). The definition points (`DimKind::{Linear, Radial, ArcLength, Angular, Ordinate}`; a radial one may be jogged), the style, the text (and its angle and position) and the ties to objects are authoritative; `Dimension::picture()` regenerates lines, arcs, arrowheads (tapering wide polylines) and text (multiline text from `Dimension::contents`, which stacks tolerances) from them, and every other system reaches a dimension through that picture: the canvas paints, picks, snaps and window-selects its pieces, plotting flattens them, Explode returns them. Nothing caches the picture; a dimension is a handful of pieces.

- **Style.** `DimStyle` carries the `DIM*` variables the code uses (lines, arrows including a second one, text with fill and frame, fit, primary, angular and alternate units, tolerances, fixed extension lines, baseline spacing). A dimension holds its own copy, so the drawing's current style (`Document::dim_style`, `SetDimStyle`, the `DIM*` system variables in `dim_vars.rs` and `dim_vars_extra.rs`) only affects new ones. The drawing also keeps a table of named styles (`Document::dim_styles`, changed by `SetDimStyles`, which restyles the dimensions made in a style that changed); a dimension finds its style by the name it carries; DIMOVERRIDE changes a dimension's own copy. `DIMSCALE` multiplies sizes (`DimStyle::resolved`), never the measurement.
- **Modules.** `style`, `text` (measurement text, `<>` templates), `tolerance` (alternate units, stacked tolerances), `font`, `fit` (`DIMATFIT`), `sketch` (primitives, readable text angle, text box and mask, line-around-box clipping), `linear`, `radial`, `jogged`, `arc_length` (also draws angular), `angular`, `ordinate`, `centre`, `chain` (baseline and continue), `jogline` (jog lines, spacing), `assoc` (ties), `edit` (transforms, stretch, grips, DIMEDIT's changes) and `pick` (object ends, automatic linear direction, radial from a click). Pure and tested; the `opendraft-app/src/dimension_*_cmd.rs` files only ask, and `dimension_commands.rs` registers them.
- **Associativity.** `Dimension::assoc` ties defining points to points of objects (`AssocPoint`: start, end, centre, vertex, circumference). A dimension made by a command is tied to the objects its points sit on (`Dimension::associated`, in `draw::add`), and `opendraft-commands/src/associations.rs` (the hook the associative hatches use) refreshes the points of dimensions whose objects changed in the same undo step; a dimension edited on its own, or whose object is erased, lets go of the points it no longer shares. DIMDISASSOCIATE and DIMREASSOCIATE are the commands; paste clears the ties (the ids differ). Not saved to DXF (no `DIMASSOC`), and the angle between two lines is not tied.
- **Files.** `.odraft` (`opendraft-files/src/native/dimension.rs`, `dimension_style.rs`) stores every dimension style in full, in one pool without repeats (`dim_styles`) that the named table (`named_dim_styles`), the current style (`current_dim_style`, by name) and each dimension (`style`, a position) refer to, so a file does not change meaning if the stock style does; and the ties. DXF (`dxf/write2000/dimension.rs`, `dxf/read/dimension.rs`, shared group codes in `dxf/dimstyle_codec.rs`) writes linear, aligned, radius, diameter, angular and ordinate dimensions as `DIMENSION` entities with anonymous `*D` picture blocks, a DIMSTYLE table of all the styles and `DSTYLE` extended data for overrides, and reads them back; arc length, jogged and jog line dimensions are written as pictures. Checked with ezdxf, not AutoCAD. DWG dimensions are skipped.
- **Not built, in the order to take them:** DWG dimension import (the DWG reader skips the dimension objects; needs the DIMSTYLE table object too), colours, linetypes and lineweights in styles (the picture's pieces need roles), the standard arrowhead set, `ARC_DIMENSION` and jogged radius as real DXF, DIMBREAK and DIMINSPECT, `DIMASSOC` in files (needs a handle per written entity), then annotative scales and arrowheads from the user's own blocks. Also: tolerances and alternate units on angular dimensions, and the angle between two lines is not tied. What each needs is in `docs/parking_lot.md`, "Dimensions".

## Multiline text (built: data, parser, layout and painting)

`Entity::MText(Box<MText>)` (`opendraft-core/src/mtext/`) keeps AutoCAD's `MTEXT` fields and, as its authority, the exact format-code stream in `contents`. Nothing derived from the contents is stored: glyphs, wrapping and the real extent belong to the layout engine (below), which works them out when asked.

- **Styles.** `Document` owns a text-style table (`text_style.rs`, `document/text_styles.rs`): `TextStyleId` (never reused, counter kept), `Standard` (id 0) always first, unique names ignoring ASCII case, a current style. A font is a `FontDescriptor`; what a style asks for is kept even where this build would draw something else.
- **Parser.** `opendraft_core::text::parse(&str)` is lossless: every byte belongs to one `Node`, in order. What it understands becomes a typed node (text, `\P`, escapes, `\U+`, groups, character formats, stacks, fields); anything else, or anything malformed, is an `Opaque` node with an `OpaqueReason` and a `Diagnostic`. An edit may rewrite only nodes it understands. Limits (`TextLimits`: 1 MiB, 100,000 nodes and paragraphs, eight group levels, 64-byte numeric and 1 KiB other payloads) are checked before work. Paragraph controls (`\p...;`) are decoded only as far as `private_material/MText Example.dxf` (made in AutoCAD) shows: `\pxi<first>,l<left>,q<l|c|r|j>,t<stop>,<stop>...;` become a `NodeKind::Paragraph(ParagraphStyle)` (distances in drawing units). A control holds for its whole paragraph, wherever it sits, and for every paragraph after it until another one (the second sample writes a list's control only on its first item), so `ParsedMText::paragraphs[i].style` is the effective style and `apply_paragraph_edit` writes a control only where the style changes. Lists are plain text in AutoCAD files (`1.` and a tab, or a Symbol-font bullet), not a control; `text::list::apply_list` writes the markers and the hanging indent together. Anything else in a `\p` (right indent, spacing, tab kinds) stays opaque; its paragraph and those inheriting from it are `protected`. Layout aligns each line after the line breaker has run (`align_line`): right and centre shift it within the wrapping width (the widest line when there is none), justified spreads the spaces of every line that does not end its paragraph. See `private_material/`.
- **Refusal.** `Entity::mirror_refusal` and `scale_refusal` say why an object cannot take a transform; Mirror and Scale (and their grips) ask first and change nothing when any object refuses, so the contents are never rewritten by guess.
- **Layout.** `opendraft_core::text::layout_text(&MText, &TextStyle) -> TextLayout` shapes each run with `rustybuzz` in the bundled DejaVu Sans, in the regular, bold, oblique or bold-oblique face the run's `\f` control or the style asks for (`opendraft-core/assets/fonts`), scales it so a capital is the text height tall, wraps greedily at spaces, hyphens and ideographs (a word with no break runs past the width, as in AutoCAD), runs tabs to a default interval, spaces lines (at least / exactly), and returns positioned glyphs, per-line spans, merged underline/overline/strike bars, frame and text extents and a list of `LayoutIssue`s for whatever it did not do (stacks drawn as text, fields skipped, fonts substituted, columns and vertical flow ignored, missing glyphs). A stack (`\S1/2;`) is one unbreakable cluster of smaller, offset glyphs with an optional bar, so it wraps, takes carets and is deleted like a letter. Local coordinates: origin at the block's top left, x along the text, y up. `MText::world_point(&layout, x, y)` applies attachment, direction and insertion. `glyph_contours(id, tolerance)` gives an outline as flat closed contours in font units.
- **Remembered layouts.** `MText::layout(&style)` goes through a small thread-local memory (`text/memo.rs`) keyed by exactly what layout reads, so moving or rotating text keeps its entry and every bounds query or repaint is a lookup. It only remembers; the answer is the same without it.
- **Context-free queries use the stock style.** `MText::frame`, bounds, snapping, grips and picking lay out in `Standard` because an `Entity` does not know its style; painting uses the real style. A style with another width factor or slant is therefore picked and snapped slightly off its drawn size. `Document::object_bounds` (style-aware) is the fix and is not built.
- **Painting** (`opendraft-canvas/src/view/text_paint.rs`): each glyph's outline is cut into triangles by `lyon_tessellation` (non-zero fill) once per size bucket and cached, then a repaint only moves vertices into one mesh per text. Text under 12 px tall is instead rasterised whole (`text_raster.rs`: exact horizontal and eight-fold vertical coverage into a small texture, kept by a hash of what it shows and the zoom rounded to an eighth of an octave, drawn as a quad so rotation is free; too large a picture falls back to the fill), and under 0.75 px as a line per text line that fades with its height. In the fill (above 12 px) a stroke-font pen is never thinner than 1.1 px, and the window uses 4x MSAA for the filled text above 12 px. Colours: the object's own, `\C` indexes (7 is the foreground) and `\c` true colour; a selected text is drawn in the selection colour with its frame. ACI colours now live in `opendraft_core::aci` (moved from `opendraft-files`).
- **Files and commands.** Native files distinguish `text` from `mtext` and keep the whole `text_styles` table. DXF export writes `TEXT`, `MTEXT` and STYLE in R2000; import reads both text kinds and STYLE (`dxf/read/text.rs`). `TEXT` keeps its point, height, rotation, width factor, oblique angle, style, generation flags and horizontal/vertical justification. Align and Fit additionally retain their second point: Align changes height uniformly to span the points, while Fit keeps the requested height and changes only the entity width factor. Their resolved ordinary TEXT fields keep drawing context-free; grips, stretch, transforms, Properties, native files and DXF preserve the two-point rule. `MTEXT` keeps its contents as written, box width, direction or rotation, attachment, flow, spacing and mask; columns and non-XY planes are skipped by reason. DWG import keeps `TEXT` as single-line text and `MTEXT` as multiline text; attributes remain attributes. Plotting writes both kinds as filled glyph outlines through the shared MText projection. `TEXT`/`DTEXT` (`opendraft-app/src/single_line_text_cmd.rs`) asks for justification or style, point, height, rotation and one line; its Align and Fit options ask for two endpoints, and empty text adds nothing. `MTEXT` (`opendraft-app/src/mtext.rs`) takes two corners and opens the editor. Height (`TEXTSIZE`) is shared and remembered; a text prompt keeps typed spaces.
- **OD Roman (built: data, outlines, layout, painting, plotting, style and editor UI).** The application's own single-stroke font, drawn as one SVG per glyph in `fonts/od_roman/glyphs/` (`U+0041.svg`, whose viewBox is the advance box; red strokes are the glyph, `stroke-width` over `pen` is a stroke's weight, `class="dot"` a dot) with `fonts/od_roman/font.cfg` for the shared metrics, and described in `private_material/od_roman_font_specification.md`. `scripts/od_roman_import.py` builds `opendraft-core/assets/fonts/od_roman.odf` from them and warns about ink outside or too near an advance box; after every build it also writes `fonts/od_roman/preview/` (gitignored): `index.html`, a self-contained viewer with live text, a weight slider and a glyph grid, plus an overview and a specimen at the real advances; `od_roman_new_glyph.py` starts a glyph file, `od_roman_respace.py` changes margins by hand and `od_roman_autospace.py` spaces the glyphs listed in `fonts/od_roman/spacing.cfg` by the shape of their left and right edges (stem, round, open, diagonal, ...); `text/stroke_font.rs` reads it (`od_roman()`, `StrokeFont`, bounded and tested) and `text/stroke_outline.rs` turns a glyph and a pen weight into counter-clockwise capsule contours that the existing non-zero fills draw, so painting and plotting need no new path. Advances do not depend on weight. Layout: `FontDescriptor::OdRoman { bold, italic }` and `TextStyle::stroke_weight` (a fraction of text height, default 0.10, clamped 0.01 to 0.40); `FontFace::OdRoman` glyph ids are slots in the font; `PositionedGlyph::weight` is the pen in thousandths of cap height (0 for DejaVu) and `glyph_outline(face, id, weight, tolerance)` returns contours for either kind, which painting (`text_paint.rs`, cache keyed by weight) and plotting (`plot_text.rs`) call. `layout/items/stroke.rs` shapes a run character by character from the font's advances, so weight and shear never move a caret; bold multiplies the pen by 1.6, italic adds 15 degrees to the style and `\Q` obliques; a character the font lacks is drawn in DejaVu (`MissingGlyph` only if neither has it); a `\fOD Roman;` or `\fDejaVu Sans;` control switches font mid-text. `.odraft` keeps the font (`FontDto::OdRoman`) and an optional `stroke_weight`; DXF writes `RomanS.shx` for now. Per-run weight is a field of the font control, `\fOD Roman|b0|i0|w0.18;` (`FontFlags::weight`, thousandths of the cap height, clamped 0.01 to 0.40; a control without it hands the weight back to the style, and bold still multiplies it); `CharState::weight` carries it, `CharEdit::weight` and `SelectionFormat::weight` are how the editor sets and reads it (0 clears it), and `apply_char_edit` writes it in the font control for the family it is given (`OD Roman` for an OD Roman style). The Text Style dialog lists OD Roman and shows \"Line Weight\" (percent of height) for it; the MTEXT toolbar shows \"Weight %\" when the style is OD Roman (`MTextEditor::uses_stroke_font`). Whether AutoCAD tolerates `|w` in `\f` is untested, so DXF export may need to strip it. Still to do: DXF round trip data, the PDF text layer (see the specification's milestones 6 and 7).
- **The in-place editor** (`opendraft-app/src/mtext_editor/`). A command opens it with `Editor::edit_mtext(text)`, a prompt of kind `Wants::MTextEditor` carrying a copy of the text; `AppState::sync_mtext_editor` opens an `MTextEditor` on the running document when the command waits and drops it when the command ends. The editor edits only the copy and its own undo history. Accepting answers the command with `Reply::MText` (or `Reply::Enter` when empty or unchanged), which then makes one `AddEntity` or `ModifyEntities`; Esc cancels the command like any prompt. `state.rs` and `input.rs` are egui-free and tested (input with made-up `egui::Event`s); `window.rs` paints and reads the pointer. While `AppState::mtext_editing()` the command line, dynamic input, shortcuts and canvas picking stand aside. Carets, selection boxes and edits come from `opendraft_core::text` (`TextLayout::carets`, `caret_at`, `step`, `selection_rects`, `replace_text`); the editor never lays out text or writes controls itself. Character formatting follows the same rule: the toolbar names a `CharEdit` and `opendraft_core::text::apply_char_edit` writes the controls (a `{ }` group opened with them); `format_in` reads what a selection looks like, with the same `CharState` the layout draws with. Paragraph formatting is the same: the ruler (`ruler.rs`, drawn along the box's top edge in the text's own direction) names a `ParagraphEdit` and `opendraft_core::text::apply_paragraph_edit` rewrites each touched paragraph's `\p` control; `paragraph_view_in` reads it. A new paragraph simply inherits the control above it. The box has resize grips (`box_handles.rs`: right edge = wrapping width, bottom = `MText::reference_height`, corner = both; the box is the same one in the drawing, selection grips and editor).

## Blocks (built; dynamic blocks are not)

A block definition is a record in the drawing's block table and a block reference is an entity that points at it, as in AutoCAD; the design follows `private_material/blocks_dynamic_blocks_specification.md` in this project's structures (typed ids never reused, no slotmap, handles or `nalgebra`).

- **Data** (`opendraft-core/src/block/`, `document/blocks.rs`): `BlockDef { id, name, base, description, entities }`, each entity a `BlockEntity` (geometry in the block's own coordinates plus `Attributes`). `Entity::Insert(Box<Insert>)` holds `block: Arc<BlockDef>`, `insertion`, `scale_x`, `scale_y` (never zero; negative mirrors) and `rotation`. The table holds the same `Arc`s, so inserts share one copy of their block and need no drawing to be drawn. **Definitions are immutable:** changing one means building a new record and repointing every insert and every definition that holds it (`Document::redefined_blocks`), which the app records as `SetBlocks` plus `ModifyEntities` in one transaction. Because a definition can only hold `Arc`s that already exist, nesting cannot loop in memory; redefinition and the file reader refuse a block that would hold itself, and expansion stops at `MAX_NESTING` (64).
- **Transform** (`block/affine.rs`): `Insert::transform()` is `T(insertion) · R(rotation) · S(scale_x, scale_y) · T(-base)`. A map that keeps shapes (`Affine::similarity`) is applied with the entities' own exact transforms, so circles stay circles and a nested insert stays an insert with the maps combined (`Insert::transformed`); a mirror is kept as a negative X scale. An uneven scale turns circles, arcs and ellipses into exact ellipses (`Ellipse::mapped`, `block/picture.rs`).
- **Picture:** `Insert::picture_with(attrs)` gives every simple object the insert draws, in drawing coordinates, nested blocks expanded, each with its layer after inheritance (an object on layer 0 takes the insert's layer). Other systems reach an insert only through it, as with dimensions: hit-testing, selection, snaps (plus the insertion point), painting and plotting (`Document::insert_pieces` and `Document::drawn` give the pieces as objects so each is drawn in its own colour and hidden layers drop out), and DXF export (`dxf/blocks.rs`). Nothing caches the picture yet.
- **Validation:** unique block ids and names (ignoring case), names allowed by AutoCAD (`block_name_problem`), objects on existing layers, and every insert (in the drawing or in a definition) using the table's own record with a valid transform. A layer used inside a block counts as in use.
- **Commands** (`opendraft-app/src/block_cmd.rs`, `block_dialog_cmd.rs`, `insert_cmd.rs`): `BLOCK` opens the Block Definition dialog (`app/block_dialog.rs`, laid out as AutoCAD's: name; base point typed or picked; objects selected, picked after OK or preselected; Retain, Convert to block or Delete; description; Open in block editor) and `-BLOCK` is the command-line form; both make the block through `make_block`. The dialog follows the OVERKILL pattern (`Wants::BlockDialog`, a `BlockDraft` in `opendraft-core` that is checked and tested; its Pick point and Select objects buttons close it while the command asks in the drawing and open it again). Block unit is real: `BlockDef::unit` (an `InsertUnits`, saved in `.odraft` and in the DXF BLOCK_RECORD's code 70, not read from DWG), and INSERT scales a block by `InsertUnits::ratio(block unit, drawing insert units)` on top of the scale chosen (nothing when either is unitless). Switched off with a reason: Annotative, Match block orientation, Scale uniformly, Allow exploding, Hyperlink, quick select and Help. BCLOSE with unsaved changes asks in a dialog (Save, Don't Save, Cancel; `BlockEdit::closing`, `AppState::answer_block_close`), as does closing a drawing or quitting while a block is open. Esc while picking returns to the dialog (the same for Select block in the Attribute Editor): a prompt asks for that with `Options::esc_backs`, and the app then answers Esc with `Reply::Back`, which fails only that ask, where `Reply::Cancel` ends the command. `INSERT`, `PURGE` (a dialog over `opendraft_core::purge`, in `purge_cmd.rs`; `-PURGE` deletes everything unused) and `EXPLODE` (one level, parts keep their own properties). Pure logic (unused blocks, listing) is tested with the commands.
- **Dialog chrome** (`opendraft-ui/src/widgets/containers.rs`, `dialog`): the only place a dialog's title bar and close button are drawn. A dialog is held by its top-left corner (centered once, from its laid-out size), so a warning appearing in it moves its bottom edge, not the whole window. The header is laid out after the body, at the window's final width, so wide content cannot leave the close button short of the corner. Guarded by opendraft-ui tests of the header and close geometry (narrow, just-fitting and wide content) and by `opendraft-app/tests/dialog_chrome.rs`, which fails if any other file uses `.title_bar(false)` or `DIALOG_CLOSE`. Build every dialog with `widgets::dialog`.

- **Files:** `.odraft` (`opendraft-files/src/native/block.rs`) has a `blocks` list and an `insert` entity naming its block by id; definitions are resolved by id in any order. DXF (R2000) writes real blocks: a block record and a `BLOCK` ... `ENDBLK` per definition (`dxf/write2000/blocks.rs`; a dimension, leader or multileader inside a block is written as the pieces it draws) and an `INSERT` per reference, with `ATTRIB`s owned by it and a `SEQEND` when it has attributes (`write2000/insert.rs`). A drawing with a block is written as R2000.
- **Import (DXF and DWG):** both readers collect each named definition with its references to other blocks unresolved (DXF names, DWG handles) and hand them to `opendraft-files/src/block_import.rs`, which builds them depth first (a definition can only hold `Arc`s that already exist), puts them in the table in the file's order, and resolves the model's references. A block whose name AutoCAD would not allow or that repeats another, a reference that would nest a block in itself (or past `MAX_NESTING`), a reference to a missing block and one with a zero or non-finite transform are left out and counted in the warnings. An anonymous block (`*U`: how AutoCAD stores a modified dynamic block) that an INSERT places is built as an ordinary block named `Anonymous_U12` (unique ignoring case; `block_import::importable_names`), keeping its picture but none of its parameters or actions, and the references are counted in one warning; the anonymous pictures of dimensions and hatches (`*D`, `*X`), which nothing places, stay out of the table. DXF finds the placed ones by scanning every INSERT (`dxf/read/blocks.rs`, `keep_inserted`); DWG follows references from model space and the named blocks through other anonymous blocks (`opendraft-dwg/src/anonymous.rs`). External references are not read; references to them are counted. Both readers leave out an object the file marks invisible (DXF group 60 = 1, a DWG entity's invisible flag) and count it in one warning; this is how a dynamic block keeps its other visibility states, so a modified instance shows only the state it was saved in. DXF reads definitions when its BLOCKS section begins (`dxf/read/blocks.rs`; entities go through `Importer::shape` into the drawing or the definition being read); `opendraft-dwg` decodes INSERT and the block record's base point and description, and a downward extrusion on an insert becomes a negative X scale and a negated rotation. Attributes (ATTDEF/ATTRIB) are read from DXF (`dxf/read/attribute.rs`) and DWG (see "Files"), MINSERT arrays and other DXF extrusions are skipped or ignored; "by block" properties become "by layer" with a note.
- **Dynamic blocks in DXF** (`opendraft-files/src/dxf/read/dynamic.rs`, `dynamic/nodes.rs`; public as `opendraft_files::dynamic`): a decoder, and an importer on top of it (`dxf/read/blocks/dynamic_import.rs`). The decoder reads plain values (`DynamicBlocks`: definitions with their nodes and edges, and the modified references with their values). The importer keeps a definition's linear parameters (value lists as a list value set; a grip for each grip node linked to it) and its stretch and move actions, its rotation parameters (base point, radius from the grip's point; one with a list or increment of angles is left out) with rotate actions about the parameter's base point, its flip parameters (the mirror line) with flip actions, its scale actions, when they act about the linear parameter's start point, its XY parameters (base, corner, a point value) and point parameters (a location) with the moves and stretches that follow them (a modified reference of a point parameter is not rebuilt, as its state is not read), and its polar parameters (base, end, an angle increment as the angle's value set; a list of distances or of angles is left out) with the polar stretch, stretch, move, scale and rotate actions that follow them, a polar stretch being read as a stretch; a reference to a definition that has a flip is not rebuilt, because whether it is flipped is not read (`dxf/read/blocks/dynamic_import/definition.rs` reads a definition). An action's object handles become block object ids, which on import are the objects' positions in the block's list in the file (so an id may skip a number where an object was left out), and a stretch frame becomes its bounding rectangle; a parameter nothing follows is dropped, and an action whose objects did not come across is dropped with it (the block is then kept as its default picture and counted). A modified reference, an INSERT of a `*U` block, becomes a reference to the definition with the distance each linear parameter's record gave, brought into the parameter's value set, and the anonymous block is not kept; this is done only when everything in the definition that moves geometry was understood (a lookup parameter and table change no geometry, so they do not stop it but are named in the note), otherwise the reference keeps the anonymous block's picture. Array, alignment and base point parameters, and a lookup whose table does not read as one input column of a linear parameter's values and one output column of labels,, and a scale about a point of its own, are left out and named in one note. A modified reference to a polar parameter gives its end point, kept as a `Point` value. A modified reference's rotation is the angle of the grip point its record gives, from the definition's own direction, and is kept as an `Angle` value. On `dyn_blocks_2`, three modified references of a linear stretch (5, 10 and 2.5) evaluate to the same bounds as their anonymous blocks. DWG has no decoder, so DWG import is unchanged. Autodesk does not publish these objects; the layout below was read from AutoCAD-made files and has been checked against two sample drawings, not against AutoCAD's own code. A definition is a BLOCK_RECORD with XDATA `AcDbDynamicBlockTrueName`; its extension dictionary's `ACAD_ENHANCEDBLOCK` entry is the `ACAD_EVALUATION_GRAPH`, a list of nodes (`91` index, `360` handle) and edges (`91` from, `91` to, by index). Each node object starts `AcDbEvalExpr` with its id in group 90, and an instance's records are keyed by that id. Decoded: linear, polar, rotation, flip and visibility parameters (a visibility parameter's `331` handles are the objects it governs and each state is a `303` name with `332` handles of the objects it shows; the objects of the states a definition does not show are written invisible, `60` is 1, and are kept when a visibility parameter governs them and dropped, counted, when nothing does; an instance's record holds the state's name in `1`, so a modified reference keeps its state when the block has a state of that name), and lookup parameters with their lookup action, whose table (`92` rows by `93` columns, each column an input or output flag with its property name) is read as a lookup when it has the one input column `UpdatedDistance` (the value of the block's one linear parameter) and one output column of labels, each row's label being its output cell and its value its input cell (start, end, a value list as `175` count and `144` values), lookup parameters, stretch, polar stretch, move, scale and lookup actions (the table is `92` rows by `93` columns of `302` cells, each column an `281` input or output flag and a `304` property) and grips; every other object is kept by its DXF name (`NodeKind::Other`) so nothing is guessed. A modified reference is an INSERT of an anonymous `*U` block whose extension dictionary leads, through `AcDbBlockRepresentation`, to `AcDbRepData` (`340` is the definition's block record) and to `AppDataCache` > `ACAD_ENHANCEDBLOCKDATA`, one `XRECORD` per node that holds a value: a linear or polar parameter's start and end points (the value is the end's distance, and for polar its angle too) and a lookup's text. The scale action's factor is the linear parameter's value over the definition's. Reading is bounded (`MAX_NODES`, `MAX_LIST`) and a damaged object is left as `Other` or left out, never a panic. DWG is not decoded: `opendraft-dwg` has no reader for these classes.
- **Block Editor** (`opendraft-app/src/block_editor.rs`): BEDIT swaps the tab's `Doc::session` for a session over `Document::block_editor_document(id)` (the drawing's tables and counters, no layouts, the block's objects with its base point at the origin) and keeps the drawing's session, view and selection in `Doc::block_edit`. Every command then works on the block unchanged. **Anything about the file uses `Doc::drawing()`** (save, export, autosave, the unsaved star), never `session`, which is the editor's while a block is open. BSAVE asks `Document::block_edit_save` for the changes (worked out on a copy, so a refusal changes nothing) and records them in the drawing's history as one step. A command that must open or close the editor (BEDIT's name prompt, BCLOSE's question) runs on its own thread, so it pushes a `BlockEditRequest`, which `AppState` carries out after polling the command. While a block is open the ribbon shows the contextual Block Editor tab and opens on it (see "Ribbon", contextual tabs).
- **ByBlock.** `Attr<T>` is `ByLayer`, `ByBlock` or `Set(v)` (`opendraft-core/src/layer.rs`) for colour, linetype and lineweight. Expanding an insert (`Insert::picture_with`, `exploded`) resolves each ByBlock object through `block::inherited`: it takes the insert's own setting, a ByLayer insert giving the value of *its* layer (`LayerLook`, from `Document::layer_look`) even when the object sits on another layer, and a ByBlock insert passing ByBlock on to the next level out. What is still ByBlock on a piece (or on any object outside a block, or while editing a block) draws with `LayerLook::OUTSIDE_BLOCK`: white, continuous, default weight, as AutoCAD does. Files keep it: `.odraft` `by_block`, DXF 62 = 0, 6 = ByBlock, 370 = -2 (MLEADER style 0xC1000000 / -2), DWG colour 0/257, linetype flag 1 and lineweight 30. The wire adds `by_block` to the colour, linetype and lineweight modes. A layer's colour cannot be ByBlock.
- **Attributes and data fields** (`opendraft-core/src/block/attribute*.rs`, `field.rs`; `opendraft-app/src/attdef_cmd.rs`, `attribute_prompt.rs`, `attribute_edit.rs`, `attribute_sync_cmd.rs`, `attribute_memory.rs`; `opendraft-files/src/native/attribute.rs`). Built from `private_material/block_attributed_and_data_fields_specification.md`; see `docs/history.md`, "Block attributes and data fields". An attribute definition (`Entity::AttributeDefinition`, DXF `ATTDEF`) is a template text inside a block (or loose in the drawing). Each insert owns `Insert::attributes`: one `AttributeReference` per non-constant definition, in definition order, holding its own value, in the block's coordinates, so moving the insert moves the text. A reference names its definition by `AttributeDefinitionId` (`source`), never by tag, because tags may repeat; `source: None` is an orphan (its definition went) and is kept until ATTSYNC. A reference may carry `attrs: Option<Attributes>`, properties of its own (layer, colour, linetype, lineweight); `None` follows its definition (or, for an orphan, its insert). Those count as uses of a layer or linetype (`layer_in_use`, `linetype_uses`), are validated, remapped on paste, saved in `.odraft` (`look`), read from and written to DXF (an `ATTRIB` equal to its definition keeps none), and reset by ATTSYNC. DWG import does not carry them yet. A constant definition has no references: every insert draws the definition's value. Ids are allocated from `Document::next_attribute_definition_id`, never reused, and only have to be unique inside one block: loose definitions may be copied (BLOCK and the Block Editor's save renumber repeats with `BlockDef::renumber_duplicate_attributes`). The picture of an insert includes constant values and visible references as `MText` projections of the single-line text (`AttributeText::projection`), so bounds, painting, picking, snapping, plotting and EXPLODE need no case of their own; invisible attributes are not drawn (`ATTDISP` is not built). Redefining a block keeps references and orphans those whose definition went (`Insert::rebound`); `sync_references` (ATTSYNC) is pure and idempotent. A data field (`FieldText`, `DataField`) is stored as evaluator, code, format, object references (by our ids, or `Unresolved`), children and its last value: a field always shows its cached value (`####` when it has none, never its code), and `block/field_eval.rs` brings it up to date with two evaluators: `AcObjProp` (Length, Area, Radius, Diameter, Circumference, Layer, Name of the object in the field's first reference, formatted in the drawing's units) and `AcVar Filename`, whose `FieldContext` the app passes in the command `Context` when a command starts. Any other evaluator stays `Unsupported` with its cache; one that cannot be evaluated now (object erased, property not suited, unsaved drawing) keeps its last value and is `EvaluationFailed`. `update_fields` plans the edits (pure, one `ModifyEntities` step); `FIELD` (`opendraft-app/src/field_cmd.rs`) puts a field in an attribute from command-line prompts and `UPDATEFIELD` refreshes the selected inserts and multiline texts. Multiline text keeps its fields in `MText::fields` and marks each place in the contents with `%<\_FldIdx N>%` (`mtext/fields.rs`); layout shows the value in its place. `FIELDEVAL` (`Settings::field_eval`, bits 1 open, 2 save, 4 plot) decides when `field_refresh.rs` runs `update_all_fields` over the drawing: on open directly on the loaded `Document`, on save and plot as one undo step. The Attribute Editor's Field button reuses the Field dialog (`field_dialog_cmd::choose_field`) and `EditorRow::field`. `block/field_kinds.rs` lists the fields the Field dialog offers (Date, Object and the text ones: Filename and the drawing properties Author, Comments, HyperlinkBase, Keywords, Subject, Title, kept in `Document::properties` and handed to fields through `FieldContext`) with their formats and the date and case formatting; `opendraft-app/src/field_picker.rs` is the dialog and `mtext_editor/field_dialog.rs` hosts it in the text editor (Ctrl+F). Fields paste into another drawing with their object references detached. Limits live in `block/field.rs` and `attribute.rs` and are checked by `Document::validate` and the `.odraft` reader. `.odraft` stores definitions, references and fields (`native/attribute.rs`). DXF reads `ATTDEF` and, after an `INSERT` with group 66, its `ATTRIB`s up to `SEQEND` (the insert is held until its `SEQEND`, so a cut-short sequence is dropped and counted, never joined to the next insert); an `ATTRIB` arrives in drawing coordinates and `block_import` moves it into the block's (`Insert::attribute_text_in_block`, the exact inverse of how the picture draws it), then pairs it with the first unused non-constant definition of the same tag, so duplicate tags pair in order and an unmatched one is an orphan. A mirrored insert's `ATTRIB` (extrusion 0,0,-1) is reflected back; aligned, fit, multiline and tilted-plane text is skipped by name; a constant `ATTRIB` is skipped and counted; an attribute with extension data (possibly a data field) is read as its last text, with a warning. DXF writes them back as above (ATTRIB at its drawn place, unmirrored) and **refuses** a drawing that holds a data field. Checked with ezdxf (`tests/fixtures/make_ezdxf_attributes.py`, `check_attributes.py`), not AutoCAD.
- **Attribute dialogs** (`opendraft-core/src/block/attribute_draft.rs`, `opendraft-commands/src/editor/attribute_asks.rs`, `opendraft-app/src/attribute_dialog_cmd.rs`, `opendraft-app/src/app/attribute_{definition,editor}_dialog.rs`). `ATTDEF` opens the Attribute Definition dialog and `EATTEDIT`/`ATTEDIT` the Attribute Editor (tabs Attribute, Text Options, Properties; Select block; Apply, OK, Cancel), laid out as AutoCAD's; `-ATTDEF` and `-ATTEDIT` are the command-line forms. They follow the OVERKILL pattern: the command asks (`Wants::AttributeDefinitionDialog`, `Wants::AttributeEditorDialog`) with a plain draft (`DefinitionDraft`, `EditorDraft`: checked, and turned into the definition or the edited insert, in `opendraft-core`, tested), the app draws the dialog from `AppState::attribute_dialogs` and replies. Shown switched off with a reason: Multiple lines, Annotative, Boundary width, Plot style, Align below previous, the field button, the pick-on-screen buttons and Help. The justification list has no Aligned, Middle or Fit. A value that is a data field is shown and not edited. Apply makes one undo step each time and the dialog stays open on the same attribute and tab.
- **DWG attributes** (`opendraft-dwg/src/attrib.rs`, `opendraft-files/src/dwg/attribute.rs`): an `ATTDEF` is a `Shape::AttributeDefinition` (tag, prompt, modes, lock, field length, its text) and an insert's `ATTRIB`s ride on `Shape::Insert::attributes`, each its tag, modes and a `Shape::Text` placed in the drawing (empty values kept; one under a flipped plane has its place and angle reflected; an entity switched off is read as invisible). They then follow the DXF route above: `block_import` moves them into the block's coordinates and pairs them with definitions by tag. Skipped by name: multiline attributes, and constant `ATTRIB`s on an insert. Only model space and blocks are imported from a DWG, so the attributes of inserts on a layout (a title block's) are not seen; the title block's definitions inside the block table are.
- **Dynamic block slots** (`opendraft-core/src/block/dynamic.rs`; the first step of a staged plan, `private_material/dynamic_blocks_specification.md`, 24-11-2026): the schema and values are data; `block/dynamic_eval.rs` evaluates them (below). `BlockDef::dynamic: Option<Box<DynamicBlock>>` is a block's schema (parameters, actions, value sets, with ids per definition that are never reused) and `Insert::dynamic: Option<Box<DynamicInstanceState>>` the values one insert overrides (only overrides are stored, so an untouched insert has none). Both are `None` until something makes them (nothing authors or saves them yet), so ordinary blocks, and every file, are unchanged. `BlockEntity::id` (`BlockObjectId`) names an object inside its definition, not in the drawing (it is not an `EntityId`), so an action can refer to an object without a list position. It is unique in a block (`validate` refuses a repeat); the importers, BLOCK and paste number objects in order; the Block Editor makes it the object's `EntityId` (`Document::add_with_id`) and BSAVE reads it back, so ids survive an edit, and a new object takes the editor's next id. `.odraft` saves them (below). `Document::block_editor_dynamic` is the schema an editor's drawing is drafting: it is not drawing data (no file holds it, `validate` ignores it, `clone_tables` leaves it, BSAVE turns it into the block's schema), and `SetBlockEditorDynamic` in `opendraft-commands` changes it as one undo step and reports `Changes::dynamic_blocks`. `validate` checks the structure of a schema (`DynamicBlock::check`: the version, ids, an action's parameter and selection; `DocumentError::BadDynamicBlock`) and that an insert has values only when its block has a schema and they are finite and sorted (`BadDynamicState`, `BadInsert`). Pasting an insert whose values the target's block of that name cannot take drops them with `TransferWarning::DynamicStateDropped`. `GripKind::Dynamic` is the grip of a parameter. `Insert::exploded` returns `Piece`s: the objects it makes go into the drawing, where a definition id means nothing. To make room, `document.rs` was split (the queries over a drawing's objects are in `document/queries.rs`) and so was `transplant.rs` (`transplant/merge.rs`).
- **Evaluating a dynamic block** (`block/dynamic_eval.rs`; linear, rotation and flip parameters; Move, Stretch, Scale, Rotate and Flip). A visibility parameter (`Visibility { position, states }`, at most one a block) has named states (`VisibilityState { name, hidden }`, the objects that state hides, sorted); its value is the name of the state shown (`DynamicValue::Text`), the first by default and so not stored, and no action follows it. `evaluate` applies the actions and then drops the hidden objects, whether or not the insert has any state, so every picture, bound, pick and plot follows (`dynamic_visibility.rs`); `Insert::with_visibility_state(name)` changes it, a name no state has is refused and a stored name no state has draws the authored objects. `DynamicBlock::pruned` takes a deleted object off every state. In the Block Editor `BVSTATE` (New, Rename, Delete, List), `BVHIDE` and `BVSHOW` (one state or All) edit the states (`dynamic_visibility_cmd.rs`); Properties shows a drop-down whose edit carries the state's position as its number. A lookup parameter (`Lookup { position, inputs, rows }`, `dynamic_lookup.rs`) is a table: each row (`LookupRow { label, values }`) gives a value to every input, which are linear, rotation or flip parameters. Nothing is stored for it in an insert and nothing in evaluation changes: `Insert::with_choice(parameter, index)` sets the inputs to a row's values, and `Insert::choice(parameter)` gives the choices (the row labels then "Custom") and the row the inputs match now (a reverse lookup), so the Properties drop-down for a visibility parameter and for a lookup is the same code. `check` refuses a table with no inputs or rows, a row with no value for an input or one its value set does not hold, a label that is empty, repeated or "Custom", and two rows with the same values (a reverse lookup could not tell them apart). `BLOOKUPTABLE` edits the rows. An XY parameter (`Xy { base, end, x_set, y_set, y_label }`) and a point parameter (`Point { position }`) have a `Point` value like a polar one: the XY value is the corner (each distance from the base brought into its own set by `fit_end`), the point's is its location. Move and Stretch follow either by the displacement from where it was drawn; Scale, Rotate and Flip do not. Properties shows two rows for each (the two distances, or `Label X` and `Label Y`); `parts_of` and `point_of` turn a point into its two shown numbers and back. A polar parameter (`DynamicParameterKind::Polar { base, end, distance_set, angle_set, angle_label }`) has a `Point` value, its end (the drawn `end` by default), so one value carries a distance and an angle (`DynamicValue::Point`); `DynamicParameter::fit_end` brings it into both sets (the distance into `distance_set`, the angle into `angle_set`, the nearest turn in a list). Move, Stretch and Scale follow it as well as a linear parameter, and Rotate as well as a rotation: Move and Stretch by the end's displacement (times the multiplier, turned by the angle offset), Scale by the ratio of the end's distance from the base to the drawn one about the base, Rotate by the change of angle about the base (`block/dynamic_apply.rs` applies every action). `DynamicActionKind::follows` says which pairs go together. Its grip is on the end; dropping it brings the point into the sets. Properties shows two rows, the distance and the angle (`dynamic_polar`; each is edited keeping the other). The Scale action follows a linear parameter and enlarges its objects, with `Entity::scaled`, about the parameter's start point by the value over the value as drawn (a factor that is not above zero is refused as a bad value); one uniform factor, no separate X and Y. A flip parameter (`DynamicParameterKind::Flip { base, end }`, the mirror line) has a `Bool` value, not flipped by default; the Flip action mirrors its objects about the line with `Entity::mirrored` when it is flipped. Its grip sits at the middle of the line, and dropping it on the left of the line from base to end sets flipped (right of it, not flipped). Properties shows Yes or No. `DynamicParameterKind::family` and `DynamicActionKind::family` say which go together, and `DynamicBlock::check` refuses any other pair. A rotation parameter (`DynamicParameterKind::Rotation { base, radius, value_set }`) has a value in radians that is the turn from the block as drawn (default 0); its value set is in radians, with no set a value is brought into 0 to a full turn, and in a list the nearest angle is the one a shorter turn away (`DynamicParameter::normalize`). The Rotate action turns its objects about the parameter's base point by the value, so the kinds pair: Move and Stretch follow a linear parameter, Rotate a rotation (`DynamicBlock::check` refuses a mismatch, and a rotation without a radius). Its grip sits `radius` from the base at the value's angle from +X; dragging it sets the pointer's angle, normalised. Properties shows the value in degrees (`Insert::dynamic_scale` is 180 over pi for an angle). The native file writes the parameter as `rotation { base, radius, values }` and the action as `rotate { objects }`. `evaluate(block, state)` starts from the authored objects every time and applies the actions in schema order, so it is deterministic and never drifts; an insert with no values borrows the definition's objects. A linear parameter's value is a distance along the line from its start to its end (default: their distance); an action moves by `(value - default) * multiplier` along that line turned by `angle_offset`: Move translates its objects, Stretch calls `Entity::stretched` with the frame (so it cannot disagree with the STRETCH command). It never panics: a schema or state it cannot follow (`DynamicBlockError`) draws the authored objects (`Insert::evaluated`). `Insert::picture`, `exploded`, `bounds` and so every query built on them (painting, picking, snapping, plotting, `Document::insert_pieces`) use the evaluated objects, with layers and ByBlock inheritance unchanged. `DynamicValueSet::normalize` brings a value into its set (list: nearest, lower on a tie; range: clamp, then the increment counted from `min`, never past `max`). `Insert::with_dynamic_value` stores a value (none when it equals the default, so an untouched insert stays `dynamic: None`). `Entity::grips` of an insert adds one `GripKind::Dynamic` grip per parameter that shows one, after the insertion grip, at `start + dir * value` through the insert's transform; dragging it (`Insert::with_dynamic_grip_moved`, reached through `with_grip_moved`) maps the point back through the inverse transform, projects it on the line and normalises it, so non-uniform scale, mirror and rotation hold; a drag that changes nothing is refused. `DynamicBlock::check` also refuses a parameter without a length or with an unusable value set, more than two grips, and an action with a multiplier or angle that is not finite and positive or an empty frame; `check_state` (used by `validate`) refuses a value its parameter's set does not hold (`BadDynamicState`). Not yet: the start grip, authoring, and any dynamic grip drawn differently from a plain one.
- **Saving dynamic blocks** (`opendraft-files/src/native/block_dynamic.rs`, `.odraft`, `CURRENT_VERSION` still 0, no bump). Every block object is written with its `id`; a block with a `dynamic` key carries its schema (`version`, the next parameter and action ids, `parameters`, `actions`; a parameter's kind, an action's kind and a value set are externally tagged objects such as `{"linear": {...}}`, `{"stretch": {...}}`, `{"list": [...]}`), and an insert's `dynamic` key its overridden `values`. Every dynamic structure refuses a field it does not know (`deny_unknown_fields`), so a file from a newer version is refused, not read with data dropped; a schema `version` other than 1 is refused. Lists are bounded while they are read (`limits.rs`: 4096 parameters, actions or values; 65,536 allowed values; a selection is bounded as a block's objects are). Reading refuses, with the block named: a block with some object ids but not all, or none and a schema (a block with no schema and no ids, as in older files, is numbered in order); two objects with one id; a schema `DynamicBlock::check` refuses (including an action naming a missing object or parameter); a stretch frame with its corners the wrong way round; and an insert whose values its block's schema does not allow (`check_state`), also inside a definition. Writing refuses a schema that could not be read back.
- **Authoring dynamic blocks** (`opendraft-app/src/dynamic_block_cmd.rs`, the Block Editor only; ribbon: the Block Editor tab's Dynamic panel, and Reset on the Insert tab). `BPARAMETER` (alias `PARAM`) asks for the type (Linear, Polar, XY, Point, Rotation, Flip, Visibility or Lookup; an XY parameter is asked its base and corner, a point its location; a polar parameter is asked its base and end, the questions below, an angle label and a value set for each of the distance and the angle; a flip is asked the two ends of its mirror line, then the questions below except the value set; a rotation is asked its base point, radius and then the questions below, with its value set typed in degrees) and, for a Linear parameter, its two points, name (default `DistanceN`, unique), label, description, whether the Properties palette shows it, grips (0 or 1) and a value set (None, List, Increment); `BACTION` a Move or Stretch (frame, multiplier, angle offset, name) or a Scale (name only) on a linear parameter, a Rotate (name only) on a rotation, or a Flip (name only) on a flip, with the pickset or a selection (attribute definitions are left out, saying so); `BACTIONSET` replaces an action's objects. Each commits one `SetBlockEditorDynamic`, so it is one undo step of the editor, and checks the schema (`DynamicBlock::check`, which also caps a block at 256 parameters, 1024 actions and 100,000 selected objects in all) before it does. The draft is in the editor's coordinates: `block_editor_document` moves the schema by minus the base point with the geometry, so BSAVE, which puts the base at the origin, needs no second move. BSAVE (`Document::block_edit_save`) drops deleted objects from the actions (`DynamicBlock::pruned`; an action left with none is removed), and every insert rebound to the new definition keeps the values the new schema still allows (`DynamicBlock::fit_state`: a missing or other-typed parameter's value is dropped, a value outside the set is brought into it, a value that becomes the default is not kept). BSAVE says what it did (actions that lost objects or were removed, references adjusted); it does not ask first, because the whole save is one undo step of the drawing. `-BLOCK`/`BLOCK` refuse to redefine a dynamic block. In the Block Editor the schema is painted over the drawing (`opendraft-canvas/src/view/dynamic_overlay.rs`): each parameter as an orange line with end ticks and its name, each action's name, and a stretch's frame. It is painted only: it is no object, so nothing picks, snaps to or plots it, and it goes with the editor. `RESETBLOCK` (drawing only) puts selected dynamic references back to the definition's values in one undo step.
- **Dynamic blocks in DXF** (`opendraft-core/src/block/materialize.rs`, `opendraft-files/src/dxf/mod.rs`). A DXF cannot keep a dynamic block's parameters and actions, so `DxfFormat::write` first calls `Document::materialized_static()`, which returns a copy of the drawing (or `None` when it has no dynamic block) in which every block is static: each reference points at a block holding the objects it draws now. A reference with no values shares the definition's own picture, kept under the definition's name; each other state of a block gets one block of its own, however many references share it (`<name>_1`, `<name>_2`, skipping names the drawing has, ignoring case). Nested blocks are made static innermost first; attributes and object ids are kept. The note says how many dynamic block references (or, when none is placed, dynamic blocks) were written as ordinary blocks. Export never refuses for this and never changes the open drawing; `.odraft` keeps everything. Measured (release, 1,000 references of a 100-object block, each in a state of its own, the worst case): evaluating and bounding them 11 ms, making them static 12 ms (1,001 blocks, 100,100 objects); the ignored test is `block/dynamic_bench.rs`. Not built: AutoCAD's own anonymous `*U` form and the dynamic objects (a DXF AutoCAD opens shows the right picture but is not dynamic).
- **Dynamic blocks in the drawing** (`opendraft-app/src/dynamic_rows.rs`, `opendraft-canvas/src/view/paint.rs`, `entity_paint.rs`). The Properties panel gets a Custom section when every selected object is a reference to one dynamic block: a row for each parameter that shows (`show`), in schema order, with its label, the value in drawing units (the block value times `Insert::dynamic_scale`, the length the parameter's line has after the insert's transform, so scale, mirror and rotation hold), and "Varies" when the references differ. A typed length is divided by that scale and brought into the parameter's value set (a list or range snaps; the field stays numeric, with no drop-down), and one `ModifyEntities` records every changed reference (`AppState::set_dynamic_value`; an unchanged value or a flattened insert is no step). All the panel's edits go through `AppState::apply_property_edit`. A parameter's grip is drawn as a diamond, not a square. A selected or hovered reference is stroked from the same kept pieces as a plain one (`InsertPieces`), so a dynamic block is not evaluated again every frame it is highlighted; the pieces already leave out hidden layers. Picking, snapping, plotting and painting all read `Insert::picture` or `Document::insert_pieces`, which are evaluated, so they follow the values with no case of their own (tests in `opendraft-canvas/src/dynamic_tests.rs` and `block/dynamic_eval_tests.rs`).
- **Not built:** `FIELD` objects in DXF, DWG field import, multiline attributes, Properties rows for attributes, `BATTMAN`, `ATTDISP`, extraction, insert arrays, dynamic blocks beyond the slots and the linear parameter's evaluation; the full list is in `docs/parking_lot.md`, "Blocks, attributes and fields".

## Ellipses (built, baseline)

`Entity::Ellipse(Ellipse)` (`opendraft-core/src/ellipse/`) follows AutoCAD's `ELLIPSE` in this project's structures: centre, major-axis vector, minor-to-major ratio and a counter-clockwise *parameter* interval (the eccentric anomaly, not the angle seen from the centre; `parameter_at_angle` and `angle_at` convert). These five values are the authority; points, outlines, bounds and lengths are worked out from them and never stored or cached.

- **Validity.** `Ellipse::new` is the one place values are checked and made canonical (start in [0, 2π), a full turn is exactly 0 to 2π, ratio in [1e-6, 1], spans of at least 1e-6, coordinates within 1e12). Every transform of a valid ellipse is valid. `Ellipse::validate` is what `Document::validate`, block validation and the file writers call.
- **Derived geometry is bounded.** Nearest point and flattening do a fixed amount of work. Flattening sizes even parameter steps from the bound `a·h²/8` on chord error (a = major radius), so the tolerance is guaranteed, and returns `ResourceLimit` past 8,192 points: the canvas then draws a coarse outline for that frame (`outline`), plotting fails with `PlotError::TooDetailed` rather than plot coarser than asked, and files write the semantic entity and never flatten.
- **Crossings are exact or bounded, never from the outline.** `Curve::Ellipse` takes part in `intersections` and `extended_intersections` like the other curves (its carrier is the whole ellipse), so Trim and Extend use ellipses as edges and targets. A line is met in closed form; a circle, arc or ellipse by bounded root finding on a degree-two trigonometric polynomial (`ellipse/cross.rs`).
- **Fillet of two parallel lines** (`fillet_parallel.rs`) follows AutoCAD: a half circle whose diameter is the gap, whatever the radius; the first line picked stays as it is and the half circle starts at its end nearest the pick; the second line is cut back or extended to end level with it (refused when it lies wholly beyond that end).
- **Fillets and tangent circles** with an ellipse (`fillet_ellipse.rs`) find centres a radius off the ellipse along its normal that are also a radius from the other object, by bounded root finding along the parameter, keeping only centres truly a radius from the whole ellipse.
- **Edits that are not exact are refused, not approximated.** Offset refuses an ellipse by name (its offset is a spline, and fitting one is not built), Chamfer needs lines as in AutoCAD, and a display outline is never used as edit geometry.

## Splines (built, baseline)

`Entity::Spline(Box<Spline>)` (`opendraft-core/src/spline/`) follows AutoCAD's `SPLINE` as a planar NURBS: degree, control points, the full knot vector, optional weights (`None` when all are 1), closed and periodic flags, tolerances and optional fit data. The control frame is the authority; fit data is kept and never refitted on load, draw or save. Boxed because it owns several arrays.

- **Validity.** `Spline::validate` is the one check (counts, finite values within 1e12, non-decreasing knots, multiplicity within the knot tolerance, a domain with length, positive weights in 1e-12..1e12, periodic implies closed, a closed spline's ends meeting, fit data); `new_nurbs`, `from_control_points` and `from_fit_points` call it, and so do `Document::validate`, block validation and both writers. Evaluating a valid spline cannot fail (positive weights keep the denominator positive), so evaluation returns points, not results.
- **Derived geometry is bounded and never stored.** Evaluation by homogeneous De Boor about the first control point; spans become rational Bezier pieces by blossoming (local to the span). Flattening is certified by the hull of each piece (halving until its control points lie within the tolerance of its chord; runs of spans whose control points fit in a box the tolerance wide become one chord) and capped (8,192 points on screen, 65,536 for plots, depth 32), returning `ResourceLimit` past them: the canvas then draws a coarse outline for that frame, plotting fails with `PlotError::TooDetailed`. Length is adaptive Gauss-Kronrod with a work cap; nearest point refines the outline's best stretches. Bounds are the control points' box (safe for culling, not tight).
- **Edits.** Exact transforms of control points, fit points and tangents (any affine map, so uneven block scales stay splines). Grips and Stretch move fit points (refitting) when the spline can be refitted (cubic, open, exact, no tangents), otherwise control points (dropping the fit data). No display outline is ever used as edit geometry (`Entity::curves` gives a spline none, so a spline is never a crossing by accident).
- **Cutting and joining** (`spline/cut.rs`, `spline/join.rs`). `Spline::split_at_parameter` cuts exactly by knot insertion (Boehm, in homogeneous coordinates), so both pieces are the same curve; Break, Break at Point and Trim use it through `Entity::split_at` and `break_between`. A crossing with a spline is found along its flattened segments (`Entity::crossing_curves`, within a ten-thousandth of its size), then the cut takes the nearest parameter; snaps and tangents still see no curves in a spline. `Spline::joined` concatenates splines of one degree that meet end to end, repeating the knot at the join, and JOIN takes a line, an arc or an open polyline onto a spline by turning it into the spline of the run's degree it exactly is (`spline/convert.rs`: a line is a Bézier piece with collinear control points, an arc is rational quadratic Bézier pieces of at most a quarter turn raised to the degree on their homogeneous points, so arcs need degree 2 or more). Extend runs a spline on as a straight tail along its end tangent to the nearest boundary (`spline/lengthen.rs`, shared with LENGTHEN). A periodic spline is not cut.
- **Offset and Fillet of splines** (`offset_fit.rs`, `fillet_spline.rs`). The offset of a spline or an ellipse is not one of its own kind, so `Entity::offset` fits a cubic spline through points of the true parallel curve (`offset_fit`): it starts from 16 samples, checks the middle of every gap against the true offset and adds samples where the fit is more than a hundred-thousandth of the size off (at most 800), so the result stays within that of the true curve; natural ends, so the first and last spans take the most samples. An offset that would fold (distance times curvature reaching 0.98 anywhere) is refused, not trimmed, and an ellipse or an elliptical arc offsets into a spline as AutoCAD does. A fillet between a spline and a line, arc, circle or another spline (`fillet_spline`) finds the arc's centre where the offset curves of the two meet (both sides of each; lines and arcs made whole), makes it exact with Newton's method on the true distances, picks the one whose touching points are nearest the picks, and cuts a spline exactly at its touching point (`split_at_parameter`), keeping the part picked. A spline is never lengthened to meet the arc, so a corner whose touching point lies beyond the end of a spline has no fit; a chamfer still needs lines.
- **SPLINE** (`opendraft-app/src/spline_cmd.rs`) asks and records; `SPLMETHOD`, `SPLKNOTS` and `SPLDEGREE` live in `spline_memory.rs` with the user's settings, like the corner variables.
- **Files.** `.odraft` stores splines in `native/spline.rs`; DXF `SPLINE` read in any group order with declared counts and sizes checked before gathering (`dxf/read/spline.rs`) and written as R2000. The native reader's `serde_json` uses `float_roundtrip` so every value reads back bit for bit. DWG import decodes SPLINE (`opendraft-dwg/src/spline.rs`): a spline stored by its control frame comes in exactly, checked like a file's; one stored by its fit points alone is refitted (cubic; natural ends, or smooth where closed, as AutoCAD does without end tangents), as fit-points-only DXF records are, and skipped by name when it has end tangents or is not cubic.

## Hatches (built, baseline)

`Entity::Hatch(Box<HatchEntity>)` (`opendraft-core/src/hatch/`) follows AutoCAD's `HATCH` (`AcDbHatch`) as a semantic entity: boundary loops (a polyline with bulges, or typed edges: line, circular arc, elliptic arc, spline), an island style (Normal, Outer, Ignore), a fill (pattern, solid or gradient), seed points, loop flag bits kept as read, and the objects each loop was made from. Strokes and areas are worked out by `HatchEntity::evaluate` and never stored. Built from `private_material/hatch_engine_specification.md`; where this differs from it, this is what the code does.

- **Pattern lines are final.** As DXF stores them, each `PatternLine` (angle, base, offset, dashes) already has the pattern's scale, angle and origin applied: the `.pat` step `(delta-x, delta-y)` is turned by the line angle, then scaled and turned with the pattern, and the origin is part of the base. The specification's section 2.7 applies scale and angle again at draw time; doing that to the lines of an AutoCAD file would scale and turn them twice. `HatchPattern::{angle, scale_or_spacing, origin}` are what the user last asked for; `with_scale`, `with_angle` and `with_origin` change them by transforming the lines about the origin, so Properties edits need no pattern file. `PatternCatalog` reads `.pat` text; the built-in catalog is a small starting set in AutoCAD's imperial units (ANGLE, ANSI31, ANSI32, ANSI37, LINE, NET, NET3), not the whole of `acad.pat`.
- **Evaluation works on flattened loops** (`boundary.rs`): arcs, ellipses and splines are followed to a tolerance with the existing flatteners, then the loops are polygons. A loop's depth is how many larger loops contain it (`topology.rs`; winding plays no part); Normal keeps every loop, Outer depths 0 and 1, Ignore depth 0, and the filled area is the even-odd area of the loops kept (outer loops run counter-clockwise and islands clockwise, so non-zero and even-odd agree). A boundary always closes itself, so a two-vertex polyline with bulges 1 and 1 is a whole circle, which is how AutoCAD stores one. Overlapping loops that are not nested are filled by parity, as AutoCAD does for Normal.
- **Pattern lines** (`clip.rs`, `dash.rs`): each family is worked in its own frame (`u` along, `v` across). Edges cross line `k` by a half-open rule, crossings sort and pair; a line along an edge is drawn along it on both sides of a region (checked against ezdxf), and stretches shorter than rounding noise are dropped. Dashes keep their absolute phase (`k * shift` along the line), so a line cut by an island resumes where the uncut one would be. Everything is relative to the middle of the hatch, so far-from-origin drawings keep their precision.
- **Bounded.** `HatchLimits` (100,000 pattern lines as `HPMAXLINES`, 1,000,000 strokes, 4,000,000 crossings; a smaller `preview()` budget) is checked before lines are made, and a family whose line numbers would pass 2^50 is refused; the result is `HatchError::TooDense`, drawn as the boundary with a note, never a hang. `HatchEntity::validate` caps loops (4,096), edges, vertices, pattern lines, dashes, seeds and colour stops, and checks every spline's knot count; `Document::validate`, both file readers and writers call it.
- **Planar.** Only hatches facing +Z are kept (others are skipped by name on import); `elevation` is kept for files. Uneven scaling is refused (`transformed` takes only maps that keep shapes).
- **Associativity** (`hatch/follow.rs`, `opendraft-commands/src/associations.rs`). Each loop remembers the objects it was made from (`BoundarySource::Entity`) and the hatch is flagged `associative` (`HPASSOCIATIVE`, on by default). Transforms keep both. After the edits of a transaction, or of a single action through `Session::perform`, every associative hatch that was edited itself or follows an object that changed or went is checked, and what it needs becomes one more edit in the *same undo step* (`Transaction::finish`, `Session::perform`), so undo restores the hatch before the object and redo changes the object before the hatch. `follow` joins each loop's sources end to end again (the outer loop of a picked-point hatch can instead be traced again from its seed when its sources overshoot each other). If the hatch was not itself edited it takes the new loops, or is detached when the objects no longer close or one is gone; if it was edited, it is left alone when its loops are still the ones its objects make (hatch and boundary moved together) and detached when not (the hatch alone was moved, grips, or copied away). A detached hatch keeps its shape and loses `associative` and its sources. Properties edits and HATCHEDIT keep the association. There is no reverse index: the hatches are scanned after each edit. Not done: a picked-point hatch whose islands' sources change shape is detached unless they still close by themselves; copies of a hatch and its boundary together are detached (not remapped to the copied boundary); the hatch is not selected with its boundary (`PICKSTYLE`).
- **Files.** `.odraft` stores hatch loops, style, fill and sources in `native/hatch.rs` and `hatch_fill.rs`; strokes are never stored. DXF read (`dxf/read/hatch.rs`): read in order with a cursor, because `97` means a fit-point count inside a spline edge and a source count after a loop; counts are checked against the groups that remain and the hatch limits before anything is gathered, with a 8,000,000-group file budget; a clockwise arc or ellipse edge (`73 = 0`) carries its angles as `360 - angle` (ezdxf's `ArcEdge.load_tags` documents this), mirrored on the way in and out; each source handle is resolved to the object that carries it (`Importer::handles`), and an associative hatch that does not match its objects (the sample file has twelve copied away from theirs) is kept without the association; a pattern's origin is recovered for built-in patterns (the first line's base less the definition's origin, scaled and turned), otherwise it reads as (0, 0); a gradient tail with `450 = 0` is dropped and `450 = 1` is kept (name, angle, shift, tint, colours); hatches inside blocks are skipped by name (the block table refuses them: `Document::redefined_blocks`). DXF write (`dxf/write2000/hatch.rs`): R2000, always non-associative with no source handles (the handles the objects will get are not known when a hatch is written; a note says so), groups in AutoCAD's order, counts of what is written, the loop's polyline bit set to match what is written, angles in degrees (the gradient's rotation in radians), a gradient's colours with both `63` and `421`.
- **Canvas.** `opendraft-canvas/src/hatch_cache.rs` keeps what each hatch drew per object; an entry is reused only while the hatch equals the one it was made from (and the tolerance, a power of two, is the same), so edits, undo, redo and another drawing's object that shares an id can never show a stale picture; it holds 512 hatches and 2,000,000 strokes at most, and `View::invalidate_hatches` frees entries early (nothing needs to call it). Solid fills are tessellated with lyon relative to the hatch's middle. Pattern lines closer than 2.5 px on screen are drawn as a tint of the area. A gradient is drawn as its first colour (the other kinds of gradient are not drawn yet). Pick: a click inside a hatch is just inside the pick radius, so it picks the hatch only when nothing nearer is under it; window and crossing selection use the boundary; no snaps; one grip at the middle of its extent moves it.
- **HATCH** (`H`, `BH`; ribbon Home > Draw > Hatch; `opendraft-app/src/hatch_cmd.rs`): an internal point (`Pick internal point or [Pattern/Scale/Angle/Style/Origin/Select objects]`) or objects (preselected, or chosen with Select objects), then the hatch follows the pointer as a preview and Enter or a click accepts it, one undo step, drawn behind the first boundary object in the drawing order (`AddEntity::behind`, as `HPDRAWORDER` 3). `Pattern` takes a name, `SOLID`, `USER` or `?`; `Spacing` and `Double` for user-defined lines; `Associativity` turns `HPASSOCIATIVE` on or off. **HATCHEDIT** (`HE`; ribbon Modify > Edit Hatch; `opendraft-app/src/hatch_edit.rs`) takes the selected hatch or asks for one, fills HATCH's settings from it (restored afterwards), and offers the same options with a preview; it keeps the boundary and the association and does not edit gradients or patterns outside the catalog (use Properties). Circles, rectangles, closed polylines, ellipses and closed splines are loops by themselves; lines, arcs, open polylines, elliptic arcs and open splines are joined end to end, and a chain that does not close is refused with its size. `HPNAME`, `HPANG`, `HPSCALE`, `HPSPACE`, `HPDOUBLE` and `HPISLANDDETECTION` are user settings (`hatch_memory.rs`), with the origin. Properties (`properties/hatch.rs`): fill, island style, angle, scale (or spacing and double), origin, boundaries, associative and area; style, angle, scale, spacing, double and origin can be typed.
- **Pick internal point** (`hatch/trace.rs`, pure and tested): every visible curve of the space being edited is flattened and cut at all crossings into a planar graph (merged within 1e-9 of the drawing's size); a ray to the right finds the nearest edge, and the face on the point's side is walked (at each node the first edge clockwise from the one used), dead ends cancelled. If the ray hit an island first (the walk comes back inside out) that connected group is skipped and the ray goes on. Objects wholly inside the face whose group touches nothing on its boundary become islands (each found by walking the outside of its group); with Normal style they punch holes, Outer and Ignore apply as usual. A loop that is one whole closed object (circle, rectangle, closed polyline, whole ellipse, closed spline) is that object's exact loop; any other loop is a polygon of the flattened pieces (curves followed to 1e-5 of the drawing's size), marked Derived, and the click is kept as the seed point. The hatch goes behind the earliest object of its outer boundary. Not built: gap tolerance, Draw boundary, ray-casting options, detection limited to a boundary set, text as islands. The whole visible drawing is flattened per click (100,000 segments at most).
- **Operations** (specification 4.8): Move, Copy, Rotate, Mirror, uniform Scale, Erase, layer and colour work; Stretch moves a hatch only when the window holds all of it; Trim, Extend, Fillet, Chamfer, Offset, Break, Join and Explode do not apply (a hatch is never an edge); a block cannot hold one; plotting writes a pattern as its strokes and a solid as a fill (a pattern too dense to plot fails with `PlotError::HatchTooDense`).
- **Checked** against `HatchTest.dxf` (`private_material/`, made in AutoCAD: sixteen hatches over a square, a circle, a four-vertex polyline with arcs and a cubic spline edge) and ezdxf: stroke counts and lengths equal ezdxf's own generator (`tests/fixtures/hatch_lengths.py`; the circle's centre line, which ezdxf misses where it passes through two vertices, is checked against the analytic answer), ezdxf audits our export clean (`tests/fixtures/check_hatches.py` after `cargo test -p opendraft-files --test hatch_fixtures`), and every edge kind, style and fill round-trips through both formats. **Not checked in AutoCAD itself:** the prompts, clockwise-edge angles beyond what ezdxf documents, and how AutoCAD draws a pattern line that falls on a boundary.
- **Not built:** Draw boundary, retained boundaries, separate hatches, gap tolerance, exact (not polygon) loops from traced pieces, writing associations to DXF, Reassociate and Recreate Boundary, loop grips, gradients drawn (kept and written, drawn as a flat colour), transparency and background colour, annotative hatches, hatches in blocks, non-XY planes, nonuniform scale, Explode, the rest of `acad.pat`, loading user `.pat` files, DWG import and export of hatches.

## Multileaders (built: the entity, MLEADER and the style table with its dialogs)
`Entity::MLeader(Box<MLeader>)` (`opendraft-core/mleader/`) stores points, text and a copy of what its style said (`look`), and derives everything it draws (`picture`), like a dimension; `Object::dimension_picture` caches the picture for both. Every `Entity` match treats it intentionally: transforms, grips, stretch, hit, selection, snaps, plot and block pictures use the picture; Trim, Extend, Offset, Break, Join, Fillet, Explode leave it alone, and Mirror is refused while text cannot be mirrored. A style change restyles its multileaders in the same undo step (`SetMLeaderStyles` carries the edits). `.odraft` version 1 holds it. DXF reads and writes `MULTILEADER` and `MLEADERSTYLE` in the AutoCAD 2018 layout (the writer picks `AC1021` when a drawing has one); see `docs/history.md`, "Multileaders".
`Document` owns a multileader-style table (`mleader/style.rs`, `document/mleader_styles.rs`) like the text-style table: `MLeaderStyleId` (never reused, counter kept), `Standard` (id 0) always first, unique names ignoring ASCII case, a current style, checked by `validate`. A style holds the values of AutoCAD's three tabs (leader format, structure, content) with typed enums, not codes; ByBlock, annotative, block content and vertical attachment are not representable yet. `SetMLeaderStyles` (`opendraft-commands`) swaps the whole table, current style and counter as one undo step (`Changes::mleader_styles`), as `SetTextStyles` does. `.odraft` writes the whole table, the current style and the counter. `mleader::sample` builds the preview geometry as ordinary entities in `opendraft-core`; the dialogs in `opendraft-app` (`mleader_style_table.rs`, `app/mleader_*.rs`) only draw it. The `Leader` and `MLeader` entities follow `private_material/leader_and_mleader_specification.md`; entities will name their style and keep overrides, not an id.

## Legacy leaders (built: baseline)
`Entity::Leader(Box<Leader>)` (`opendraft-core/leader.rs`) is a polyline with an arrowhead and an optional reference to the MTEXT it annotates, which is a separate object. Like a multileader it is drawn from its stored points (`picture`, cached by `Object::dimension_picture`) and goes through every `Entity` match intentionally. The reference may name an erased text (ids are never reused); the leader does not follow the text. `.odraft` version 2; DXF reads and writes `LEADER` in AutoCAD's layout, joining text by handle after everything is read. See `docs/history.md`, "Legacy leaders".

`Entity::Point { at }` is a bare location. How every point looks is a property of the drawing, not of the object: `Document::point_style()` (`PointStyle { mode, size }`, `opendraft-core/src/point_style.rs`; the `PDMODE` and `PDSIZE` variables, undoable through `SetPointStyle`, saved in `.odraft` as optional `point_mode` and `point_size`, read and written as `$PDMODE` and `$PDSIZE`). `PointStyle::marks` works out the lines, circle and square of a mode at a size; the canvas (`view/point_paint.rs`) and plotting (`plot.rs`, `point_outlines`) draw them, and a size of zero or below is a share of the screen height (the viewport's height when plotted). A point is picked, boxed and snapped (Node) at its location only, has one grip, and moves, rotates, mirrors and scales with it. `.odraft` version 3.

**Modify settings.** What FILLET, CHAMFER, OFFSET and LENGTHEN remember is a property of the drawing, as in AutoCAD: `Document::modify_settings()` (`ModifySettings`, `opendraft-core/src/modify_settings.rs`: `FILLETRAD`, `CHAMFERA` to `CHAMFERD`, `CHAMMODE`, `TRIMMODE`, `OFFSETDIST` and LENGTHEN's last delta). They are not an undo step, as with a system variable: a command changes them through `Editor::change_modify_settings` (`Session::change_modify_settings`: no history, and on its own it does not mark the drawing modified, so a radius typed into an otherwise untouched drawing is saved with the next real edit). `corner_memory::Memory` is the corner commands' view of them, and `modify_vars.rs` holds the variables. `.odraft` always writes them (`native/modify_settings.rs`; a file without them gets the defaults, and a value that cannot be used is put back to its default). DXF reads and writes `$FILLETRAD`, `$CHAMFERA` to `$CHAMFERD` (the angle in degrees) and `$TRIMMODE`; `CHAMMODE`, `OFFSETDIST` and the Lengthen delta are not DXF header variables and stay in `.odraft` only.

`Entity::Xline { origin, direction }` and `Entity::Ray { .. }` (`opendraft-core/src/infinite.rs`) store a base point and a unit direction and have no finite size. Their box (`Entity::bounds`) is open to infinity in the directions they run; the spatial index keeps such boxes in its list of exceptions and tests each like any other, and `Document::bounds`, `model_bounds`, the clipboard, arrays and the render tool leave them out of extents (`Bounds::is_finite`). Where a finite stand-in is needed, `infinite::segment` gives a stretch `REACH` (1e7) either side of the base: `Entity::curves` (so intersections, Trim and Extend boundaries and the snaps that use curves work), selection edges and plotting (solid, cut to the viewport by the frame). The canvas paints only the part inside the window (`view/infinite_paint.rs`), with the linetype laid from the base point. Blocks refuse them. Grips: the base point (moves it) and a point 80 screen pixels along the line, two for a construction line, that turn it about the base (`infinite::set_pixel_size`, set by the canvas each frame, tells them how big a pixel is). Cutting (Trim, Break) and the corner commands work on `Entity::long_line`, the stand-in, and bring the result back through `Entity::resumed` (a piece with one far end is a ray). Properties types the base point and the angle. DXF `XLINE` and `RAY` need R2000. `.odraft` version 3.

## Linetypes (built: the table and dashed drawing and plotting)

`Document` owns a linetype table (`opendraft-core/src/linetype/`, `document/linetypes.rs`), following `private_material/autocad_linetype_reference_guide.md`, which is the compatibility contract.

- **Records.** `Linetype { id, name, description, elements, flags }`: `LinetypeId` (never reused, counter kept), names unique ignoring ASCII case, up to 255 bytes. A pattern is one repeat of `StrokeElement::Dash(len) | Gap(len) | Dot` (lengths above zero and finite; `from_dxf`/`to_dxf` convert DXF group 49). `CONTINUOUS` (id 1), `BYLAYER` (2) and `BYBLOCK` (3) always exist, have no pattern and cannot be changed or removed. A new drawing also has `DASHED`, `DOT`, `DASHDOT`, `CENTER`, `HIDDEN` and `PHANTOM` (ids 4 to 9) so the names layers and objects use already resolve.
- **Stock library** (`linetype/stock.rs`): the 24 families (8 x `x`, `2`, `X2`) in AutoCAD's metric (`acadiso.lin`) numbers and the 14 ISO 128 patterns. The variants are data, not computed (`CENTER2` is not half of `CENTER`); a test holds the imperial numbers apart and checks metric = imperial x 25.4. `LinetypeTable::load_stock(name)` adds one to the drawing; once loaded the drawing owns it.
- **References are ids.** `Layer.linetype` is a `LinetypeId`; an object's, a block object's, the new-object default's and a multileader style's linetype is `Attr<LinetypeId>` (`ByLayer`, `ByBlock` or `Set(id)`). Renaming a record changes one record and every user follows. `BYLAYER` and `BYBLOCK` are not legal references (an object says ByLayer with `Attr::ByLayer`; ByBlock is `Attr::ByBlock`); `Document::validate` refuses them and any id the table lacks (`DocumentError::BadLinetype`). `Document::linetype_uses` is the one list of who holds a reference (layers, the new-object default, objects, block objects including nested blocks, multileader styles) and `linetype_in_use`, PURGE and `validate` all go by it. Names live at the boundaries: the lists in the UI, the command line, DXF export and the `opendraft-api` wire (resolved through the table; an unknown name is an error to the caller).
- **File.** `.odraft` writes `linetypes` (id, name, description, pattern as DXF lengths, flags) and `next_linetype_id` always, in full, so a file does not change meaning if the stock patterns do; a file without them is refused. Loading refuses a table missing or patterning a special record (`LinetypeTable::from_records`).
- **The generator** (`linetype/dash.rs`, pure): `fit(length, closed, elements, scale)` says which stretches of a path are drawn; `dash_path(points, closed, elements, scale)` maps that onto a flattened path (`Piece::Dash(run)` keeps the corners it crosses, `Piece::Dot { at, along }`). Rules from the guide: an open path starts and ends with a dash (a dot-first pattern with a dot), the end dashes take up the slack, a dot-first pattern stretches its gaps, a closed path is stretched to whole repeats so there is no seam, a path shorter than one repeat plus a dash is continuous, and a bad scale or more than 200,000 marks is continuous. **The slack split is our own choice, not AutoCAD's published arithmetic: lock it down with AutoCAD-made fixtures.**
- **Which curves** (`linetype/paths.rs`): `is_dashable` (line, circle, arc, ellipse, spline, rectangle, polyline) and `curve_outlines(entity, tolerance)`, the flattening plotting already used (a circle starts at angle 0). Text, hatches, dimensions and block references are not dashed as a whole.
- **Which pattern an object uses:** `Document::dash_pattern(object)` = its resolved linetype name looked up in the table; the scale is the object's own `Attributes::linetype_scale` times the drawing's `LTSCALE` (`Document::linetype_scale`, undoable through `SetLinetypeScale` and the `LTSCALE` variable, saved in `.odraft` and read and written as `$LTSCALE`).
- **Canvas** (`opendraft-canvas/src/view/dash_paint.rs`): the entity is flattened to half a pixel, dashed, and each dash stroked; the selection glow follows the dashes. A pattern whose repeat is under 6 px on screen (`MIN_REPEAT_PX`: 10,000 dashed objects in view cost 41 ms at a 4 px repeat, 26 ms at 7 px, 8 ms solid), or a path needing over 20,000 dashes, is drawn solid: a view-only choice that never reaches the file or a plot.
- **Plot** (`plot.rs`, `dashed_outlines`): outlines are dashed in the units they are made in (model units for a viewport, so its scale applies to the dashes; millimetres on the sheet), then clipped. A dot is a hair of line that the writers' round caps make a dot.
- **Scale and generation live on `Attributes`** (`linetype_scale`, default 1, above zero; `continuous_generation`, default false), not on the polyline entity, so no entity variant changed. Linetype Generation applies to polylines and rectangles: off (AutoCAD's default) lays the pattern afresh on every segment (`curve_outlines(.., per_segment = true)`), on lays it along the whole outline. Properties' General section has Linetype scale (typed) and, when a polyline or rectangle is selected, Linetype generation. `.odraft` writes both as optional fields on objects and block objects (flattened `ScaleDto`) and `LTSCALE` beside the table; DXF reads and writes group 48, bit 128 of group 70 on polylines, and `$LTSCALE` (R12 and R2000).
- **File patterns** (`linetype_import.rs` is shared by the DXF and DWG readers; `dxf/read/ltype.rs`, `dxf/linetypes.rs`): each LTYPE record (groups 2, 3, 49 in order) becomes or replaces a record of the table, so the file's numbers are what is drawn: an imperial `DASHED` from an `acad.lin` drawing replaces our metric one and keeps its id. The three special records are ignored. A definition with text or shapes (group 74 not 0) is read as its dashes and reported. Each name a layer or object uses is turned into a record id as it is met (`Imported::id_for`): the record of that name, or a placeholder record with the file's spelling that a later definition replaces keeping its id; at the end a placeholder still undefined gets the stock pattern if there is one, and is reported, else stays a record with no pattern (drawn solid) and is reported, so no reference points at nothing and the name is kept; a bad dash length skips that record. Both writers define every record of the table (not only those in use), from the table, under the record's own name (the old `Dotted` is written as `DOT`); the made-up imperial patterns are gone. Checked with ezdxf (reads R12 and R2000 output, audit clean) and with `private_material/Linetypes.dxf` and `Linetypes.dwg`, made in AutoCAD from `acad.lin` (`tests/linetype_fixtures.rs`: the 24 families' numbers match our imperial table exactly, the DXF and the DWG give the same table and descriptions, the two complex ones read as dashes and are reported).
- **DWG patterns** (`opendraft-dwg/src/tables.rs`, `read_linetype`; §20.4.58): after the name come the xref index (BS), then the description (strings stream), the pattern length (BD), the alignment (RC, always `A`; anything else leaves the name alone), the dash count (RC) and each dash's length (BD), shape code (BS), x and y offsets (RD), scale and rotation (BD) and shape flag (BS; non-zero marks a complex dash). The spec's 64-flag and Xdep bits are not in AC1032 drawings. A pattern that does not decode keeps the name. The entity's own linetype scale and the header `LTSCALE` come across too.
- **Between drawings** (`document/transplant.rs`, `Document::absorb`): paste, paste as block and block insertion map the source's linetype ids to this drawing's as they copy (`Merge::linetype`): the three special records are the same everywhere; a record of the same name (ignoring case) in this drawing is used, and one with another pattern (compared by its dash/gap/dot elements) is reported once per name, this drawing's winning, as AutoCAD does; an absent one is copied in under a fresh id; an id the source does not resolve is drawn continuous and reported. The map is total, so a transfer cannot fail halfway; `Absorbed::warnings` carries the reports and `PasteDrawing::reporting` hands them to the app, which says them on the command line. An id is never copied between drawings raw. `Document::bring_block` (`transplant/library.rs`) is the other way in, for the Content Manager: it copies one block and the blocks it contains with the same merging, but the caller decides, for each source block whose name the target has, between using the target's block and adding the copy as `Name_2` (`block_clashes` lists them first), where a paste always uses the target's. A third choice, `Replace`, gives the target's block the source's definition (`redefined_blocks`: it keeps its id and name, every block and object that holds it follows, inserts keep their attribute values); a replacement that would hold itself is refused with the drawing as it was. `insert_from` brings the block and adds a reference in one call, and `unbring`/`unplace`/`replace_placed` undo and redo it exactly (`opendraft-commands::InsertFromLibrary` is the one undo step). `Library::import` copies the ticked blocks of a loaded drawing into a folder in one write (each block on its own rollback, so one that fails is reported and the rest go on); `importable` lists a file's blocks without the anonymous `*` ones. The Content Manager window (`opendraft-app/src/content_manager/`) is modeless and holds its state in `CommandDialogs::content`; each frame it takes a `Snapshot` of the library and the drawing, draws from that, and collects `Action`s that are carried out after drawing, so drawing code never changes the library. What it needs the app to start (LIBINSERT on a chosen block, LIBADD, renaming a block of the drawing) comes back as `Request`s; a drawing block is renamed by `AppState::rename_block` (`block_rename.rs`) in one undo step from `Document::renamed_block`, which checks the name (valid, not another block's ignoring case; a change of case is allowed) and repoints every insert through `redefined_blocks`, so inserts keep their attribute and dynamic values; nothing else in the drawing names a block (dimension arrows are built-in shapes, multileaders have no block content), and the answer goes back to the window by `Window::drawing_block_renamed`, which keeps the thumbnails (no picture shows a name). A block, of the library or of the drawing, is renamed in place in its details: a pencil beside its name turns it into a field (`name_edit.rs`); the bar above the tiles is for folders. A drawing block's unit has its own pencil, which opens the list of units (`unit_menu.rs`); `AppState::set_block_unit` records the choice in one undo step from `Document::block_in_unit`, and the inserts already placed keep their size, since the unit only scales a block when it is inserted; LIBINSERT is told the block by `LibraryHandle::queue_pick`. Block pictures are made on the UI thread, four a frame, by the canvas's CPU rasteriser (`purge_cmd::block_picture`) and kept as textures until the library's `stamp` or the drawing's revision changes. The app reaches the user's library through `content_library::LibraryHandle` in `CommandDefaults`, opened on first use in the folder of `Location::Library`; `LIBADD` copies a drawing's block (or the selected objects made into a scratch block, so the drawing is untouched) in, and `LIBINSERT` places one with INSERT's prompts, asking only when the drawing already has a block of a name the library block (or one it holds) has. Search is scoped to where the user is: in My blocks it searches the whole library (the folders are hidden and the result is titled as a search), in This drawing and the Trash it narrows that list by name, and in Favourites and Recent it narrows that list by the library's search and filters (`Snapshot::narrowed`; the tree's counts are not narrowed). The window's own controls (`content_manager/chrome.rs`: icon buttons, joined choices, tree rows; `list.rs`: list columns and the empty state) light what is chosen in a neutral tone, and the icons are the `CONTENT_*` ones. Two rules from getting it wrong: the window sizes itself to its contents, so nothing in it may take a width from a grid's first frame (a field given no width wraps a letter to a line and the window grows for good: the details fields are given a width worked out before they are drawn), and padding goes on a panel's `frame`, not in a frame inside a filling `ScrollArea`.
- **UI** (`opendraft-app/src/linetype_ui.rs`, `app/linetype_dialog.rs`): the linetype lists in Properties and in the Layers panel come from the table (`CONTINUOUS` and the named records; `BYLAYER` and `BYBLOCK` are not linetypes) and show a picture of each pattern at a size that suits any units (`paint_sample`, using `dash::fit`); `opendraft_ui::menu::list_menu_sampled` and `combo_sampled` draw the picture at the right of a row. `LINETYPE` (aliases `LT`, `LTYPE`, `DDLTYPE`; Manage > Drawing > Linetypes) opens the Linetype Manager: a list with picture and description, Load from the stock library or a `.lin` file (see below), Delete (refused for the three built in and for any linetype in use, `Document::linetype_in_use`), and the global scale factor. It edits a draft and OK commits table and `LTSCALE` as one undo step (`SetLinetypes`).
- **`.lin` parser** (`linetype/lin.rs`, pure text in, no files): `lin::parse(text)` returns a `LinFile` of `LinEntry` (name, description cut to 47 characters, elements, and whether text or shape elements were dropped) and `LinNote`s (line, name, message, skipped or kept). Grammar from the guide's section 4: `*NAME[,description]` then `A,len,...`, `;` comments, a BOM and CRLF accepted, `A` in either case. A bad entry is skipped and reported while the rest still read: a pattern that fails `lin::pattern_problem` (2 to 12 elements, the first not a gap; `Linetype::lin_problem` uses the same check), a length that is not a finite number, an alignment other than `A`, a header with no pattern line or a pattern line with no header, an empty or over-long name, `CONTINUOUS`, `BYLAYER` or `BYBLOCK`, and a name already read (ignoring case; the first is kept). A complex entry (`["GAS",STANDARD,...]`, quoted strings may hold brackets and commas) is read as its dashes and reported, as a DXF import does. A file is not always UTF-8 (`acadiso.lin` has Shift-JIS spaces in the JIS descriptions), so the caller reads bytes and decodes them leniently; `parse` takes text. The Manager's Load window (`app/linetype_dialog/load.rs`, "Load or Reload Linetypes") shows its source (the stock library, or a file picked with the File button through `FilePicker::open_file`, read as bytes and parsed with `lin::parse_bytes`), a list with a picture and description of each definition, and a note of what the file held that could not be read (the reasons are in its tooltip) and how many had text or shapes that are drawn as plain dashes. A definition the draft table has with the same pattern is marked loaded; one with another pattern is offered as a replacement (`LinetypeTable::load_definition`: the record keeps its id and its own spelling, so objects follow, and the three special records are refused; `would_change` says which). OK loads what is ticked into the draft and says how many were added and replaced on the status bar; the Manager's own OK still commits everything as one undo step. The example `opendraft-core/examples/lin_check.rs` runs it over the `.lin` files in `private_material/` when present.
- **`-LINETYPE`** (`linetype_line.rs`; aliases `-LT`, `-LTYPE`, French `-TYPELIGNE`): the command-line form, asking `[?/Create/Load/Set]`. `Load` asks for the linetype names (comma separated, `*` and `?` wildcards, ignoring case) and then for a `.lin` file's path typed as text (quotes are ignored; there is no file dialog and no default file), parses it with `lin::parse_bytes`, says what could not be read, and asks "Reload it?" (default Yes) for each name the drawing has with another pattern or description; a name it has identically is only said. What is taken is one undo step (`SetLinetypes`). `?` lists the names and descriptions in a file without changing the drawing. `Create` and `Set` say they are not built. The command reads a path the user types, so it is `Denied` to outside callers (`automation/policy.rs`, `FileRead`).
- **Not built yet:** `-LINETYPE` Create and Set and a file dialog or default file for its Load, Rename in the Manager, `CELTSCALE` and `PLINEGEN` as defaults for new objects (new ones are scale 1 and generation off), DWG linetype generation of a polyline (its flag is not decoded), complex (text/shape) elements kept for round trip (they are read as dashes), dashes on block contents, dimensions and hatch outlines (insert pieces and dimensions are drawn solid), and ByBlock in the DXF and DWG layer and style tables (see `docs/parking_lot.md`).

## Spatial index (built)

`Document` keeps an R-tree (`rstar`, kept inside `opendraft-core/src/spatial_index.rs`)
per space (model space and each sheet) over `Object::bounds()`, so asking what
is near a point or inside a rectangle costs what is found, not the size of the
drawing. It is derived state: private to `Document`, ignored by `PartialEq`,
never saved, cloned with the document.
- **Queries** (`document/spatial_query.rs`): `objects_intersecting(space, rect)`
  and the filtered `visible_in_rect` / `selectable_in_rect` (the caller passes
  the viewport's frozen layers) with `visible_here_in_rect` and
  `selectable_here_in_rect` for the space being edited. They return what a scan
  of the space would, in draw order (the tree holds ids, sorted back by current
  position), so exact code (`pick`, `snap`, `select`, painting) is unchanged and
  only given fewer objects. Layer state is never in the index: it is applied
  after. `Document::bounds` stays a filtered scan (the tree root is not a
  visible extent).
- **When it is used** (`document/spatial.rs`): a space gets a tree at 4,096
  objects and loses it below 3,072; below that, and for a rectangle that is
  invalid or covers the whole tree, a query is a scan. An object whose box is
  not finite (`NaN`, infinite, reversed) is kept in a side list tested with
  `Bounds::intersects`, so it behaves as in a scan.
- **Kept current by `Document` itself**: `push`, `insert*`, `remove*`,
  `replace*` update it; a change of many objects (at least 256 and 10% of the
  space) rebuilds the space once instead. A mismatch found on the way (a failed
  removal) rebuilds the space; one found by a query is an assertion in debug
  builds and a scan in release. File readers call `begin_bulk_load` and
  `finish_bulk_load` so the tree is built once at the end (queries scan
  meanwhile).
- **Consumers**: painting (`visible_in_rect`), `pick_here`, snapping and
  `select_in` in `opendraft-canvas`. Use these rather than iterating
  `selectable_objects()` for anything run on every frame or mouse move.
- **Checks**: `document/spatial_tests.rs` and `spatial_edit_tests.rs` run
  random edits (every mutation path, three spaces, bad boxes) against a scan with
  an invariant check; debug builds also compare one query in 1,024 with a scan
  (`set_verify_all_queries` checks all); `opendraft-canvas/src/indexed_tests.rs`
  compares pick, snap and region selection. `cargo run --release -p opendraft-core
  --example bench_index` measures it.

## Picture cache (dimensions built)

A stored dimension's picture (the lines, arrows and `MText` text it draws) is a
function of its entity, so `Object::dimension_picture()` remembers it like
`Object::bounds()`: one build, shared by painting, picking, snapping, selecting,
plotting and DXF export, forgotten when `Document::replace` changes the entity,
ignored by equality. Code that has an `Object` asks it; code with only a
detached `Dimension` (previews, tests) uses `Dimension::picture`. Block
references are not cached (see `docs/history.md`, "Picture cache").

## Entity layer cache (built; the detail controls are not)

Painting is immediate-mode, so a drawing of hundreds of thousands of entities cost
tens of milliseconds a frame even when only the pointer moved. `opendraft-canvas`
(`layer_cache/`, `view/entity_paint.rs`) keeps the plain entities (neither selected nor
hovered) of the space being edited as tessellated egui meshes and draws those instead;
selected and hovered entities are painted live over them, as AutoCAD draws highlights.
- **Used only when told**: the app gives each view `Session::draw_token()` (session id,
  unique in the process, plus the revision, which moves on every edit, undo, redo and
  viewport pan) with `View::set_document_token`. Without a token nothing is kept, so any
  other caller of `View::show` paints as before.
- **Key** (`layer_cache/key.rs`): token, space, frozen layers, camera, canvas and clip
  rectangles, line colour, point style, the hidden entity, display scale and egui's
  tessellation options, compared as exact bits. The audit of what plain painting reads is
  in `layer_cache/mod.rs`; a new input to painting must be added to the key.
- **Chunks** (`layer_cache/chunks.rs`): the plain entities are kept in chunks, each a fixed
  range of 2,048 objects of the drawing's object list (so an object's chunk is its position
  divided by 2,048, and a chunk can be made again alone from `objects()[n * 2048..]`, keeping
  those that show through the view). A chunk holding a selected or hovered entity is drawn from a variant made without
  it (kept while the highlight stays, dropped when it goes), and the highlight is drawn live
  over the layer, so nothing sits under it. Hovering therefore remakes one small chunk, not
  the layer. Variants count against the memory limit; one that does not fit is not kept and
  the chunk is drawn whole, as without a variant.
- **Capture**: a chunk's entities are painted through the normal code into a scratch egui
  layer, taken out, tessellated once with `epaint::Tessellator` and kept as `Arc<Mesh>`.
  Small text is drawn as textures held in the picture cache of `text_raster.rs`; the layer
  holds those handles so the cache evicting one cannot free a texture it still points at.
- **Settings** (`CacheConfig`, `View::set_cache_config`): mode Automatic (drawings of
  5,000 objects or more), On or Off, motion Exact, Smooth or Automatic with a settle delay
  (0 to 500 ms), and a memory limit (default 512 MB, 64 MB to 2 GB); a
  layer over the limit is not kept and is painted directly. They are the user's, on the
  Performance page of Settings (`performance_settings.rs`, saved with `Settings`, never in a
  drawing); the panel passes them to each view every frame. An optional readout over the
  canvas (`frame_readout.rs`, off by default, nothing timed while off) shows the paint time,
  the frame time, the cache's size, builds, chunk rebuilds and frames, and the object count.
- **Checks**: in debug builds a kept layer is compared with a fresh one every 256th frame
  it is drawn (every frame in tests) and a difference is an assertion; the tests also show
  the kept picture equals the directly painted one, that each key input rebuilds it, and
  that a pointer-only frame builds nothing.
- **Pan and zoom** (`layer_cache/moved.rs`, `pending.rs`, `view/layer_paint.rs`): the key has
  a content part (drawing, space, canvas, colours, ...) and a view part (the camera). When
  only the view differs and the motion setting allows (Smooth, or Automatic when the last
  layer took over 24 ms to make), the old layer is drawn moved (egui's `transform_range`, with
  the clip rectangles put back) and the new one is made a slice of chunks a frame (8 ms) once
  the view has stood still for the settle delay (50 ms); moving again starts it over, and
  when done it replaces the old one. Anything in the content part changing (an edit, a
  resize, a colour) still makes the new layer at once, because an old picture would show
  what is no longer there. If the old and the new together would pass the memory limit, the
  new is made at once. Exact motion makes a new layer every frame, as before.
- **Slots** (`layer_cache/slots.rs`): each place the drawing is painted has its own kept
  layer: the model tab, each viewport of a sheet (with that viewport's frozen layers left
  out) and the sheet's own objects. They share the memory limit (a slot may use what the
  others leave) and the 8 ms slice of a frame, and a slot not painted for 600 passes is let
  go. A viewport's clip rectangle is part of the key's view, not its content, because it moves
  with the sheet, so zooming or panning the sheet moves every viewport's picture.
- **Image mode** (`layer_cache/raster.rs`, `bitmap.rs`, `view/image_paint.rs`; `Render::Image`, the
  default): once a layer's triangles are made they are drawn into an image by a software
  rasteriser (the triangles egui would draw, with their soft edges as the anti-aliasing, blended
  as egui blends: premultiplied, "over", in gamma space; tiles shared by up to eight threads, the
  same result for any number), shown as one rectangle in a frame, and let go, so a layer costs
  the screen's pixels in memory and a frame costs one rectangle whatever the drawing holds. A
  pan or zoom moves the rectangle while a new one is made. What cannot be drawn flat (small text
  pictures) stays as triangles over the image. Selected and hovered entities are drawn over the
  image, not in place of what they cover (no chunk variants are made); a large selection has an
  image of its own. `Render::Triangles` keeps the triangles and draws them as before; a change of
  setting makes the layer again. Debug builds compare the image with a fresh one like the chunks.
  Each row of a triangle is drawn only between where its edges cross it (widened by two pixels,
  the exact test deciding them), not across its whole box, which for a slanted line is mostly empty.
  The meshes are cut into one run per thread, each readied and sorted into tiles on its thread,
  and a tile draws the runs in order, so the picture is the same for any number of threads.
  An image reaches past each side of the canvas by a tenth of it (`IMAGE_MARGIN`; the `Frame`
  carries the wider rectangle and clip, centred so the camera's mapping is unchanged), so a pan
  shows drawing, not a blank strip, until the new picture comes; whether an old picture covers
  enough of the screen to be shown moved counts the margin.
- **Background pictures** (`view/builder.rs`, `view/background.rs`): when the app shares the
  drawing (`View::set_shared_document`, a `Weak` of `Session::shared_document`) and the layer is
  kept as an image, a new picture for a moved view is made on a thread of its own, at once (no
  settle delay), while the old one is shown moved; Automatic motion then always shows it moved.
  The thread keeps its own `View` (so its hatch and block reference caches stay warm) and paints
  on an egui context of its own, because a context's shapes are taken by the frame that ends
  next; the triangles are made with the screen context's tessellator (`Tess`), small text
  pictures are loaded into the screen's context (`text_raster::load_into`), and so is the image,
  which is all that comes back. Only the newest picture asked for each slot is made; one being
  made is finished, so a pan that never stands still still gets new pictures, and one that comes
  back for a view other than the current one is kept if it shows the same content. A picture
  that needed egui's fonts (a hatch's "not drawn" note: its glyphs are in the other context's
  atlas) comes back empty and that content is made on the screen's thread from then on, as is a
  picture whose job panicked. Edits, the first picture and a zoom out too far to show moved are
  still made at once on the screen's thread. `Session` keeps the drawing as `Arc<Document>`
  and edits through `Arc::make_mut`: the view holds it weakly, so an edit copies the drawing
  (about 34 ms for 417,000 objects) only when it lands while a picture is being made from it.
- **Outlines through egui** (`view/path_stroke.rs`): the outlines of polylines, arcs, ellipses,
  splines, dashes and hatch boundaries are stroked through `stroke_path`, which drops points within
  0.05 px of the one before and cuts a path where it turns back on itself (within about a degree),
  stroking each part alone. egui joins segments by averaging their sides; at a reversal that average
  is rounding noise and the join's corner can land anywhere, even at infinity: a streak across the
  view that is not in the drawing, cannot be picked and comes and goes with the view.
- **Wheel zoom**: a notch zooms at once (`raw_scroll_delta`), as AutoCAD does, not over egui's
  smoothed delta, which creeps on for about 170 ms and so held back the settle delay and the
  sharp picture.
- **Large selections** (`layer_cache/selected.rs`): a selection of 256 or more objects has its
  highlight kept as triangles too, under a key of the layer key, a hash of the selected ids and
  the two highlight colours, made again only when one of those changes; the exclusion lists are
  kept by the same hash and the hovered entity. A hovered entity, a small selection and any
  highlight while an old picture is shown moved are still drawn live. Over the memory limit the
  highlight is drawn live. The debug check compares it with a fresh one like the chunks.
- **Not yet**: a pan faster than the margin per picture still shows a blank strip for a
  moment; kept triangles (`Render::Triangles`) are still made here, a slice a frame.
  Highlights are drawn live and over everything, so a very large selection (hundreds of
  thousands) is as slow as it was.

## Geometry in `opendraft-core` (built)

Modify commands are thin: the maths is pure, tested, and lives in `opendraft-core`,
the command only asks, calls it and records a transaction. Modules:
`arc` (circular arcs, CCW radians), `ellipse` (ellipses and elliptical
arcs, see "Ellipses"), `spline` (NURBS curves, see "Splines"), `bulge` (polyline arc segments),
`intersect` (`Curve::{Segment,Circle,Arc,Ellipse}`, crossings, nearest point),
`split` (Trim/Break), `extend`, `offset`, `corner` and `fillet` (two-curve
corners; `Chamfer::{Distances,Angle}`), `polycorner` (rounding a whole
polyline; its widths are kept, and a fillet next to an arc segment is found through the fillet of the two segments), `corner_polyline` (the two other ways FILLET and CHAMFER meet a polyline: two segments of one polyline with exactly one segment between them, which goes, two parallel ones getting the half circle, `join_apart_segments`; and a line or arc with the end segment of an open polyline, which become one polyline, `join_to_end_segment`. Both work out the corner on the segments as lines and arcs and chain the pieces back with `join`; each polyline segment keeps the side away from the corner whatever was clicked, except that two parallel segments are joined at the end beside the segment that goes. A wide segment is refused rather than losing its width), `grip` (`Entity::grips`, `with_grip_moved`), `join`
(`join(&[Entity], tol) -> Vec<Merged>`), `polygon` (regular polygons about a
centre or on an edge, for POLYGON), `array` (where array items go:
`Placement`s and a measured `Path`) and `transform`.

- **Polyline arcs:** `Entity::Polyline { points, closed, bulges, widths }`; `bulges`
  is empty or one per point, `bulges[i]` shapes the segment from point `i` to
  the next (the closing one for the last point of a closed polyline). Bulge =
  tan(angle/4), positive CCW, 1 = half circle; mirroring flips signs. Anything
  that reads a polyline must go through `bulge::*`, never assume straight
  segments.
- **Polyline widths:** `widths` is empty or one `(start, end)` pair per point,
  indexed like `bulges` (the width of that segment at its start and end, tapering
  between). `width::at` reads it and `width::triangles` gives the area to fill,
  which the canvas paints in the stroke colour; the centreline is still what is
  snapped to, picked and gripped. Moving, turning, mirroring, scaling (widths
  scale), stretching, grip editing and Extend keep the widths. Anything that
  cuts or joins segments (Trim, Break, Join, Offset, Fillet, Chamfer, Explode)
  produces a hairline polyline: those do not carry widths yet.
- **Building shapes from the command's options** is pure geometry in
  `opendraft-core`, tested there: `arc_make` (an arc from start, centre, end, included
  angle, chord, radius or direction), `tangent` (the circle tangent to two
  objects with a radius, scored by where it really touches, the far side of a
  circle it holds; with a spline, `tangent_spline` takes the steps described
  below for `tangent_three_curves`, in the centre alone), `tangent_three` (the circle tangent to three lines,
  circles or arcs, for the ribbon's Circle Tan, Tan, Tan: Apollonius' problem
  solved exactly for each choice of sides, in coordinates scaled to the picks
  so it holds far from the origin; of up to eight circles, the one touching
  nearest the picks, never a picked circle itself; with an ellipse or a
  spline, `tangent_three_curves` stands in for each by its circle of
  curvature, or its tangent line, at the pick, solves that exactly, then
  corrects each answer by Newton steps until it touches the real curves,
  an elliptical arc counting as its whole ellipse and a spline only as
  itself) and `rect` (a rectangle at an angle with rounded or
  bevelled corners and a width, as a plain `Rectangle` when it can be; also
  placed from its centre, `rect::centred`, or by three points,
  `rect::by_three_points`) and `oblong` (a slot: two half circles of the
  same radius joined by straight sides, as a closed polyline of four
  vertices, from the centres of its ends and its width).
- **Rectangle and oblong types.** The Draw panel's Rectangle list also has
  Rectangle, Center (`draw.rectangle_center`, alias RC), Rectangle, 3-Point
  (`draw.rectangle_3p`, R3), Oblong, Center (`draw.oblong_center`, OC) and
  Oblong, 2-Point (`draw.oblong_2p`, O2); AutoCAD has none of them. The two
  rectangles take RECTANGLE's remembered corners and line width and its
  Chamfer/Fillet/Width options at their first prompt; from the centre, Area,
  Dimensions (full sizes) and Rotation (about the centre) work as in
  RECTANGLE, and dynamic input shows the full width and height
  (`DynamicDimensions::Centred`: X and Y are twice the pointer's offset). By three points, the third is a point on the opposite side or a
  typed height (positive on the left of the first side). An oblong is given
  by the centres of its two ends (or its centre and one end's centre, the
  other end mirrored), then its width, typed or as a point on a side. Oblongs
  are hairline and take no options.
- **Results are lists of entities.** A trim, split or join returns the
  entities that replace the old one; the first keeps the object's id and draw
  order, the rest are new objects with the same attributes.
- **Randomized tests** check invariants (crossings lie on both curves, cutting
  keeps total length) rather than only examples; keep doing that for new
  geometry.

## Automation and MCP (reads, atomic writes, measuring, rendering, commands, files, interactive commands, selection requests and events built)
Spec: `private_material/mcp_server_specification.md`. An AI client talks MCP to the `opendraft-mcp` sidecar, which talks to the running app over a local socket; the app answers on the UI thread.
- **Boundary.** `opendraft-app/src/automation/`: `core.rs` (the automation core: the grants, the bounded queue of requests, `poll` once per frame, and `execute`, the one place a request is checked and run), `host.rs` (the local socket in front of the core: listener, descriptor, a thread per connection), `connection.rs` (one socket client: token handshake, then framed requests with a deadline), `read.rs` and `query.rs` (the operations, pure functions over `AppState`, so they are tested without IPC), `settings_page.rs`. Connection threads never touch `AppState`; a request abandoned by its caller is dropped before it runs.
- **Transport.** Named pipe `od-<instance>` on Windows, a Unix socket beside the descriptor on Linux (Linux untested). Each run writes `<instance>.json` (endpoint, pid, a 256-bit token) into `%LOCALAPPDATA%\OpenDraft\automation` (`$XDG_RUNTIME_DIR/OpenDraft/automation`; `OPENDRAFT_AUTOMATION_DIR` overrides it for both programs); a clean exit removes it and the next start sweeps ones nothing answers on. The token is checked in constant time, never logged, never shown to a model (`opendraft_instances_list` omits it). The pipe is not ACL-restricted beyond Windows defaults, so the token is what keeps other users out; anything running as the same user can read the file, so the real safety boundary is the grant. A connection has ten seconds (`HANDSHAKE_TIMEOUT`) to send its hello, polled in non-blocking mode because a Windows named pipe has no read timeout (and reports an empty read as end of stream, so there a client that has gone is noticed at the deadline); one that stays silent is dropped, so idle local connections cannot fill the eight slots.
- **Grants.** Each connection gets a grant when it authenticates: `drawing.read` only. The user ticks Allow changes for a connection in Settings > Automation to add `drawing.write` and `ui.selection` (the one `selection.set` and `selection.request` need; takes effect on its next request, and unticking stops it at once); `history.any` is never offered yet. The setting `automation_enabled` (saved) is off by default; `OPENDRAFT_AUTOMATION=1` turns the endpoint on for one run without saving (it does not grant writes). A connection checks the grant before queueing (`Link::submit`: API version, a known operation, the declared scope equal to the one the operation needs, the grant holding it) and `AutomationCore::execute` checks it again when the request runs, against the grant as it is then and **by the scope the operation needs, never the one the request declares**. The scope-equals-operation rule was once only the socket layer's; any new way of getting a request to the UI thread must not be able to skip it, so it is enforced where requests run. `core_tests.rs` builds a request that claims the wrong scope and shows it is refused.
- **Ids and revisions.** Every id is a decimal string. A drawing's wire id is `doc_<instance>_<uid>` (`Doc::uid`, never a tab index). `Session::revision()` moves on every effective edit, undo and redo (never back); every read result carries it and a paging cursor is bound to it and to its filters (stale or foreign cursors are refused).
- **Block Editor.** While BEDIT has a drawing, `doc.session` is the temporary block. Every per-document operation on that drawing returns `block_editor_open` (retryable, no retry delay, so a client must not poll); `documents.list` shows only `available: false`.
- **Writes.** `entities.apply_batch` (`mutate.rs`), `layers.apply_batch` (`layer_mutate.rs`), `selection.set` and `history.undo`/`redo` (`ui_mutate.rs`). Each goes through `guard::open_for_change`: the drawing must exist and not be in the Block Editor, no command may be running in it (`command_busy`, never cancelled for the caller), and `expected_revision` must match (`stale_revision`; there is no force). Targets, references and limits are checked before the first edit; the edits then run in `Session::checked_transaction`, which validates the whole drawing in every build before recording and reverts if it is invalid, so a failed batch leaves no trace and no revision. A successful batch is one undo step named by the caller's label, recorded with `Provenance::Automation(grant)`; a batch that changes nothing records nothing. A full `validate()` costs 0.8 ms on the 8,741-object Pipe Fittings model (linear), so no incremental validator. Wire geometry is built by `opendraft-api::convert`, one set of rules for add, replace and patch (finite numbers, positive radii, polyline arrays that match, `Ellipse::new`, `MText::validate`, layers, linetypes, lineweights and text styles that exist). Writable kinds: line, circle, arc, rectangle, polyline, ellipse, mtext and hatch; the rest are read-only (`unsupported_entity_write`). A replace that changes kind is refused while an associative hatch follows the entity; hatches follow same-kind edits in the same step. Undo and redo need the step token and may only touch steps made by the same grant (a restarted sidecar is a new grant) unless `history.any` is granted. Layer batches cannot delete layers, rename layer 0, freeze the current layer or make a frozen layer current. `Session::document` and `history` are private to the crate (read through accessors), so edits cannot skip the revision; view-state setters (`set_active_space`) and non-undoable viewport zoom (`store_view_layouts`) are explicit methods.
- **Geometry answers.** `geometry.measure` (`opendraft-api::measure::measure`: length, perimeter, area, centre, radius, end points; each answer says `exact`, `numeric` (ellipse and spline lengths) or `unsupported` (text, blocks, dimensions, hatches have only bounds); a closed polyline's area is the algebraic sum, an open one has none) and `geometry.intersections` (`Entity::intersections`, the Trim/Extend code; entities with no outline are listed as `unsupported`, not skipped silently; only pairs in the same space with overlapping bounds are tested; over 10,000 pairs or 10,000 points is `result_too_large`). Both need only `drawing.read`.
- **Audit and summary.** Two read-only looks (`drawing.audit`, `drawing.summary`; `drawing.read`, so a default connection has them) that tell a caller what is in a drawing and whether it is tidy without reading every entity. They take the same scope as `entities.query` (`automation/scope.rs`: a space, optionally a window, shared with it) and cost O(objects) on the UI thread, so the one expensive part, pairwise comparison, is capped (`AUDIT_OBJECTS_MAX` 20,000 objects and `AUDIT_COMPARISONS_MAX` 1,000,000 pairs: a check over the cap says `not_run` and to narrow with `layer_id`, `space` or `bounds`, instead of stalling the frame). The audit reuses `opendraft_core`, it does not reimplement: `duplicates` and `overlaps` are `overkill::overkill_capped` (OVERKILL's comparison; `overkill::prepare` is the one place that groups objects and marks the associative ones, now shared with the command; overlaps are the objects OVERKILL would merge, leaving out plain duplicates, and meeting end to end is not an overlap), `zero_length` and `empty_text` are `purge::unnamed_with(.., include_locked: true)` (PURGE leaves locked layers; a look must not), `unused_definitions` is `purge::purgeable` less linetypes (a new drawing carries the stock set, so they say nothing), and `layer_names` checks layer names against the `allowed_layers` the caller gives (case-insensitive, a trailing `*` is a prefix, layer 0 and Defpoints pass). It reports facts and never acts: results are bounded (`limit`, 30 by default, 200 at most; the count is complete) and carry the revision and `scanned`; names are drawing data and untrusted. The summary gives counts by kind and layer, block names with where the first is, the text a reader sees (`text::parse` then `plain_text`, one line, 120 characters, control characters removed), the box round everything that has one, and an 8 by 8 density grid (row 0 is the bottom; one count per object, in the cell of its box's centre) over the window asked for, else over everything: the overview a caller uses to choose where to look closer with `entities.query` or `view.render`.
- **Rendering.** `view.render` returns an SVG, or with `format: "png"` a PNG, through the plotting pipeline: `opendraft_core::plot_model::plot_region` (a window of model space scaled to a width, sharing `plot::add_viewed` with layout viewports so linetypes, text outlines, hatches, blocks and dimensions match what plots) or `plot_layout` for a whole sheet. The result names the revision drawn and how it differs from the canvas (white paper in plot colours, where white and the foreground colour print black; plot lineweights; wide polylines as single lines; hidden layers not drawn). Limits: 5,000 entities, 500,000 vertices, 6 MiB, width 50 to 4096; over any of them is `result_too_large`, never a cut-off picture. The sidecar returns the picture once, outside the structured part: an SVG as an embedded `image/svg+xml` resource, a PNG as an MCP image block (`image/png`), which is the form a model can look at (an SVG is text to a model and cannot be seen).
  - **PNG.** `opendraft_files::png` draws the same `PlotSheet` the SVG and PDF writers take, with `tiny-skia` (BSD-3-Clause; already in the program through `opendraft-ui`'s `resvg`, at the same version, so no new crate, and nothing parses SVG: the sheet holds only stroked polylines with round caps and joins, and non-zero fills for text and hatches, linetypes already baked into the paths). The width is in pixels (50 to 4096), the height follows the sheet, and `opendraft_files::png_size` gives both before anything is drawn so the limits apply first: a side over 4096 or more than 4,000,000 pixels is `result_too_large` (a picture is time on the UI thread, about 35 ms at that size in a release build; a model downscales a larger one anyway). No line is thinner than one pixel, so lineweights are not to scale and the result says so. Looked at on real drawings (leaders, hatches, solid fills, the linetype sample, dimensions, rotated and coloured text) it matched the SVG.
- **Commands.** `Command` carries `automation: AutomationPolicy` (`Denied` by default, `ImmediateSafe`, `InteractiveInApp`) and `effect: CommandEffect`. The one table that decides them is `opendraft-app/src/automation/policy.rs`; `build_registry` applies it, so an unlisted command stays denied, and tests require a row for every registered command (and no stale rows). Rules the tests keep: file, dialog and lifecycle commands are denied; only view, mode and selection commands (zoom, grid, snap and its modes, dynamic input, select all) are immediate; anything that asks for points is `InteractiveInApp` and is refused from `commands.invoke` ("use the entity tools"), never pretended to be immediate; Undo, Redo and Erase are denied (history and deletion have their own checked tools). `commands.list` shows what may run and whether it can now; `commands.invoke` needs the separate `command.invoke` grant (the Allow view commands switch), acts only on the drawing in the active tab (automation never switches tabs), goes through `Registry::execute` so enabled and busy checks apply, is refused with a retryable `operation_busy` while a modal dialog is open (a dialog writes its copy of settings back on OK and would undo the command), and requires `expected_revision` for any command that changes the drawing (none do today).
- **Files.** `files.open`, `files.save`, `files.save_as`, `files.export` (DXF, or a layout as PDF or SVG), `operations.get` and `operations.cancel`, in `automation/file_ops.rs` with the registry in `file_state.rs`. A call returns an operation handle (`op_N`) at once; the work runs on the app's own file worker from a copy taken when it starts, and the caller polls (`awaiting_consent`, `running`, `succeeded`, `failed`, `cancelled`). Rules:
  - The grant is its own switch (Allow files: `file.read` and `file.write`), separate from changes and commands, and the user must also approve folders (Settings > Automation > Approved folders, saved as `automation_roots`; none until added).
  - `opendraft_api::paths::check` is the one gate: absolute plain paths only (no `.` or `..` parts, network, device or extended-length paths, reserved names, alternate data streams, trailing dots), an allowed extension (`.odraft .dxf .dwg` to open, `.odraft` to save, the format's own to export), a regular file, never a link written through, and the canonical path (symlinks and junctions resolved, shown in plain `C:\` form) must lie inside an approved folder (checked per component, so a look-alike folder name does not pass). Results show only the file name, not folders. A path can still change between the check and the use; this narrows, it does not freeze the disk.
  - Saving a drawing to its own file needs no question; `files.save` never invents a file name. Replacing any other existing file (save as, export) waits for the user: a modal "Replace file?" built only from the path, the kind and the connection's self-chosen name (the safe choice is the default and Escape or X declines); it expires after 120 s, and turning automation off cancels waiting questions. A model's own say-so can never answer it.
  - Operation handles belong to the connection that made them, at most 8 unfinished each; `operations.cancel` stops only that job (`Io::cancel_job`, with the "being opened or saved" bookkeeping undone), never the user's own file work, and a cancelled save never replaces the file. Opening adds a new tab and makes it active (as the user opening a file does); an already open file is reported, not switched to.
  - No file operation touches a drawing that is in the Block Editor, and the Settings folder picker is the only way to approve a folder.
- **Interactive commands.** `commands.start_interactive` (`automation/command_runs.rs`) starts a command whose policy is `InteractiveInApp` and leaves its prompts to the user: they point and type in the app, and the caller can only start it, read what it asks and cancel it. The prompts never become remote clicks. It needs the `command.invoke` grant (the Allow commands switch), the active tab, no dialog open, and no command already running (it never replaces the user's: `command_busy`). A selection made first (`selection.set`) becomes the command's pickset, so its selection step is skipped as when a user starts it. The run is an operation (kind `command`) polled with `operations.get`: `waiting_for` carries the current prompt (app text, bounded, no control characters, data not instructions) and it ends `succeeded`, `cancelled` (Esc, or another command replacing it) or `failed` (the command's thread crashed). `AppState::command_serial` and `command_ends` (`command_record.rs`) are how a run is told from the next. `operations.get` and `operations.cancel` need only read access, because operations are private to the connection that started them. Starting waits up to 100 ms for the first prompt so the answer can say what it is.
- **Events.** `events.poll` (`automation/events.rs`): a log of the last 256 events (`document_opened`, `document_closed`, `document_changed`, `document_modified`, `document_saved`, `selection_changed`, `command_started`, `command_ended`) that the host fills by looking at the drawings and the running command once per frame, so it sees the user's edits and anyone else's without any editing code knowing. A caller polls with the `next_seq` it was given; `more` says to call again and `reset` says it fell behind the log and must reread. Because it samples, changes between two looks merge into one `document_changed` (the revision says how far it went); a drawing in the Block Editor is silent. `detail` text (titles, step names, command names) is bounded and stripped but untrusted. There are no subscriptions: the MCP SDK's resource subscriptions are not advertised, and polling by revision remains the contract. `selection_changed` is noticed by a digest of each drawing's selected ids (`detail` says how many are selected; read them with `selection.get`). View changes (pan, zoom) are not events: sampled once a frame they would flood a log of 256 and force `reset`. The optional adapter that turns scalar prompts into MCP `input_required` rounds is not built.
- **Idempotency keys.** Operations that would repeat their effect (`opendraft_api::idempotency::supports`: batches, undo and redo, `commands.invoke` and `start_interactive`, `selection.request` (so a retry finds its own prompt instead of being refused as busy), the file operations) accept an optional `idempotency_key` in their arguments. `dispatch` takes it out before the operation parses its arguments (so no argument type carries it) and consults `AppState::replays` (`automation/idempotency.rs`): a key already done by the same connection for the same operation, with the same arguments (a hash of the sorted JSON), returns the stored answer with `replayed: true` and runs nothing; the same key with other arguments is `idempotency_key_reused`. Only successes are kept (a failure leaves the drawing as it was, so running again is right), at most 256 answers of at most 256 KiB, oldest out first. Keys are plain (`[A-Za-z0-9_.:-]{1,64}`). The sidecar adds the property to exactly those tools' schemas, never retries a change after a lost connection (reads still retry once) and reports `instance_gone` with `outcome_unknown` instead. Setting the selection and cancelling an operation take no key: repeating them is harmless.
- **Selection requests.** `selection.request` (`automation/selection_request.rs`) asks the user to select objects in the app and returns their ids; nothing in the drawing changes. It needs `ui.selection` (Allow changes) and is an operation of kind `selection`, so it has the same handle, per-connection ownership, cap of 8 unfinished and idempotency key as a command run, and is polled and cancelled with `operations.get` and `operations.cancel` (there is no separate `interaction.*` family). It runs as an internal command named `Assistant` (not in the registry, so the ribbon and the command table never see it; the caller cannot choose the name, so a prompt under it cannot pass for the app) that calls `ask_selection`, so locked, hidden and frozen layers, the active space, Enter and Esc are the ones every command uses. Starting never replaces anything of the user's: `command_busy` (their command is running), `operation_busy` (a dialog is open), `invalid_reference` (not the active tab), `stale_revision`. The prompt is the caller's text made one plain line (control characters become spaces, 200 characters at most) with the wanted count appended; the selection starts empty unless `keep_current_selection`. When the user presses Enter, `Rule::judge` checks what is selected against the drawing *as it is then* (`Editor::read_revision`, one UI-thread step that also yields the revision): objects that are gone, no longer selectable, or not of the asked `kinds` or `layer_id` are taken out of the selection and the user is told, and if what is left breaks `min_count` or `max_count` (up to 1,000) it asks again. The finished operation carries `entity_ids` and the `revision` they belong to; a caller that then edits passes it as `expected_revision`. It ends `cancelled` (Esc, the caller, another command, the tab changing or closing), `failed` with `deadline_exceeded` (`timeout_seconds`, 300 by default and 900 at most) or `succeeded`. `AutomationCore::poll` withdraws a request, and tells the user, when its connection is gone or no longer holds `ui.selection`, and turning automation off does the same, so a prompt never outlives its caller. Waiting is the caller's job, because the app answers on its UI thread and never blocks it: `opendraft-mcp` implements `wait_seconds` (30 at most) on `operations_get` by asking again every 250 ms (`opendraft-mcp/src/wait.rs`), answering early when the operation finishes. MCP elicitation cannot show the canvas, so it is only for scalar and choice prompts (not built). Found by driving the real app: Enter from dynamic input at the cursor arrived as `Reply::Enter` on every `Wants::Selection` prompt, which `ask_selection` and `get_selection` treat as a cancel (Trim, Hatch, PEDIT and this); `answer_dynamic` now sends an empty line on a selection prompt through `answer_enter`. `FileOps::cancel_running` (the status bar's cancel of file work) also stopped marking running commands and selection requests cancelled while their prompts stayed up.
- **Shipping it.** `scripts/package.sh` builds release and assembles `dist/OpenDraft-<version>-<os>/` (the app, `opendraft-mcp` beside it, the licence, the readme and `docs/mcp.md` as `MCP.md`) plus a `.zip` (Windows, via the system `tar.exe` so names use forward slashes) or `.tar.gz`; `.github/workflows/release.yml` runs it on both systems for a `v*` tag or by hand and attaches the packages to the release (the workflow has not been run). The app finds the program by looking beside its own executable (`automation/setup.rs`); Settings > Automation shows that path and copies the `mcpServers` JSON for it. `opendraft-mcp --check` (`opendraft-mcp/src/doctor.rs`) connects, says what the connection may do, and exits 0 only if an app can be used. User documentation is `docs/mcp.md` (setup per assistant, switches, safety, troubleshooting, versions). Streamable HTTP is deliberately not built: it needs the OAuth, TLS and threat-model work the specification gates it on.
- **Measured (release, 16-10-2026).** On a 10,000-object drawing: a 100-entity page 0.63 ms at p95 (budget 16), one entity 0.01 ms (budget 5), a 1,000-operation add batch 11 ms in all, a full validation 0.4 ms (`cargo test --release -p opendraft-app budget -- --ignored --nocapture`). `opendraft-mcp` idles at 6.9 MiB with no CPU (budget 50 MiB); the app is 17.6 MB and the program 3.4 MB.
- **Tool catalogue.** `opendraft_api::catalogue` is the one list of tools: each is a name, a description, the operation it calls, an `Effect` hint and a schema, with `input_schema` adding the `idempotency_key` where `idempotency::supports` says. It knows nothing of MCP or a model vendor, so `opendraft-mcp` (which turns each `ToolDef` into an `rmcp::Tool` with its annotations, adds `wait_seconds` to `operations_get`, and answers the one tool only it can, `opendraft_instances_list`) and the in-app assistant read the same list. `take_pictures` splits a render result into its picture and the rest for both. Moving it out of `opendraft-mcp` changed nothing a client sees: `tools/list` was checked byte for byte before and after.
- **Tool schemas.** Generated from the `opendraft-api` argument types with sub-schemas inline (some hosts reject `$ref`), titles, null defaults and number formats (`double`, `uint32` and the `minimum: 0` that goes with them) dropped. `tools/list` is about 64 KB (30 tools; about 14 KB less if sub-schemas were shared with `$defs` instead of inlined; `the_listing_stays_small` fails at 66 KB, an alarm to raise on purpose when a tool is added; enum variants in a schema are plain comments, not docs, because their text is repeated in the listing), of which `opendraft_entities_apply_batch` is about 20 KB because the attribute and geometry unions repeat per operation; if that is too much context, move shared parts to `$defs` or split add/patch/replace into separate tools.
- **Using it.** Build `cargo build --release -p opendraft-app -p opendraft-mcp`. In OpenDraft turn on Settings > Automation, and tick Allow changes for the connection to let it edit. Point the MCP client at the `opendraft-mcp` executable (stdio, no arguments; `--instance <id>` if several apps run), e.g. Claude Desktop `{"mcpServers": {"opendraft": {"command": "C:\\path\\to\\opendraft-mcp.exe"}}}`. Turning the setting off drops every connection. Drawing text reaches the model as data: tool descriptions never include it.

## Embedded assistant (design decisions; the harness, the app side, a Mistral provider and the first panel are built)
Plan and phases: `private_material/mcp_harness_roadmap.md`. OpenDraft will offer an optional first-party assistant beside the external MCP route (Claude, Codex, Cursor and others using `opendraft-mcp`). Both reach the drawing through the same guarded operations; the engine never depends on a model vendor or on MCP.
- **Approvals and task grants (built, used by the assistant; `automation/grants.rs`).** A connection's permission is of three kinds, all created only by the owner of the core and never by the connection: its standing scopes (the Settings switches); a **task grant** (`begin_task`: the scopes held while an assistant's task runs, a count of the changes it has made, an optional limit, revoked by `end_task`); and **approvals** (`approve_once`: permission for one exact request, the operation with the very arguments the user was shown, used up when it runs and gone after five minutes, at most eight waiting; the retry key is not part of the request). `Grant::permit` decides, in that order (standing, then an approval, then a task), and `execute` spends what allowed the request under the same lock, so one approval cannot serve two requests. An approval is spent when the request is let through, whatever its outcome: a failed batch has to be rebuilt, which makes it another request that needs its own approval. A task can hold only `drawing.write`, `ui.selection` and `command.invoke` (never files, which keep their consent and approved folders, nor `history.any`); only `drawing.write` requests count against its limit. A prompt for the user is not a change to approve, so `selection.request` takes a standing or task scope; a task that ends takes its waiting prompt with it. This is what makes the approval levels hold below the assistant: a harness that tries to change the drawing without a grant gets `scope_denied` from the core, whatever the model said.
- **In-app connection (built, used by the assistant).** `AutomationCore::connect_in_process` gives a connection with no socket: it takes its own read-only grant (marked `in_process`, so Settings > Automation, which lists outside programs, leaves it out) and sends requests through the same queue, deadlines, caps, idempotency and operation ownership as a socket client. Only the owner of the core widens its scopes (`set_write` and the others). The assistant is what uses it, and the core is a separate thing from the socket, which stays opt-in (`AutomationHost` owns both).
- **The app owns the core; the socket is in front of it (built).** `OpenDraftApp` makes one `AutomationCore` at start (shared as an `Arc`, because the assistant's thread uses it) and polls it each frame while any connection exists. `SocketServer` (`automation/host.rs`) is only the listener: turning the setting on starts one in front of that core, turning it off drops it, which withdraws the descriptor, releases every outside program's grant (`Link::release_outside`) and ends each connection at its next request, and withdraws the selection prompts those programs left up. The in-app connection and its task are untouched by that. A `Link` (what connection threads hold) still cannot widen a grant; only the core's owner can.
- **The app side of the assistant (built; `assistant/`).** `AppHost` implements the harness's `Host` over the in-app connection. A read runs. A request the connection is not yet allowed to make is put to the user through a `Prompter` (the chat worker's `ChannelPrompter` passes it to the Assistant panel; tests script it) as the exact request, and only a yes gives the core `approve_once` for it. What the levels do: *Review each change* asks about each change; *Approve the plan* shows the plan and a yes opens `drawing.write` for as many changes as the plan has steps (`begin_task` with that cap); *Auto-approve* skips the prompt and allows up to the setting's count, never above `AUTO_APPROVE_CEILING` (50) in code. A rejected plan closes the changes again; `finish` ends the task and forgets unused approvals. A task starts holding only `ui.selection`, so the model can ask the user to pick objects. `selection.request` is waited for inside the host (the model has no `operations_get` tool), and Stop withdraws the prompt. `AutomationCore::coverage` says whether a request would pass without using anything up, and the core still decides again when it runs.
- **The harness (built, `opendraft-agent`; the Assistant panel runs it).** `run_task(provider, host, workflow, prompt, config, cancel, on_event)` runs one task on the caller's thread and returns a `Report` (final state, the conversation kept, counts). Its types are its own (`Message`, `Part`, `ToolCall`, `ToolResult` with text and pictures, `ModelRequest`, `ModelResponse`); a `Provider` (`complete(request, cancel)`) turns them into a vendor's wire form, and `FakeProvider` is a scripted one for tests. A `Host` is all the loop gets of the app: `call` (run a catalogue tool; it blocks and may wait for the user), `propose_plan`, `ask_user` and `finish`. **The harness cannot approve anything:** when a request needs permission the host asks the user and, only on a yes, gives the core that one permission, so a harness fault or a fooled model cannot make a change the user did not allow. A `Workflow` is data (system prompt, tools offered, plan-first, a verification prompt); `qa_review()` offers no tool that changes the drawing, and `edit()` holds the two batch tools back until a plan is approved. The model is offered only the tools of its workflow (the review's are about a third of the whole catalogue), a call is checked against what was on offer *when the model chose it*, and a change in the same turn as the plan waits for the next turn. Every changing call gets the retry key `{task}-{call id}`, replacing any the model wrote. `TaskState` has a transition table (a move it does not list ends the task as a fault). `Budgets` (20 model calls, 60 tool calls, 10 minutes, 400,000 bytes of results in all, 30,000 each, 10 pictures, tokens where the provider reports them) end a task with a named reason and keep the conversation; a result over its limit is cut with a visible marker; a picture is passed as a picture, and not as text. The model call runs on a worker thread the loop stops waiting for, so Stop is felt at once even though an HTTP call cannot be interrupted; a transient failure is tried again (three tries, doubling waits, cancel-aware). A chat is a series of tasks: `TaskConfig::history` takes an earlier report's `messages` and the new prompt continues them (two user turns in a row are sent as one), while budgets stay per task. Drawing text is data: it appears only inside tool results and the system prompt is never changed by it.
- **Copy chat as text (built).** The panel header has a copy button: the whole conversation as plain text, including the plan and every tool call with its arguments and its result (a picture is named, not pasted; each result is cut at 6,000 characters with a mark), headed by the kind, approval level and drawings in force. The transcript on screen says "Changed the drawing"; this is how a bad run is shown to someone who has to find out what it did.
- **The Assistant panel (built, `assistant/panel/`).** A dock tab (`PanelTab::Assistant`), opened from View > Palettes > Assistant and restored beside Layers; it is not in the default layout. A header (the chat's title, truncated, with the history and new-chat buttons), the transcript, a status line, and a rounded composer: a multi-line box (Enter sends, Shift+Enter adds a line), then a row of options (the drawing in view, Review or Edit, and for Edit the approval level) and a round send button that becomes Stop while a task runs. Your messages sit in a soft rounded box, the assistant's answers are plain text (`**bold**` and `- ` bullets only, `markdown.rs`), what it did is dim one-line entries, and a question it waits on is a card with its buttons (Allow once or Decline with the change shown on demand; Approve or Reject with the plan's steps and what approving allows; a clarification with choices and a text field). With no key the composer is a card asking for one (a password field, kept for the session only, and dropped again if the service refuses it). History replaces the transcript with the run's earlier chats. The panel only draws `Assistant` and turns clicks into calls on it; the session lives in `app/automation_update.rs` beside the core, polled once a frame. A typed key box and the transcript were driven in the real app (a dummy key was refused by the real service and explained in the panel).
- **Why the assistant has no per-part recipes (decided).** A first trial asked for a Class 600 NPS 4 weld neck flange; the model drew nonsense from raw coordinates although it recalled the dimensions, and a recipe tool for that one part fixed it. That was the wrong fix: it answers one prompt, a recipe per part cannot scale, and a table of standards in code is worse. A part is not special; the failure is generic (a language model cannot place geometry reliably from raw coordinates and does not check what it drew). The recipe (`opendraft_core::parts`, `parts.draw`) was therefore removed. The generic remedies, in order: exact construction operations in the batch (the drafter's own mirror, arrays, offset, transforms, regular polygon, which the program already has as tested geometry), a calculator for named dimensions and trig so the model never does arithmetic in its head, an automatic picture and measurements after each change, reference data (standards tables) as files the user supplies and one lookup tool, and part knowledge as written skill files that use those operations. Kept from the trial because they are generic: hatch in the write tool, the honest prompts, and the chat export.
- **Looking at its work (built, `assistant/host.rs`, `opendraft-agent/src/shape.rs`).** A model that cannot see what it drew reports success on a nonsense result. After any call that changes the drawing and adds or changes shapes, `AppHost` asks the app for a `view.render` (png, 640 wide, the whole drawing in model space, at the revision the change produced; a picture of only the new shapes hid what was missing around them) and merges the picture into the change's own result with `picture_of` (a label) and `picture_region` (the bounds shown). The harness takes a picture out of *any* tool result, passes it as a picture labelled with `picture_of`, and counts it against the picture budget (10 a task). The look is the host's, not the model's, so it cannot be skipped, and it is a read: a render that fails or finds the drawing moved on leaves the change's result as it was, and a layer-only change gets none. The Edit prompt says a picture follows each change and that anything wrong must be corrected before reporting; hatch only when asked and add nothing that was not asked for; and the verify step has the model list each thing requested (size, count, position, layer) and read each back with a query or measurement, a property not read back being unchecked. The dev runner (`OPENDRAFT_DEV_TRANSCRIPT=folder`) writes every call, result and picture the model saw.
- **A calculator (built, `opendraft-core/src/calc/`, `opendraft_calculate`).** A model that does arithmetic and trigonometry in its head gives a number that looks right and is a guess, which is how a bolt circle ends up in the wrong place. The calculator is a small strict expression evaluator in `opendraft-core` (pure and tested): a list of steps, each a name and an expression that may use the names before it, worked out in `f64` and returned in order. Numbers (with fractions and exponents), `+ - * / ^` (power is right to left and binds tighter than a leading minus, so `-2^2` is -4 and `2^-1` is 0.5), brackets, the constants `pi`, `tau` and `e`, and `sin cos tan asin acos atan atan2 sqrt abs floor ceil round round_to min max pow hypot exp ln log10 rad deg`; angles are radians, and `rad` and `deg` convert. No implicit multiplication and no units, so an expression means one thing. Anything that is not a finite number (a division by zero, the root of a negative, an overflow) is an error that names the step, never a quiet `inf` or `nan`; names are plain and may not reuse a constant, a function or an earlier name; the sizes (steps, length, nesting) are limited. The operation `calculate.evaluate` needs only the read scope and reads nothing of the drawing. Both workflows offer it and the shared prompt says to use it for every number: a number worked out by hand is a guess.
- **Tangent arcs, and a self-contained construct tool (built, `opendraft-core/src/tangent_arc.rs`, `automation/construct/shapes.rs`).** A bend such as a pipe elbow needs an arc that leaves a line without a corner; a model that works out its centre and angles gets it wrong (it swept 180° to 270° instead of 270° to 360° and the arc bent backwards). `Entity::tangent_arc(at_end, radius, sweep)` is the pure, tested geometry: from the end (or start) of a line or arc, the arc of that radius that goes on in the same direction, turning left for a positive sweep and right for a negative one. `entities.construct` has the step `tangent_arc` and a `line` step, so a whole bend (axis, bend, the two walls by `offset`) is one request using names, and `line`, `polygon`, `tangent_arc` and `offset` each take an optional `layer_id` (an offset copy otherwise keeps its source's layer, so walls could not be put on another layer). `geometry.measure` gives an arc's `sweep_degrees`, so a check can read the turn instead of inferring it from a length. A malformed batch now names the operation (its index and `op`) and what each kind takes, and says a geometry always names its type, even in a patch. The Edit prompt says to join straights with a tangent arc, to make the sides by offsetting the centreline and never to replace a curve with straight lines; the verify step asks for an arc's radius and sweep and both ends of shapes that should meet.
- **Construction operations (built, `automation/construct.rs`, `opendraft_entities_construct`).** The generic answer to a model that cannot place geometry from raw coordinates: say what to do, and the program does it exactly. One request is a list of steps (at most 100, run in order, all or nothing, one undo step by the caller, through the same `run_edit` the batch uses): `polygon` (centre, sides 3 to 1024, radius, inscribed or circumscribed, rotation, layer; bottom side level as POLYGON draws it), `move`, `rotate`, `scale`, `mirror` (across a line), `offset` (a copy a distance away on the side a point is on), `rect_array` and `polar_array` (the targets stay as the first item; polar can rotate the items or not and fill part of a turn). Move, rotate, scale and mirror change the targets, or with `copy_as` add copies and leave the originals. A target is a plain string: the id of an entity in the drawing (digits) or the name of a shape made earlier in the request (never all digits, so the two cannot be confused); new shapes get names the caller chooses, and copies are named `{prefix}_{k}` (`{prefix}_{k}_{n}` for several targets), so later steps and later requests can use them. The geometry is the program's own tested code (`Entity::translated`, `rotated`, `scaled`, `mirrored`, `offset`, `array::rectangular` and `polar`, `polygon::about_radius`), so nothing is written twice. Copies keep the layer, colour and space of the shape they came from; it touches only the kinds the batch tool can write; a refused step names its index and leaves the drawing as it was. It is a separate tool from the batch so the batch schema does not grow. The Edit prompt tells the model to use it for anything a drafter would copy, array, mirror, offset or draw as a regular polygon (make one bolt hole and polar-array it; draw half of a symmetrical part and mirror it). `construct_compose_tests.rs` composes a flange-like turned part from these steps and the hatch alone, with no recipe for it.
- **Hatch through the write tool (built, `automation/hatch_mutate.rs`).** `entities.apply_batch` can now add a hatch: `{"type": "hatch", "boundary": [...], "pattern": {"type": "named", "name": "ANSI31", "scale": 4, "angle": 0} | {"type": "solid"}, "associative": false}`. Each boundary is an existing closed entity (`entity_id`) or one added earlier in the same batch (`client_ref`; named ahead of its add it is refused before anything is edited). It is built as the HATCH command builds one: boundaries joined into loops (`loops_and_sources`), remembered as the hatch's sources, the associative flag set (or the hatch detached), and checked that it can be drawn with the same limits, so a scale too fine to draw is refused with a message that says to change it. A boundary that is not a closed shape, an unknown pattern name (the error lists the built-in ones) and an empty boundary are refused. A hatch can only be added, never patched or replaced. A first trial in which the model, with no hatch available, faked one with 14 hand-placed polylines (several ran outside the outline, and it called them "visually accurate") is why.
- **Making changes (built, `assistant/`).** *Undo this task:* after a task that changed a drawing, the transcript says "Made N changes" with an Undo button. Undo (`undo.rs`) takes back only steps whose provenance is that task's own connection, only while they are still on top of a drawing's history, and never more than the task is known to have made; the moment you have edited since, what is beneath your edit is left alone and the line says why ("Nothing could be undone: you have made changes since..."), and it will not run under a running command. This is the decision for the roadmap's open question about undo after your own edits: the assistant never undoes your work or reaches past it. *Which drawings:* the options row has a drawings choice, Current drawing or All drawings. It is the user's consent and holds for the whole task: `AppHost` is given a `Reach` (`Only(document id)` or `All`), refuses any call whose `document_id` names another drawing (a `scope_denied` that tells the model what the user can choose), and cuts the list of open drawings to what it may reach; the model is also told in its first line which drawings it may use. *A change in words:* the approval card says what will happen ("Add 2 lines and 1 circle", "Create 1 layer and set the current layer", `describe.rs`), names the drawing when more than one is open, and keeps "Show exactly what will be sent" one click away, so a summary is never a substitute for the request.
- **The chat behind the panel (built, `assistant/chat/`).** `Assistant` holds the conversations of this run, the one task that may be running, the unsent draft, the approval level and the workflow (`Review` offers no change tool; `Edit` plans first). All of it lives on the UI thread; a task runs on its own thread (`worker.rs`) and reports through a channel that `poll` drains once a frame, waking the window with a callback. A question the assistant needs answered (a plan, a change, a clarification) arrives as a `Pending` carrying the channel its answer goes back on; the screen shows it and calls `answer`, and `stop` withdraws it and ends the task. A conversation keeps the model's messages, so the next message continues it, and a new chat starts empty; earlier chats of the run are listed (newest first) and can be reopened. Each message is sent with one line saying which drawing is in view (its name and wire id, never its content). Tool activity is shown in plain words ("Checked the drawing for problems"), never tool names, and a stop or failure is explained ("Stopped: it reached the limit on tool calls."). The key is held only here, for the session, and handed to the provider factory; the type has no `Debug`, so it cannot be printed. `ProviderFactory` makes the model from the key (`mistral()`), and tests give it a scripted one.
- **Trying it by hand (built, `assistant/dev_run/`, a test).** `cargo test -p opendraft-app --bin opendraft assistant::dev_run::dev_run -- --ignored --nocapture` runs a prompt on a drawing file with the real harness, host and core, and either the scripted model or Mistral (the key from `MISTRAL_API_KEY` or `~/.opendraft/test.env`), with no window: the plan and each change are printed and answered y or n at the keyboard, and `OPENDRAFT_DEV_SAVE` writes the result to a file to open in the app. Choices are environment variables (`OPENDRAFT_DEV_FILE`, `OPENDRAFT_DEV_PROMPT`, `OPENDRAFT_DEV_WORKFLOW`, `OPENDRAFT_DEV_LEVEL`, `OPENDRAFT_DEV_PROVIDER`; the list is at the top of `dev_run/mod.rs`). It is a test so that the program that ships has no console path to the model; a request to pick objects is cancelled because there is no canvas. Scripted runs of it are ordinary tests, so it cannot rot.
- **The Mistral provider (built, `opendraft-agent/src/mistral/`; the Assistant panel uses it).** `MistralProvider` implements `Provider` over one blocking HTTPS call (`ureq`, rustls, the same client the update check uses; no async runtime) to `POST /v1/chat/completions`, non-streaming. `lower.rs` builds the request as JSON from our own types (system prompt first, tools as `{"type":"function",...}`, a call's arguments as a JSON *string*, each result as a `tool` message with the tool's name and the call id, a picture as a following user message naming the call because their documentation shows tool messages carrying text only); `raise.rs` reads the answer leniently (text as a string or chunks, arguments as a string, an object or missing; unreadable arguments kept as text so the loop refuses them, not guesses). Failures are sorted: 401 and 403, other 4xx and unreadable answers are `Fatal`; 408, 425, 429, 5xx, no connection and a timeout are `Transient` (the loop retries). The key lives in the struct only, goes out in one header, is scrubbed from every error text, and is hidden from `Debug`; nothing else in the crate or the app sees it. `recording_to(dir)` keeps each raw answer for fixtures. Tests run the real client against a loopback server and against answers recorded from the real service; two tests that call the real service are `#[ignore]` (`opendraft-agent/tests/mistral_live.rs`; the key from `MISTRAL_API_KEY` or `~/.opendraft/test.env`), run by the user, so the key never passes through a session. Seen in the real answers: tool-call ids are nine letters and digits; a final answer has `"tool_calls": null`; `finish_reason` was `tool_calls` and `stop`; usage has `prompt_tokens` and `completion_tokens`; a tool result as a `tool` message with name and call id is accepted; a picture in a user message is accepted. Still open: streamed deltas, and how a model reads a real render.
- **Boundary.** A new crate `opendraft-agent` (provider-neutral conversation and task state, the model, tool, result loop, budgets, cancellation) depends on `opendraft-api` and nothing below it. `opendraft-app` owns the panel, the approvals and the secrets. `opendraft-core`, `opendraft-commands`, `opendraft-files`, `opendraft-canvas` and drawing serialisation never see a model, a provider or MCP, and provider SDK types stop at the adapter. The loop does not spawn `opendraft-mcp`.
- **One guarded path.** The assistant calls the operations through `automation::dispatch` (a shared typed dispatcher), so scopes, `expected_revision`, `checked_transaction`, idempotency and undo provenance are not written a second time and cannot be skipped; it never calls `AppState` mutation directly. The tool catalogue and its schemas come from the `opendraft-api` argument types for both routes: `opendraft_api::catalogue`, built, free of `rmcp`. The dependency rule that keeps `opendraft-agent` from reaching `AppState` is tested (`opendraft-app/tests/crate_rules.rs`); the checks a request meets live in the core (`automation/core.rs`, `grants.rs`), which the assistant can only call.
- **Keeping the key (built, `assistant/keystore.rs`, `chat/keys.rs`).** `KeyStore` (`load`, `save`, `forget`) has one real implementation, the operating system's credential store through the `keyring` crate (Windows Credential Manager; the Secret Service over D-Bus on Linux, in pure Rust, so no system library is needed), under the service "OpenDraft" and the account "Mistral API key". The key card in the panel has a "Remember on this computer" box (ticked at first); without it the key is for this session only. At start the key is `MISTRAL_API_KEY` if set (never saved), else the kept one. "Key > Forget this key" removes it from the session and the store, and a key the service refuses is forgotten from both. If the store cannot keep it (no keyring service, a locked one) the session still has the key and the panel says why; a load that fails is a missing key, not an error. Tests use an in-memory store and a `NoStore`, never the real one; one ignored test round-trips the real store under a throwaway account. Not tested on Linux yet.
- **Provider.** First Mistral, bring-your-own-key: the user's key lives in the operating system's credential store and never in settings, drawings, conversation files, logs, MCP results or crash reports (with no credential service, a key for the session only). A configurable endpoint URL can follow. OpenDraft owns the message, content, tool-call, usage and stop-reason types a conversation is stored in. Licence compatibility with GPL-3.0-or-later is checked for any provider crate before it is added.
- **Permissions.** An embedded conversation is its own grant with its own provenance and starts read-only. The user picks an approval level in the chat: *Review each change* (the default), *Approve the plan* (one approval for a stated plan, asked again if it materially changes) or *Auto-approve for this task* (a count of changes, a stop button and one-step "Undo this task"). Writing or replacing a file always asks, whatever the level. The scope is a dropdown, *Current Drawing* (the default) or *All Open Drawings*; choosing the second is the grant, the panel lists the drawings it covers, the set is fixed when a task starts (a drawing opened later is not included until the user confirms) and cannot change while it runs. Every tool call names its drawing and revisions are per drawing.
- **Human input is a typed task state, not an error string:** approval, a short value, a choice, selecting objects (built: `selection.request`), finishing an interactive command (built) and consent for a protected file operation (built for replacing files). Task states: Idle, CallingModel, RunningTool, WaitingForUser, Paused, Completed, Failed, Cancelled.
- **Data and limits.** Drawing text and file contents are untrusted data, kept apart from instructions; nothing goes to a model before the panel shows what scope it covers. Pictures only on request, through a render call that takes a region (the model zooms rather than asking for bigger images): the full and a reduced size are cached locally, the model gets the reduced one, and the context keeps a text placeholder after a turn or two; Structure comes from data tools (entity queries, the bounded `drawing.summary`, measure and `drawing.audit` results, all built) and sight from a PNG on request (built: `view.render` with `format: "png"`; an SVG is text to a model and cannot be seen); a per-task cap on pictures enforces restraint, because a prompt asking for it is not a limit. Limits on turns, tool calls, time, bytes, pictures and tokens are app settings with hard ceilings in code. Conversation history is an app setting, off by default, kept under `profile::app_data` in files of their own (never in `.odraft`) with their own version number and a "Clear history" that also deletes the picture cache.
- **The generation fence (built, `opendraft-agent/src/workflow.rs`, `scope()`).** The Edit workflow may on its own create and change layers, change existing objects (move, rotate, scale, mirror, copy, attributes, text) and add dimensions. Generating objects (drawing new geometry, recreating a part or symbol from a description) is fenced off by the model's judgement, not by removing tools: the system prompt tells it to ask the user first, with `ask_user` and a plain warning that the result is experimental and every dimension is theirs to check, and to plan generation only on "Go ahead". The construct tool, the tangent arc and the rest stay on offer and tested, so the fence can be lifted by deleting the section. A prompt is a request, not a guarantee; if it proves leaky the next step is a harness-side check.
- **Workflows and discipline.** A workflow is data: its tools offered (QA Review offers no write tool at all), default approval level and scope, budgets, required stages and whether verification is mandatory. Care is structural: mutating tools are not offered until a plan is approved (`Planning`, `AwaitingApproval`), a required value that is missing is asked of the user, and a number that reaches the drawing must come from a tool result or the user, then be checked by deterministic tools (`geometry.measure`, audit operations), never by asking the model. A Concept mode writes only to scratch and reaches a drawing through an explicit promote step; it is a permission, not a tone.
- **Not goals.** Replacing the external route; giving a model `AppState`, the drawing file or unrestricted disk or network; unattended changes after the user closes a task; letting a model decide permissions, validation or confirmation; network-facing MCP over HTTP as a side effect (it stays gated on its OAuth, TLS and threat-model work).

## Profiles (where the app keeps its files)
Everything the app keeps lives in one folder, `eframe::storage_dir(<profile name>)`, and only `profile.rs` asks eframe for it (a test enforces this): code needing the folder calls `profile::app_data()`, and the window system's application name and window title are `profile::name()`. The name comes from the build: a release build is `OpenDraft`, a debug build `OpenDraft Dev`, a beta (`-beta`/`-rc` version) `OpenDraft Beta`, so a debug run no longer overwrites the release's settings, recents or recovery copies, and `cargo run --release` uses the release's own. `OPENDRAFT_PROFILE=<name>` (letters, digits, space, `-`, `_`, at most 32) picks `OpenDraft <name>` for tests and for trying a migration on a copy. A beta's first run copies the release's `app.ron` and `window.json` once and never writes back. Drawings are not part of a profile. Automation descriptors are separate: set `OPENDRAFT_AUTOMATION_DIR` for both the app and `opendraft-mcp` to keep a development app out of the real list.

## Windows window and crash log
A Windows **release** build of `opendraft` is a windowed program (`#![cfg_attr(all(windows, not(debug_assertions)), windows_subsystem = "windows")]` at the top of `main.rs`); without it the exe is a console program and double-clicking it opens a console window beside the app, which also ends the app if closed. Debug builds keep their console for development, and `opendraft-mcp` stays a console program because it speaks over standard input and output. A windowed program has no console for a panic message, so `crash_log::install()` (first thing in `main`) records every panic (time, version, thread, message, place, backtrace) in `crash.log` in the profile's folder (`profile::app_data`: `%APPDATA%\<profile>\data` on Windows, `~/.local/share/<profile in lower case>` on Linux), cut back to its newest reports at 256 KiB, and then runs the ordinary hook so a terminal still shows it. A panic inside a command is caught and the drawing carries on, but it is logged too. The app menu's **Crash log** item (and `CRASHLOG`) is the command `manage.crash_log` (`AppState::show_crash_log`): it reveals the file in the file manager through `reveal.rs` (shared with the Home page), or says there is none. Not built: telling the user, when it happens, that a crash was recorded.

## Update checks (`opendraft-app/src/updates/`)
The program can tell the user a newer version exists. It only informs: nothing is downloaded or installed (installing is a later phase that needs signed installers). It is **off until the user says yes** (`Settings::update_checks` is `None` until answered; the Updates card on Home asks, Settings > Updates mirrors it), so a fresh install makes no network request. Once allowed, `Updates::tick` (every frame, cheap) starts a check on its own thread when none was made for 24 hours (an hour after a failure; "Check now" forces one). The thread does one HTTPS GET of the project's releases list (`fetch.rs`, `ureq` with `rustls`; 10 s timeout, 2 MiB cap) sending only `User-Agent: OpenDraft/<version>` and the ETag of the last answer, so an unchanged list costs a 304. `releases::newest` (pure) takes the highest semver above this build's version, skipping drafts, tags that are not `v<semver>`, prereleases unless this is a beta build, and releases lacking this system's package (`OpenDraft-<version>-windows.zip` / `-linux.tar.gz`, the names `scripts/package.sh` makes), so a release still being uploaded is not announced. The newest `/releases/latest` is not used (it is by creation date, so a late backport would win). The answer is stored (`update_state` key: last check, ETag, newest found, skipped version, remind-after), so the notice shows at the next start with no network. "Skip this version" hides that version only; "Remind me later" hides for three days. The address opened on "View changes" is built from the version (`release_page`), never read from the reply, and release text is never shown. Failure is silent: the card says it could not check, the title bar does not change. Development (debug) builds never check; `OPENDRAFT_UPDATES_URL` replaces the list's address (and lets a debug build check) to try it against a local server. What it shows: the Updates card (`app/home_page/updates.rs`), the title bar's right-hand text (`app/update_notice.rs`: the name, "Allow internet access to stay up to date" before the user has answered, "Version X is available. See Home" when there is one), and Settings > Updates.

## Translations (the setup built; texts are wrapped step by step, issue #138)
Texts are written in English in the code and wrapped in `rust_i18n::t!("...")` (crate `rust-i18n` 4, MIT): the English text itself is the key, with no `minify_key`, so the code still reads in English and a translator reads whole sentences. `locales/<code>.yml` at the root of the repository, one file per language shared by every crate, maps each English text to its translation; a text a file leaves out is shown in English, so a language can be translated a few texts at a time and English is never changed. Placeholders are named, `t!("Same as the system (%{language})", language = ...)`, and a translation keeps them. A crate that translates calls `rust_i18n::i18n!("../../locales")` at its root (the app in `main.rs`, `opendraft-ui` in `lib.rs`); the files are read at compile time, and each such crate's `build.rs` rebuilds when `locales/` changes. The language is `Settings::language` (`None` follows the system's, through `sys-locale`, when it is offered, otherwise English), chosen in Settings > Display and applied by `language::apply` at start and on OK or Apply: every frame draws its texts again, so it takes effect at once, except for the prompts and answers already written in the command history. The ribbon is translated where it is drawn (`opendraft_ui::ribbon::tr`): its data (`ribbon_def`) stays in English, which the app matches on (tab titles, split picks), so its labels are keys without a `t!`; widths follow the translated text, and a translation may cut a big button's label into two lines with `\n` (elsewhere shown as a space, by `opendraft_ui::i18n::tr`; without one the label is cut at its first space). Other texts that are also data (menu tables, the status bar's toggles and snap modes, palette titles, the Properties rows, `ByLayer`, `Varies`) stay English where they are defined, marked `opendraft_ui::key!("...")` (it gives the text unchanged), and are translated with `opendraft_ui::i18n::tr` where they are drawn. Labels from `opendraft-core` (kinds of object, hatch island styles, arrowheads, leader types) are translated the same way in the Properties palette, which also reads a translated value back when it is typed (`Oui`, `Extérieur`). Tests (`language_tests.rs`) check that every key of every translation file is still the text of a `t!` or a `key!` in the code, a text of the ribbon or a label from `opendraft-core`, and that translations keep their placeholders. Prompts: a command still asks in English, since outside callers (the automation host, MCP, the Assistant) read `ask.message`; the prompt is translated where it is shown (`interact.rs`: the command line, dynamic input and the status bar), with the " or" joined before the options translated too. Prompt texts are marked `key!("...")` where the command asks them. A prompt with a value in it is asked with `Options::worded(key!("Enter new value for %{name} <%{current}>"), &[("name", ...), ("current", ...)])` (`opendraft_commands::Wording`): its message is the filled English text, as before, and it keeps the wording and the values, so the interface translates the wording and fills it again (`prompt_language::shown`). A value that is itself a word to translate (TRIM's mode, LENGTHEN's total or delta, a purge category) is not a field: each case is a whole sentence of its own, so a translation can follow its own grammar. Built so far: the setting, the ribbon (tabs, panels, buttons, tooltips, the layer list's switch tooltips), the menus (application menu, right-click menus of the drawing, of the Layers palette and of the layout tabs, the Shift+right-click snap menu), the palettes (titles, Layers, Properties, the command line's buttons, Assistant) and the status bar, the prompts of the commands (draw, modify, grips, selection, zoom, view, CCS, dimensions, text, leaders, blocks, attributes, fields, layers, layouts, plot, purge and system variables, one-off snaps), and the prompts' options, in French. Prompt options are bilingual, as in a localised AutoCAD (`option_language.rs`): the command offers them in English and is always answered with the English label (`Reply::Keyword`), whatever the language. The interface shows each option translated under the key `[English label]` in `locales/` (`[context: label]` for a label that means something else elsewhere, offered with `Options::keyword_in`, as SPLINE's Fit), and the capitals written in the translation are its shortcut, as AutoCAD writes them (`annUler` is picked by U; the English letter is kept where the French word has it). Typing the shortcut or the start of the word shown picks it, accents optional; the English option after `_` (`_Undo`, `_U`) picks it in every language, so scripts and outside callers do not depend on it; an exact shortcut wins over the start of a label (L is Longueur when LArgeur is offered). A name that is data (a block, a layout) has no translation and is shown as written. Tests (`option_language_tests.rs`) read every `.keyword(...)` chain and `("Label", "KEY")` table of the app's sources, with a list of options that are joined at run time, and check that no two options of one prompt share a shortcut in any language, that every option has its French and that every option translation is still offered. Command names are bilingual the same way (`command_language.rs`): the commands keep their English names and aliases (`cmd_aliases.rs`) and are run by id, so the automation host, MCP and the Assistant never see a translated name. A translation gives each command its name and aliases under the key `$` and its English name, separated by commas (`"$LINE": "LIGNE, L"`); typed without `_`, only the names of the interface's language run a command (`LINE` is unknown in French, as in AutoCAD), accents optional, and the English name or alias after `_` (`_LINE`, `_L`, `_-PLOT` or `-_PLOT`) runs it in every language. A leading `'` (`'ZOOM`) is accepted and changes nothing. A command with no translation keeps its English names. The command line suggests, echoes ("Commande : LIGNE"), remembers for Up and shows before its prompts the name of the interface's language; the runner keeps the English name it was started with (`is_running`). Tests (`command_language_tests.rs`) check that no two commands share a name or alias in any language, that every command has its French names and that every `$` key is a command. Messages (what a command says without asking: "No previous view saved.", "Moved 3 objects") are said in English too, since the status line goes back to the automation host (`InvokeResult::message`), and translated where they are shown (`message_language.rs`): the command line keeps its log in English (`CommandLine::log`) with the wording of each line that has values, and shows it through `shown_log`; `AppState::message` stays English and `message_wording` holds its wording (`AppState::tell` says a message in both, `set_message` in the status bar only). `Editor::say` takes text or a `Wording`; a plain message is marked `key!("...")` where it is said (`opendraft_core::key!` in the core, for refusals such as `CornerError`). A message with values is a `Wording` with `%{name}` fields; a field may be filled by another wording, translated with it (`Wording::part`), and a count picks a sentence for one and one for the rest (`Wording::count`; `text::objects` gives "1 object" / "3 objects"), so a translation follows its own grammar. A test lists the files whose messages are all marked and fails on any `say("...")` or `say(format!(...))` left in them. A reason from another function is a part (`message_language::because(key!("Unable to hatch: %{why}"), why)`), translated when it is a marked text; `SysVarError::wording` does the same for system variables. Messages built so far: draw, modify, fillet and chamfer, arrays, PEDIT, one-off snaps, measuring, zoom, view and CCS; files (open, save, export, templates, autosave), the clipboard, layers, layouts and viewports, plot and -PLOT, blocks and the Block Editor, attributes, fields, dimensions, leaders and multileader styles, text, hatch, PURGE, OVERKILL and system variables, with the core refusals they show (block and attribute names, layer deletion, hatch boundaries).

## Plugins (design decision, not yet implemented)

Plugins are written in **Python**: the likeliest authors already know it, and
the whole PyPI ecosystem (ezdxf, numpy, shapely) is available to them. They run
**out of process**: a plugin is a script that imports a small `opendraft`
package and talks to the app over a local pipe. This keeps the app free of an
embedded interpreter, lets a script block while waiting for the user
(`p = get_point("Pick start")`), and means a crashing plugin cannot take the
drawing down. Whether we bundle a Python or require the user's own is a
packaging decision that does not change the API. No custom scripting language.

What the app must keep true so the API is cheap to add later:

1. **The command registry is the API.** Plugins register commands (id, label,
   shortcut) and run existing ones by id. Command ids are stable once released;
   never rename one casually.
2. **All document changes go through `Action`s inside a transaction**, so a
   plugin's edits are undoable and grouped into one undo step like any other
   command.
3. **Prompts are a service, not UI code.** Asking the user for a point, a
   number or a selection is one request/response interface (the `Editor`'s
   `get_*` methods) that the command line, canvas and plugins all use. A
   plugin's `ed.get_point(...)` is forwarded to it.
4. **Core and commands stay free of egui** (see the crate table), so the same
   operations can be driven by a script, a test or the UI.
5. **State a plugin may read is plain data** (entities, layers, selection,
   settings) and is addressed by id. Plugins never hold references into the
   app.
6. The wire format is versioned from the first release, and plugins declare
   which API version they target in a manifest.

## Where things are

- Panels: `opendraft-app/src/app/panels.rs`; command line UI: `app/command_line.rs` (and `app/command_line_strip.rs` for its grip when docked above or below the drawing); dock layout: `dock.rs` (panels, default layout, saving), `dock/places.rs` (where hidden panels return), `dock/targets.rs` and `dock/drag.rs` (dragging a panel: tab-bar drops are egui_dock's, body drops float, explicit targets dock);
  Properties: `properties.rs` (model) and `properties_ui.rs` (view). The geometry rows are the ones every shown entity has. A polyline that traces a rectangle (four straight sides at right angles, closed or with a last vertex back on the first, whichever command drew it and at any angle; `opendraft-core/src/rect_shape.rs`) is titled Rectangular polyline and also shows Width and Height (its first and second sides) and Angle (its first side), typed over with the first corner, the vertex order and the turn kept; a `Rectangle` object shares Width and Height with it. Its four corners may also be rounded alike (quarter circles of one radius) or bevelled alike (the same distance along both sides), as RECTANGLE's Fillet and Chamfer draw them, the polyline starting with a corner or with a side: Width and Height then run to the sharp corners, and a Radius or Chamfer row is added. A typed value is refused when a side would keep no straight part. Square corners show neither row, and corners that differ are not recognised. A polyline that traces an oblong (four vertices: two straight sides the same length facing each other, joined by two half circles turning the same way; `rect_shape::slot_of_polyline`) is titled Oblong polyline and shows Center X and Y, Center distance (between the centres of its ends), Width (across) and Angle (its first straight side), typed over with the centre staying put, the vertex order, the turn, the arcs and the widths kept.
- Visual constants and palettes: `opendraft-ui/src/theme.rs`. What comes next:
  `docs/ROADMAP.md` (priorities and next steps), `docs/parking_lot.md` (everything
  not built yet) and `2d_commands_reference.md` (the AutoCAD command list we
  work through).
- A new modify command: pure geometry in `opendraft-core` (+ tests), the command in
  its own `opendraft-app` file, an `editor_command!` line in `commands.rs`, an alias
  in `cmdline.rs`, a ribbon item in `ribbon_def.rs` or, for the Home tab,
  `ribbon_def/home.rs` (if Home already shows it dimmed, take its id off
  `NOT_BUILT` there; icons are codepoints in `opendraft-ui/src/icons.rs`; find names
  in the font with fontTools, then run `scripts/export_icons.py` for the new
  icon's SVG), a description in this file, and its line taken off
  `docs/parking_lot.md` (and `docs/ROADMAP.md`'s next steps) if it was listed.
- Testing in the real app (Windows): build `opendraft-app`, drive the exe with
  PowerShell (keys, clicks, screenshots). Click on a grip location starts a
  grip edit, so pick selection points away from grips.
